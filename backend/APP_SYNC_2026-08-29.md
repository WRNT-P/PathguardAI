## 1.1 คำถามข้อ 1 (แอปส่งตำแหน่งถี่แค่ไหน) — ไม่ต้องรอคำตอบแล้ว

เดิมบอกว่าการจัดอันดับติดคำถามนี้ **ไม่ติดแล้ว** เพราะเปลี่ยนวิธีออกแบบ:

**ผู้ดูแลที่ตำแหน่งเก่าเกินเกณฑ์ หรือไม่เคยส่งตำแหน่งเลย จะถูกดันไปท้ายรายการ ไม่ใช่ถูกตัดออก**

ถ้ากรองออก วันที่แอปส่งตำแหน่งห่างกว่าเกณฑ์ที่เราเดา endpoint จะตอบว่า "ไม่มีใครเลย"
ตอนที่ผู้ป่วยหายจริง ต่อหน้าครอบครัวที่ยืนอยู่ตรงนั้น — รายการที่เรียงผิดคนอ่านแก้เองได้
รายการว่างแก้ไม่ได้

ทุกแถวมี `usable: true/false` มาให้ **แอปควรแสดงแถวที่ `false` ต่างออกไป** (เทาลง หรือเขียนว่า
"ตำแหน่งเมื่อ 2 ชม.ที่แล้ว") ไม่ใช่ซ่อน

ตอบมาเมื่อไหร่เราแก้ตัวเลขในฐานข้อมูลแถวเดียว **ไม่ต้องแก้โค้ด ไม่ต้อง deploy ไม่กระทบแอป**
ตอนนี้ตั้งไว้ 30 นาที และส่งค่ามากับทุก response (`max_age_s`) เพื่อให้คุณเขียนข้อความได้ตรง

## 1.2 คำถามข้อ 2 (กด "ฉันไปรับ" แล้วคนอื่นเห็นอะไร) — ทำค่าตั้งต้นไว้แล้ว

ทำไปตามนี้ **ถ้าอยากได้ต่างจากนี้บอกมา แก้ให้**

* คนอื่นได้ push ทันที ไม่มี cooldown: **"[ชื่อ] กำลังไปรับผู้ป่วย"**
* **คนกดเองไม่ได้ push** — แจ้งเตือนคนเรื่องปุ่มที่เขาเพิ่งกดเอง คือวิธีสอนให้เลิกอ่านแจ้งเตือน
* มีคนรับไปแล้ว → `409` **พร้อมชื่อ + เวลาในตัว error เลย** แสดง "ลูกชายรับเรื่องนี้แล้วเมื่อ 14:02"
  ได้โดยไม่ต้องยิงซ้ำ
* **เปลี่ยนใจได้** `DELETE` เฉพาะคนที่รับไว้ แล้วคนอื่นรับต่อได้
* ยังไม่มี: **ตำแหน่งบนแผนที่ของคนที่กดรับ** ตอนนี้เห็นแค่ชื่อกับเวลา — ข้อมูลมีอยู่แล้วใน §12.3
  อยากได้บอกมา ต่อให้ไม่ยาก

🛑 **"รับเรื่อง" ไม่ใช่ "จบเรื่อง"** คนละฟิลด์กัน ตั้งใจ — `resolved` แปลว่าผู้ป่วยปลอดภัยแล้ว
ปิดด้วย `PATCH /api/alerts/{id}` เหมือนเดิม ถ้ากดรับแล้วปิด alert ไปด้วย ครอบครัวจะเสียแถวเดียว
ที่บอกว่าเรื่องยังไม่จบ

# 2. Safe Zone Navigation — เป็นของคุณทั้งก้อน

**เมื่อวานเราบอกว่า "backend จะสร้างตาราง POI ให้" วันนี้ยกเลิก** และเหตุผลไม่ใช่เพราะขี้เกียจ

ตาราง POI ที่เราป้อนมือจะครอบคลุม**เฉพาะพื้นที่รอบบ้านผู้ป่วย** ซึ่งเป็นที่ที่เขา
*ปลอดภัยที่สุดและต้องการฟีเจอร์นี้น้อยที่สุด* และครอบคลุม **0% ตอนเขาเดินหลงออกไปไกล**
ซึ่งเป็นตอนที่ต้องการมากที่สุด **ความครอบคลุมของข้อมูลสวนทางกับความจำเป็นของฟีเจอร์พอดี**
คุณมี Google API key อยู่แล้ว Places ตอบได้ทุกที่ที่ผู้ป่วยไปโผล่

## 🔴 แต่มี endpoint หนึ่งตัวที่คุณต้องใช้ และเราไม่เคยบอกคุณว่ามันมี

```
GET /api/danger-zones
```

**มีมาตั้งแต่ 20 ส.ค. ใช้ได้เลยวันนี้** เพิ่งเขียนลงสัญญาวันนี้เป็น **§13** — ขอโทษด้วย
เป็นรูปแบบเดิมกับ `places` (§10) และปุ่ม SOS: ของสร้างเสร็จแล้วแต่คนที่ต้องใช้ไม่เคยถูกบอก

**ทำไมต้องใช้:** Google จะคืนโรงพักที่อยู่**คนละฝั่งทางหลวง**มาให้หน้าตาเฉย เพราะระยะเส้นตรงใกล้
Google ไม่รู้ว่าอะไรอันตรายสำหรับผู้ป่วยสมองเสื่อม **เรารู้ และเก็บไว้ในตารางนี้**
(ทางหลวง คลอง ไซต์ก่อสร้าง พร้อมเหตุผลที่เอาไปแสดงบนจอได้เลย)

ถ้าไม่กรอง แอปจะนำทางคนสับสนข้ามถนน 6 เลนเพื่อไปหา "ที่ปลอดภัย"

**วิธีใช้ ดู §13** — สั้น ๆ คือ ยิงครั้งเดียวแคชไว้ · ตัดผู้สมัครที่อยู่ในวงกลม · ถ้าเส้นทางผ่านวงกลม
ให้เลือกที่อื่นก่อน

## ⭐ กลไกทั้งหมดอยู่ในรายงานแล้ว — เราไปอ่านมา ไม่ต้องออกแบบใหม่

รายงานข้อ 1.4/1.5/1.6 เขียนไว้ครบ ยกมาตรง ๆ:

> **1.6 SOS** — กดแล้วส่ง SOS signal + GPS ปัจจุบัน **ระบบจะแยกว่า Alzheimer level
> ของผู้ป่วยอยู่ระดับใด เพื่อส่งต่อไปยัง Zero-UI Mode (ระยะ 2) หรือ Safe Zone Navigation (ระยะ 1)**
>
> **1.5 Safe Zone Navigation** — ทำงานเมื่อผู้ป่วยกด SOS หรือเข้าสู่ Zero-UI Mode
> นำทางไปพื้นที่ปลอดภัยใกล้สุด เช่นสถานีตำรวจหรือโรงพยาบาล **พร้อมแจ้งผู้ดูแลให้ไปรับ**
>
> **1.4 Zero-UI Mode** — เฉพาะระยะ 2 เมื่อกด SOS สลับหน้าจอเหลือข้อความเดียว
> **"ยืนรอตรงนี้ ผู้ดูแลกำลังมารับ"**

แปลว่า **Safe Zone Navigation ไม่ใช่ปุ่มแยก มันคือปลายทางหนึ่งของปุ่ม SOS ที่คุณมีอยู่แล้ว**

| กด SOS แล้ว `severity_level` เป็น | ไปที่ |
|---|---|
| `1` | Safe Zone Navigation — นำทางไปที่ปลอดภัย |
| `2` | Zero-UI Mode — "ยืนรอตรงนี้ ผู้ดูแลกำลังมารับ" |
| `null` | **ทำเหมือน `2`** — บอกให้ยืนรอทั้งที่เดินได้ เสียหายน้อยกว่าบอกให้เดินทั้งที่ไม่ควรเดิน |

**ของใหม่วันนี้: `POST /api/sos` คืน `severity_level` กลับมาให้แล้ว** จะได้แยกทางได้ทันที
ในจังหวะที่กด ไม่ต้องยิงซ้ำ ดู §8

🛑 **ระวัง `severity` กับ `severity_level` สลับกัน** — `severity` คือความรุนแรงของ alert
(เป็น `"critical"` เสมอ) ส่วน `severity_level` คือระยะของโรค **อ่านผิดตัว = ส่งผู้ป่วยระยะกลาง
ออกไปเดินข้ามถนน** เขียนเตือนไว้ใน §8 แล้ว

## แล้ว "แจ้งผู้ดูแลให้ไปรับ" ล่ะ — ✅ มีอยู่แล้ว ไม่ต้องทำอะไรเพิ่ม

`POST /api/sos` เขียน alert แล้ว push หาผู้ดูแล**ทุกคน**อยู่แล้ว (และตั้งแต่เมื่อวาน
ผู้ดูแลกดรับเรื่องได้ด้วย §12.4) ประโยค "พร้อมแจ้งผู้ดูแลให้ไปรับ" ในรายงานคือ push ตัวนี้เอง

## เรื่องเดียวที่ต้องเช็คก่อนเริ่มเขียน

**Places API ต้องเปิดแยกจาก Directions** ใน Google Cloud คนละ API คนละบิล
ต่อให้เป็น key เดียวกันก็ต้องไปเปิด Places API ในโปรเจกต์นั้นก่อน

# 3. ข้อที่ยังค้าง — เหลือข้อเดียว

## 🛑 ขอ 1 หน้าจอ เรียก 1 endpoint จริง

**ถามไปเมื่อวานแล้วและยังไม่ได้คำตอบ ขอถามซ้ำเพราะมันเป็นเรื่องตารางเวลา ไม่ใช่เรื่องเทคนิค**

W1 ของแผน 4 สัปดาห์คือ "GPS จากมือถือจริงไปถึงฐานข้อมูล" — **ยังไม่เริ่มเลยสักก้าว**
และ W2/W3/W4 ต่อคิวอยู่หลังมันทั้งหมด แผนครบราว 11 ก.ย.

ฝั่ง backend ตอนนี้มี **31 endpoint พร้อมใช้ เทสต์ผ่าน 391 ตัว ฐานข้อมูลจริงพร้อม**
แต่ยังไม่มีสักเส้นที่ถูกแอปเรียกจริง ความเสี่ยงทั้งหมดของโปรเจกต์กองอยู่ตรงจุดนี้จุดเดียว

**ไม่ได้ขอให้หยุดทำ UI** ขอแค่ 1 หน้าจอ เรียกจริง 1 ครั้ง ตัวที่เหมาะที่สุดยังเป็น
`GET /api/recommendation/{id}` (§11.1) เพราะคุณ mock `recommendedPlaces` อยู่แล้ว
เปลี่ยนเป็นของจริงคือแก้ที่เดียว **และพอต่อเสร็จ ระบบนำทางที่คุณทำเสร็จแล้วจะพาไปหมุดจริง
ของผู้ดูแลแทนข้อมูลปลอมทันที**

**บอกมาว่าพร้อมวันไหน** เราต้องเปิด `AUTH_ENABLED` + เปิด tunnel ให้ ใช้เวลาไม่กี่นาที
แต่ต้องนัดกัน เพราะ tunnel รันบนโน้ตบุ๊กและ URL เปลี่ยนทุกครั้งที่รีสตาร์ต
