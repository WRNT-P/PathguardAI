> · **แก้ 2026-08-27 หัวข้อ 2 ขั้นที่ 4 — `GET /api/patients/{id}` และ `severity_level` ใน response ของ `/api/pair`**

ก่อนหน้านี้เวลาผู้ป่วยเดินหลง ระบบเขียนแถวลงตาราง `alerts` แล้วจบ ไม่มีอะไรออกจากเซิร์ฟเวอร์
วิธีเดียวที่จะรู้คือต้องนั่งเฝ้า dashboard เอาไว้ ตอนนี้ต่อสายสุดท้ายแล้ว

# 1. ลงทะเบียนเครื่องผู้ดูแล

## `POST /api/devices/token`

**ถ้าไม่เรียกอันนี้ = ไม่มี push ตลอดกาล** alert จะถูกเขียนลง DB แล้วไม่ไปไหน

### Request

```json
{
  "user_id": 12,
  "token": "fcm-registration-token-จาก-firebase-messaging",
  "platform": "android"
}
```

| ฟิลด์ | ชนิด | หมายเหตุ |
|---|---|---|
| `user_id` | int | `users.id` ของ **ผู้ดูแล** ไม่ใช่ของผู้ป่วย — ได้จาก `POST /api/register` |
| `token` | string 10–255 | จาก `FirebaseMessaging.instance.getToken()` |
| `platform` | `android` \| `ios` \| `web` | default `android` |

### Response `200`

```json
{ "id": 1, "user_id": 12, "platform": "android" }
```

`404` = ยังไม่ได้ `POST /api/register` ก่อน

### เรียกเมื่อไหร่

- หลัง sign-in ครั้งแรก
- **ทุกครั้งที่เปิดแอป** — Firebase ออก token ใหม่ตอนลงแอปใหม่ และหมดอายุเองได้
- ตอน `onTokenRefresh` ยิง

เรียกซ้ำได้ ไม่เกิดแถวซ้ำ (upsert ยึด token เป็นตัวตน) และถ้าเครื่องเดียวกันมีคนล็อกอินใหม่
token จะย้ายไปเป็นของคนหลังสุดโดยอัตโนมัติ

# 2. ผูกผู้ป่วยกับผู้ดูแล — ด้วยรหัสจับคู่

> **เปลี่ยนเมื่อ 2026-08-26** เดิมหัวข้อนี้เขียนว่า *"ไม่มีรหัสเชิญ ไม่มีตารางจับคู่"* และให้
> ผู้ป่วยเรียก `POST /api/register` เอง **ยกเลิกแล้ว** — ผู้ป่วยอัลไซเมอร์ถือ email + password
> ไม่ได้ ตอนนี้ผู้ดูแลเป็นคนสร้างผู้ป่วย แล้วได้รหัสมากรอกบนเครื่องผู้ป่วย

## ขั้นที่ 1 — ผู้ดูแลสร้างผู้ป่วย

```json
POST /api/patients
{ "name": "ยาย", "severity_level": 2, "caregiver_id": 12 }
```

| ฟิลด์ | จำเป็น | หมายเหตุ |
|---|---|---|
| `name` | ✅ | 1–255 ตัวอักษร |
| `severity_level` | ⬜ | `1` = ระยะต้น · `2` = ระยะกลาง · ไม่ส่งก็ได้ |
| `caregiver_id` | ⚠️ | **ส่งเฉพาะตอน `AUTH_ENABLED=false`** พอเปิด auth แล้ว backend ยึดจาก token เสมอ และ**เมินค่าที่ส่งมา** เพื่อไม่ให้ใครผูกผู้ป่วยเข้าบัญชีคนอื่น |

ตอบ `201`:

```json
{
  "patient_id": 42,
  "name": "ยาย",
  "severity_level": 2,
  "caregiver_id": 12,
  "pairing_code": "7K2M-P9QX",
  "expires_at": "2026-08-27T09:15:00Z"
}
```

| สถานะ | เมื่อไหร่ |
|---|---|
| `404` | `caregiver_id` ไม่มีในตาราง `users` |
| `422` | **ใหม่ 30 ส.ค.** — `caregiver_id` มีอยู่จริง แต่แถวนั้น `role` ไม่ใช่ `caregiver` เดิมผ่านได้ ผลคือผู้ป่วยใหม่ถูกผูกกับ *ผู้ป่วย* อีกคน ได้ 201 กับรหัสจับคู่ปกติ แล้วไม่มีใครให้แจ้งเตือนตอนเกิดเรื่อง |

**แสดง `pairing_code` ให้ผู้ดูแลเห็นตามที่ส่งมา** (มีขีดคั่นเพื่อให้อ่านออกเสียงง่าย) รหัสอายุ
**24 ชั่วโมง** และ**ใช้ได้ครั้งเดียว**

> **"สถานที่ปลอดภัย" ที่หน้าจอนี้เก็บ ส่งด้วย `PUT /api/patients/{id}/places/home` — ดูหัวข้อ 10**
> `POST /api/patients` ไม่รับพิกัด และ**ปักแค่บ้านจุดเดียวไม่พอ** หัวข้อ 10 มีตัวเลขที่วัดมาแล้ว

## ขั้นที่ 2 — เครื่องผู้ป่วยกรอกรหัส

```json
POST /api/pair
{ "code": "7K2M-P9QX" }
```

**เป็น endpoint เดียวในระบบที่ไม่ต้องมี token** เพราะมันคือทางที่เครื่องผู้ป่วยจะ*ได้*
token มา ตอบ `200`:

```json
{
  "patient_id": 42,
  "firebase_custom_token": "eyJhbGciOi...",
  "severity_level": 2
}
```

`severity_level` **เพิ่มเมื่อ 2026-08-27** เพื่อให้เครื่องผู้ป่วยวาดหน้าจอที่ถูกต้องได้ตั้งแต่
ครั้งแรก โดยไม่ต้องยิงเพิ่มอีกรอบ ค่าเป็น `null` ได้ถ้าผู้ดูแลไม่ได้ระบุตอนสร้าง —
**อย่า default เป็น 1** ให้ถามผู้ดูแลแทน

## ขั้นที่ 3 — แอปเอา custom token ไป sign in

```dart
await FirebaseAuth.instance.signInWithCustomToken(res.firebaseCustomToken);
// จากนั้นใช้ ID token ปกติในทุก request — ดูหัวข้อ 7
```

Firebase จะสร้างบัญชีให้ตาม uid ที่ backend กำหนดไว้ล่วงหน้า เครื่องผู้ป่วย
**ไม่ต้องสมัคร ไม่ต้องจำอีเมล ไม่ต้องตั้งรหัสผ่าน** และกรอกรหัสแค่ครั้งเดียวตลอดไป

## ขั้นที่ 4 — อ่านกลับมาว่าผู้ป่วยรายนี้คือใคร ระดับไหน

```
GET /api/patients/{patient_id}
```

ตอบ `200`:

```json
{ "patient_id": 42, "name": "ยาย", "severity_level": 2 }
```

**เพิ่มเมื่อ 2026-08-27** ขั้นที่ 2 ตอบ `severity_level` มาแล้วก็จริง แต่ตอบได้ครั้งเดียว —
รหัสจับคู่ใช้ได้ครั้งเดียวและแอปเรียก `/api/pair` ครั้งเดียวตลอดชีวิตเครื่อง เปิดแอปรอบหน้า
ใช้ token ที่ cache ไว้ **ลงแอปใหม่ หรือผู้ดูแลแก้ระดับทีหลัง จึงต้องมีทางอ่านซ้ำ** นี่คือทางนั้น

เรียกได้ทั้งเครื่องผู้ป่วย (อ่านของตัวเอง) และเครื่องผู้ดูแล (อ่านของผู้ป่วยที่ตัวเองดูแล) —
คุ้มด้วยระบบสิทธิ์เดียวกับ `/track` และ `/alerts` ดูหัวข้อ 7

| รหัส | แปลว่า |
|---|---|
| `200` | ปกติ |
| `403` | ไม่ใช่ผู้ป่วยของคุณ (เปิด auth แล้วเท่านั้น) |
| `404` | ไม่มี `patient_id` นี้ในตาราง `users` |

**ฝั่งผู้ดูแลใช้ตัวนี้ได้ด้วย** — ก่อนหน้านี้ไม่มี endpoint ไหนคืนชื่อหรือระดับของผู้ป่วยกลับมาเลย

## ข้อควรรู้

- รหัสรับได้ทั้งพิมพ์เล็ก มีขีด มีเว้นวรรค หรือมีช่องว่างท้าย — backend normalise ให้เอง
- ตัวอักษรในรหัสเลี่ยง `0 O 1 I L U` เพราะคนอ่านผิดบ่อย
- **รหัสผิด / หมดอายุ / ใช้ไปแล้ว ตอบ `404` เหมือนกันหมด** เจตนา — ถ้าตอบต่างกันเท่ากับ
  ยืนยันให้คนที่กำลังเดาว่ารหัสนี้มีอยู่จริง
- ถ้า sign in ไม่สำเร็จ **ให้ผู้ดูแลกดสร้างรหัสใหม่** อย่าให้ผู้ป่วยลองซ้ำ
- `POST /api/register` ยังอยู่ **สำหรับผู้ดูแล** ที่ sign in Firebase เองตามปกติ
- **ใหม่ 30 ส.ค.: `POST /api/register` รับ `phone` ได้แล้ว** (ไม่บังคับ) — เบอร์ของ *ผู้ดูแล* ที่ปุ่มโทรบนหน้า SOS contact ของผู้ป่วยจะกด อ่านกลับได้จาก `GET /api/patients/{id}/caregivers` (หัวข้อ 12.3) ไม่กรอกก็ได้ แต่แถวนั้นจะได้ `phone: null` และแอปควรซ่อนปุ่มโทร

ผู้ป่วยที่ไม่มี `caregiver_id` จะไม่มีวันได้รับ push — แต่เส้นทางนี้ตั้ง `caregiver_id` ให้เสมอ

# 3. หน้าตาของ push ที่จะได้รับ

### `notification`

| ฟิลด์ | ค่า |
|---|---|
| `title` | `PathGuard — เข้าเขตอันตราย` / `— ต้องการความช่วยเหลือ` / `— สัญญาณ GPS หาย` / `— พบการเดินหลง` |
| `body` | ข้อความจาก backend เช่น `Patient entered a danger zone — risk 91%.` |

### `data` — **ทุกค่าเป็น string** (ข้อบังคับของ FCM ต้อง parse เอง)

```json
{
  "alert_id": "42",
  "patient_id": "7",
  "alert_type": "geofence",
  "severity": "critical",
  "latitude": "13.77",
  "longitude": "100.555"
}
```

| ฟิลด์ | ใช้ทำอะไร |
|---|---|
| `patient_id` | เอาไปเปิดหน้าแผนที่ของผู้ป่วยคนนั้น |
| `latitude` / `longitude` | จุดที่เกิดเหตุ — **อาจเป็นสตริงว่าง `""`** ถ้า alert นั้นไม่มีพิกัด ต้องเช็คก่อน parse |
| `alert_type` | `geofence` (เข้าเขตอันตราย) · `emergency` (คะแนนสูง/เสี่ยงต่อเนื่อง) · `gps_loss` (สัญญาณหาย) · `sos` (ผู้ป่วยกดปุ่มเอง) · `trip_denied` (คำขอเดินทางถูกปฏิเสธ) · `wandering` |
| `severity` | `low` · `medium` · `high` · `critical` |

`android.priority = "high"` ตั้งไว้แล้วฝั่ง backend เพื่อให้ทะลุ Doze ของ Android

# 4. จะได้ push ถี่แค่ไหน

**อย่างมาก 1 ครั้งต่อ 10 นาที ต่อ `alert_type` ต่อผู้ป่วย 1 คน**

ตาราง `alerts` ยังเขียนทุกรอบที่เข้าเงื่อนไข (รอบละ 60 วิ ตอน GPS เข้า) เพราะมันคือประวัติ
ที่หน้า timeline ต้องใช้ แต่การ *ส่ง* ถูกจำกัดแยกต่างหาก — ยายที่นั่งอยู่ในเขตอันตราย 1 ชั่วโมง
ได้ alert 60 แถว แต่ได้ push 6 ครั้ง ไม่ใช่ 60

`alert_type` ต่างชนิดไม่กด cooldown ของกันและกัน — GPS หายตอนที่เพิ่งส่ง geofence ไป
30 วินาทีก่อน ยังส่งได้ตามปกติ

ค่า 10 นาทีนี้อยู่ในตาราง `risk_thresholds` ชื่อ `push_cooldown_seconds` แก้ได้ตอนรันโดยไม่ต้อง deploy
(อ้างอิง MOPH ED Triage 2561 Level 1-2 = แทรกแซงใน 0–10 นาที)

**ยกเว้น `sos` ซึ่งใช้ค่าของตัวเอง = 60 วินาที** (`sos_cooldown_seconds`) เพราะการกดปุ่มซ้ำ
คือคนกดอีกครั้ง ไม่ใช่เงื่อนไขเดิมที่ยังค้างอยู่ — ดูหัวข้อ 8

# 5. เกณฑ์ที่ทำให้เกิด alert (ไม่ได้เปลี่ยน)

ทั้งหมดมาจาก MOPH ED Triage 2561 ที่เก็บใน rule KB — backend ไม่ได้ตั้งเกณฑ์ใหม่เพื่อ push

| เกิด alert เมื่อ | ผลลัพธ์ |
|---|---|
| อยู่ในเขตอันตราย | `geofence` · `critical` · ทันที |
| คะแนน > 80 | `emergency` · `high` · ทันที |
| คะแนน ≥ 50 ติดกัน 5 รอบ | `emergency` · `high` · reason `sustained_risk` |
| ไม่มี GPS เกิน 10 นาที | `gps_loss` · `high` |
| **ผู้ป่วยกดปุ่ม SOS** | `sos` · `critical` · ทันที **ไม่ผ่านการให้คะแนนเลย** (หัวข้อ 8) |

> ⚠️ **สิ่งที่ต้องรู้:** เดินหลงห่างบ้าน 2 กม. วัดได้ **63.5 = medium ไม่ถึง 80** เคสเดินหลงจริง
> จึงมาทางกฎ "5 รอบติด" เสมอ = ~5 นาทีหลังเริ่มหลง ไม่ใช่ทันที

# 6. หลังกด push แล้วดึงอะไรต่อ

push พาไปหน้าแผนที่ได้ แต่ payload มีแค่จุดที่เกิดเหตุจุดเดียว หน้าจอต้องการเส้นทาง
และประวัติ — สองอันนี้คือที่มา

> ทั้งคู่ย้ายมาจาก `/demo/track` และ `/demo/alerts` ใน `demo_server.py` ที่ dashboard
> ใช้อยู่แล้ว **ไม่ใช่ของปลอมและไม่ได้เขียนใหม่** — dashboard ตอนนี้เรียก endpoint
> เดียวกับที่มือถือเรียก

## `GET /api/patients/{patient_id}/track?hours=6`

| พารามิเตอร์ | ค่า |
|---|---|
| `hours` | 1–720 · default 6 |

```json
{
  "patient_id": 7,
  "count": 240,
  "points": [
    {
      "latitude": 13.7563,
      "longitude": 100.5018,
      "recorded_at": "2026-08-22T09:14:03.120000+00:00",
      "speed": 1.1,
      "synthetic_injected": false
    }
  ]
}
```

- **เรียงเก่า → ใหม่** วาด polyline ได้เลยไม่ต้อง sort
- ชื่อฟิลด์ตรงกับ `POST /api/gps` ที่แอปส่งอยู่แล้ว ใช้ model ตัวเดียวกันได้
- `speed` เป็น `null` ได้ (มือถือไม่ได้ส่งมา)
- `synthetic_injected: true` = จุดที่สคริปต์เดโมใส่เข้าไป ข้อมูลผู้ป่วยจริงเป็น `false` เสมอ
- **ถ้าในช่วง `hours` มีไม่ถึง 2 จุด จะคืน 300 จุดล่าสุดแทน** ตั้งใจให้เป็นแบบนี้ —
  มือถือที่ปิดมาตั้งแต่เช้าไม่ควรทำให้แผนที่ว่างเปล่า เพราะจอว่างอ่านว่า "ยายไม่ได้ไปไหน"
  ทั้งที่ความจริงคือ "ไม่มีข้อมูลช่วงนี้" — ให้ดูที่ `recorded_at` ของจุดสุดท้ายเสมอ

## `GET /api/patients/{patient_id}/alerts?limit=20`

| พารามิเตอร์ | ค่า |
|---|---|
| `limit` | 1–200 · default 20 |

```json
{
  "patient_id": 7,
  "count": 2,
  "alerts": [
    {
      "id": 101,
      "patient_id": 7,
      "alert_type": "geofence",
      "severity": "critical",
      "message": "Patient entered a danger zone — risk 86.8%.",
      "latitude": 13.77,
      "longitude": 100.555,
      "resolved": false,
      "created_at": "2026-08-22T04:01:30.247575+00:00"
    }
  ]
}
```

**ใหม่สุดขึ้นก่อน** และ **จำนวนแถวจะเยอะกว่าจำนวน push มาก** — ตารางนี้เขียนทุกรอบที่
เข้าเงื่อนไข (ดูหัวข้อ 4) ยายอยู่ในเขตอันตราย 1 ชั่วโมงจะได้ 60 แถว แต่ push 6 ครั้ง
ถ้าจะทำ timeline ให้อ่านง่าย แนะนำให้ยุบแถวที่ `alert_type` เดียวกันติดกันเป็นก้อนเดียว
ฝั่งแอป

## `PATCH /api/alerts/{alert_id}`

```json
{ "resolved": true }
```

คืน alert ที่อัปเดตแล้ว (หน้าตาเหมือนใน list) · `404` ถ้าไม่มี alert นั้น

**ย้อนกลับได้** ส่ง `{"resolved": false}` เพื่อยกเลิก — ตั้งใจให้กดผิดแล้วแก้ได้
`resolved_at` ถูกเซ็ต/ล้างให้อัตโนมัติ ไม่ต้องส่งมา

> ก่อนหน้านี้คอลัมน์ `resolved` มีมาตั้งแต่สร้างตารางแต่ไม่มีใครเขียนเลย — แปลว่า
> "เจอยายแล้ว" ไม่มีที่อยู่ในระบบ นี่คือที่ของมัน

## `404` ทั้งสอง endpoint ถ้า `patient_id` ไม่มีในตาราง `users`

ตั้งใจให้ 404 ไม่ใช่คืน list ว่าง เพราะ list ว่างอ่านว่า "ยังไม่มีอะไรเกิดขึ้น"
ทั้งที่ความจริงคือ "ส่ง id ผิด"

# 7. Auth — เตรียมโค้ดไว้ แต่ยังไม่เปิด

**ตอนนี้ทุก endpoint ยังเปิดโล่ง ไม่ต้องส่ง token ก็เรียกได้** แต่โค้ดฝั่ง backend
เขียนและเทสต์ครบแล้ว เปิดได้ด้วย env ตัวเดียว (`AUTH_ENABLED=true`)

**เขียนแอปให้ส่ง token มาตั้งแต่ตอนนี้เลย** ตอนนี้ backend จะไม่สนใจมัน แต่วันที่เปิดสวิตช์
แอปจะไม่ต้องแก้อะไรเลย ถ้าไม่ทำ วันนั้นทุก request จะ 401 พร้อมกันหมด

> **เครื่องผู้ป่วยเอา ID token มาจากไหน** — จาก `signInWithCustomToken()` ในหัวข้อ 2
> ไม่ใช่จากการ sign in ด้วยอีเมล หลังจากนั้นมันคือ ID token ธรรมดาเหมือนของผู้ดูแลทุกประการ

## ต้องส่งอะไร

```
Authorization: Bearer <Firebase ID token>
```

เอามาจาก `FirebaseAuth.instance.currentUser?.getIdToken()` — **คนละตัวกับ FCM token**
ในหัวข้อ 1 · token หมดอายุทุก 1 ชั่วโมง Firebase SDK ต่ออายุให้เอง แต่ต้องเรียก
`getIdToken()` ใหม่ทุกครั้งที่ยิง อย่า cache ไว้เอง

ส่งทุก endpoint ยกเว้นไม่มี — รวมถึง `/api/register` ด้วย

## กฎที่ backend จะบังคับ

| กรณี | รหัส |
|---|---|
| ไม่ส่ง token / token ปลอม / หมดอายุ | `401` + header `WWW-Authenticate: Bearer` |
| token ใช้ได้ แต่ยังไม่เคย `POST /api/register` | `403` `signed in but not registered` |
| ขอข้อมูลคนไข้ที่ไม่ใช่ของตัวเอง | `403` `not your patient` |
| `POST /api/gps` ในนามคนไข้อื่น | `403` |
| `POST /api/devices/token` ด้วย `user_id` ของคนอื่น | `403` |
| `POST /api/register` ด้วย `firebase_uid` ไม่ตรงกับ token | `403` |

**ใครดูข้อมูลคนไข้ได้บ้าง:** ตัวคนไข้เอง กับผู้ดูแล**ทุกคน**ที่ผูกกับคนไข้คนนั้น (ตาราง `patient_caregivers` ตั้งแต่ 2026-08-28 เดิมเป็น `users.caregiver_id` ผูกได้คนเดียว)
ของคนไข้คนนั้นเท่านั้น ผู้ดูแลคนอื่นได้ `403` (ไม่ใช่ `404` — ตั้งใจ ไม่โกหกว่าไม่มีคนไข้คนนี้)

## ที่แอปควรทำ

- เจอ `401` → ขอ token ใหม่แล้วลองอีกครั้ง 1 รอบ ถ้ายัง 401 → พาไปหน้า sign-in
- เจอ `403 signed in but not registered` → เรียก `/api/register` แล้วลองใหม่
- เจอ `403 not your patient` → นี่คือบั๊กฝั่งแอป (ส่ง `patient_id` ผิด) อย่า retry

# 8. ปุ่ม SOS — `POST /api/sos`

**เพิ่ม 2026-08-26** หลังคนที่ 1 ถามว่าปุ่มใน `navigation_screen.dart` ควรยิงไปไหน
คำตอบคือ endpoint ของตัวเอง **ไม่ใช่ `POST /api/gps` + flag**

## ทำไมไม่ใช้ GPS + flag

| ปัญหา | รายละเอียด |
|---|---|
| จะโดน throttle กลืน | `POST /api/gps` คำนวณ risk แค่ **1 ครั้ง/60 วินาที/คนไข้** กดตอนวินาทีที่ 20 หลังรอบล่าสุด = ไม่มีการคำนวณ = ไม่มี alert = ปุ่มเงียบ |
| เครื่องกฎจะตัดสินแทนคน | alert เกิดเมื่อ `decide_emergency` บอกว่าเข้าเกณฑ์ กดปุ่มขณะยืนอยู่ในบ้าน คะแนน ≈ 16.5 = `low` = **ไม่ยิงอะไรเลย** ปุ่มจะตายเงียบตรงที่ที่คนไข้อยู่บ่อยที่สุด |
| `batch` เรียงตาม `recorded_at` | SOS ที่ค้างในคิว offline จะถูกเล่นย้อนหลังเหมือนเพิ่งเกิด |

endpoint นี้จึง **ข้ามการให้คะแนนทั้งหมด** — เขียน alert แล้ว push แล้วตอบ
คนไข้คือผู้มีอำนาจตัดสินว่าคนไข้ต้องการความช่วยเหลือหรือไม่ ไม่ต้องให้ AI เห็นชอบ

## Request

```json
POST /api/sos
Content-Type: application/json
Authorization: Bearer <Firebase ID token>

{
  "patient_id": 1,
  "latitude": 13.7563,
  "longitude": 100.5018
}
```

| ฟิลด์ | ชนิด | บังคับ | หมายเหตุ |
|---|---|---|---|
| `patient_id` | int | ✅ | `users.id` ของ **ผู้ป่วย** (จาก `/api/register`) ไม่ใช่ Firebase UID |
| `latitude` | float \| null | — | ตำแหน่งตอนกด ถ้าส่งมาจะใช้ค่านี้ก่อน |
| `longitude` | float \| null | — | เหมือนกัน |

**ส่งพิกัดมาด้วยถ้ามี** ถ้าไม่ส่ง (หรือส่ง `null`) backend จะใช้จุด GPS ล่าสุดที่มีในฐานข้อมูล
ถ้าไม่มีเลยก็ยังยิง alert อยู่ดี แค่ไม่มีพิกัด — **ห้ามรอ GPS fix ก่อนยิง SOS**
เพราะที่ที่ GPS จับไม่ได้ (ในอาคาร ใต้ดิน ชิปเย็น) คือที่ที่คนไข้หลงง่ายที่สุดพอดี

## Response `201`

```json
{
  "alert_id": 42,
  "patient_id": 1,
  "severity": "critical",
  "severity_level": 1,
  "latitude": 13.7563,
  "longitude": 100.5018,
  "push": "sent"
}
```

## 🛑 `severity` กับ `severity_level` เป็นคนละเรื่องกันสิ้นเชิง

| ฟิลด์ | คือ | ค่า |
|---|---|---|
| `severity` | **ความรุนแรงของ alert** | เป็น `"critical"` เสมอสำหรับ SOS |
| `severity_level` | **ระยะของโรคอัลไซเมอร์** (เพิ่ม 29 ส.ค.) | `1` · `2` · `null` = ผู้ดูแลไม่ได้ระบุ |

ชื่อคล้ายกันแต่**อ่านผิดตัวแล้วผลลัพธ์ตรงข้ามกัน** — ดูหัวข้อถัดไปว่าทำไมมันสำคัญตรงนี้

## ⭐ กด SOS แล้วแอปต้องแยกทางตาม `severity_level` — ตามรายงานหัวข้อ 1.6

รายงานเขียนไว้ชัดว่า **ปุ่ม SOS คือจุดที่ระบบแยกเส้นทางตามระยะของโรค**

| `severity_level` | ไปที่ | รายงานข้อ |
|---|---|---|
| **`1` (ระยะต้น)** | **Safe Zone Navigation** — นำทางไปพื้นที่ปลอดภัยใกล้สุด (สถานีตำรวจ/โรงพยาบาล) | 1.5 |
| **`2` (ระยะกลาง)** | **Zero-UI Mode** — สลับเหลือข้อความเดียว **"ยืนรอตรงนี้ ผู้ดูแลกำลังมารับ"** ไม่ต้องกดอะไรอีก | 1.4 |
| **`null`** | **ปฏิบัติเหมือน `2`** ไม่ใช่เหมือน `1` | — |

`null` ต้องไปทาง "ยืนรอ" เพราะสองทางนี้ความเสี่ยงไม่เท่ากัน: **บอกให้ยืนรอทั้งที่เดินได้
แค่ช้าลง แต่บอกให้เดินทั้งที่ไม่ควรเดิน คือส่งคนสับสนออกไปข้ามถนน** เมื่อไม่รู้ ให้เลือกทางที่พลาดแล้วเสียหายน้อยกว่า

**ทั้งสองทางนี้ backend ไม่ต้องทำอะไรเพิ่มเลย** — `POST /api/sos` แจ้งผู้ดูแลให้มารับ
เรียบร้อยแล้วในทั้งสองกรณี (รายงาน 1.5 เขียนว่า "พร้อมแจ้งผู้ดูแลให้ไปรับ" ซึ่งคือ push ตัวนี้)
ที่เหลือเป็นหน้าจอฝั่งแอปล้วน ๆ ส่วนการหาสถานที่ปลอดภัยดู **§13**

`push` บอกว่าเกิดอะไรขึ้นกับการส่งจริง ใช้ตัดสินใจว่าจะแสดงอะไรบนหน้าจอได้

| `push` | แปลว่า | แอปควรทำ |
|---|---|---|
| `sent` | ผู้ดูแลได้รับแล้ว | ✅ ขึ้น "แจ้งผู้ดูแลแล้ว" |
| `cooldown` | กดซ้ำภายใน 60 วิ ไม่ได้ส่งซ้ำ | ✅ ยังถือว่าสำเร็จ — ผู้ดูแลได้รับไปแล้วเมื่อครู่ |
| `no_caregiver` | ผู้ดูแลยังไม่ได้ลงทะเบียนเครื่อง | ⚠️ **ต้องบอกผู้ใช้ตรงๆ** ว่าส่งไม่ถึง |
| `failed` / `error` | FCM ล่ม | ⚠️ เหมือนกัน |

> **สำคัญ: `201` ไม่ได้แปลว่าผู้ดูแลได้รับ** มันแปลว่า alert ถูกบันทึกแล้ว
> ต้องดู `push` ถึงจะรู้ว่าถึงมือหรือยัง อย่าขึ้นข้อความว่า "ส่งแล้ว" จากรหัส 201 อย่างเดียว
> เพราะถ้าผู้ดูแลยังไม่ลงทะเบียนเครื่อง คนไข้จะเชื่อว่ามีคนกำลังมาช่วย ทั้งที่ไม่มี

## ความถี่

**อย่างมาก 1 push ต่อ 60 วินาที ต่อผู้ป่วย** (`sos_cooldown_seconds` ใน `risk_thresholds`)
ไม่ใช่ 10 นาทีเหมือน alert อัตโนมัติ เพราะการกดซ้ำคือคนกดอีกครั้ง = ข้อมูลใหม่
แต่ก็ไม่ใช่ 0 เพราะพฤติกรรมกดซ้ำเป็นอาการ BPSD อย่างหนึ่ง — คนที่จะกด 30 ครั้งคือคนที่
ระบบนี้ทำมาเพื่อเขาพอดี และ 30 push = ผู้ดูแลปิดแจ้งเตือน

**ทุกครั้งที่กดเขียนแถวใน `alerts` เสมอ** ไม่ว่าจะ push หรือไม่ ดังนั้น
`GET /api/patients/{id}/alerts` (หัวข้อ 6) จะเห็นการกดครบทุกครั้ง

## Push ที่ผู้ดูแลจะเห็น

| | |
|---|---|
| `title` | `PathGuard — ผู้ป่วยกดขอความช่วยเหลือ` |
| `body` | `Patient pressed the SOS button.` |
| `data.alert_type` | `sos` |
| `data.severity` | `critical` |

`alert_type` เป็น `sos` ไม่ใช่ `emergency` **โดยตั้งใจ** — cooldown คีย์ด้วย
(`patient_id`, `alert_type`) ถ้าใช้ชื่อเดียวกัน alert อัตโนมัติที่เพิ่งส่งไปเมื่อ 3 นาทีก่อน
จะกลืนการกดปุ่มของคนไข้เงียบๆ ฝั่งแอปควรแยกหน้าตาของ `sos` ออกจาก alert อัตโนมัติด้วย
เพราะผู้ดูแลตัดสินใจต่างกันระหว่าง "แอปคิดว่ามีอะไรผิดปกติ" กับ "เขาขอความช่วยเหลือเอง"

## Error

| รหัส | เมื่อไหร่ |
|---|---|
| `404` | `patient_id` ไม่มีในตาราง `users` → ต้อง `POST /api/register` ก่อน |
| `403` | (ตอนเปิด auth) ยิง SOS ในนามคนไข้ที่ไม่ใช่ของตัวเอง |
| `422` | `latitude`/`longitude` นอกช่วง |

# 9. ขออนุมัติเดินทาง (Trip Approval — C-3)

> **สร้าง 2026-08-26** ตามรายงานหัวข้อ C-3 ใช้เฉพาะ **ผู้ป่วย Level 2** เท่านั้น
> Level 1 เดินทางเองได้ ไม่ต้องขอ

## ขั้นที่ 1 — เครื่องผู้ป่วยส่งคำขอ

```json
POST /api/trip-requests
{
  "patient_id": 42,
  "destination_name": "ตลาดใหม่",
  "latitude": 13.7585,
  "longitude": 100.5018
}
```

ตอบ `201`:

```json
{
  "id": 7,
  "patient_id": 42,
  "destination_name": "ตลาดใหม่",
  "latitude": 13.7585,
  "longitude": 100.5018,
  "status": "pending",
  "confidence": 0.8,
  "factors": { "familiarity": 0.8, "danger_zone": false },
  "nearest_place_name": "บ้าน",
  "nearest_place_distance_m": 100.0,
  "blocking_zone_name": null,
  "confidence_status": "ok",
  "created_at": "2026-08-26T09:15:00Z",
  "decided_at": null
}
```

**ถ้าผู้ป่วยเป็น Level 1** จะได้ `201` เหมือนกัน แต่ `status: "not_required"` และ
`id: null` — **ไม่มีการบันทึกแถว ให้แอปพาไปได้เลย** ไม่ต้องรอใคร ตั้งใจให้ไม่ใช่ error
เพราะแอปไม่ควรต้องรู้กฎนี้เอง

## ขั้นที่ 2 — ผู้ดูแลดูคำขอ

```
GET /api/patients/{patient_id}/trip-requests?status=pending&limit=20
```

เรียงใหม่สุดก่อน `status` กรองได้ด้วย `pending` / `approved` / `rejected`

## ขั้นที่ 3 — ผู้ดูแลตัดสิน

```json
PATCH /api/trip-requests/7
{ "decision": "approve" }      // หรือ "reject"
```

ตอบ `200`:

```json
{ "id": 7, "patient_id": 42, "status": "rejected",
  "decided_at": "2026-08-26T09:20:00Z",
  "alert_id": 91, "push": "skipped_self" }
```

## Confidence Score หมายความว่าอะไร

**ไม่ใช่ "โอกาสที่จะหลง"** แต่คือ **"ปลายทางนี้ใกล้ที่ที่ผู้ป่วยรู้จักแค่ไหน"** (0–1)

| ค่า | แปลว่า |
|---|---|
| `1.0` | ปลายทางอยู่ในรัศมีของหมุดที่ไปบ่อยที่สุด |
| `0.5–0.9` | อยู่ใกล้ที่ที่รู้จัก |
| `0.0` | ไกลเกิน `route_deviation_ceiling_m` (500 ม.) จากที่ที่รู้จักทุกแห่ง **หรือ** อยู่ในเขตอันตราย |

**`danger_zone: true` คือการวีโต้ ไม่ใช่การหักคะแนน** — ปลายทางในเขตอันตรายได้ `0.0`
เสมอ ต่อให้เป็นบ้านตัวเอง ให้แอปแสดง `blocking_zone_name` ให้ผู้ดูแลเห็นชัดๆ

**`confidence_status: "no_profile"`** = ผู้ป่วยยังไม่มีหมุดสักที่ จึงเทียบกับอะไรไม่ได้
**อย่าแสดงเป็น 0%** เพราะมันคนละความหมายกับ "มั่นใจว่าไม่ควรไป"

## เรื่องที่ต่างจากรายงาน — ตั้งใจ

รายงานเขียนว่าเมื่อปฏิเสธ *"ระบบจะส่ง SOS ให้ผู้ดูแลทุกคนอัตโนมัติ"* ทำจริงต่างสองจุด:

1. **`alert_type` เป็น `trip_denied` ไม่ใช่ `sos`** — cooldown ของ push คีย์ด้วย
   (`patient_id`, `alert_type`) ถ้าใช้ชื่อเดียวกัน คำขอที่ถูกปฏิเสธจะกลืนการกดปุ่ม SOS จริง
   ของผู้ป่วยไป 10 นาที และผู้ดูแลก็ตัดสินใจต่างกันระหว่างสองเรื่องนี้
2. **"ผู้ดูแลทุกคน" ตอนนี้คือคนเดียว** และเป็นคนที่เพิ่งกดปฏิเสธเอง จึง**ข้าม push**
   (`push: "skipped_self"`) แต่**ยังเขียนแถว alert เสมอ** เพื่อให้ timeline และ dashboard
   เห็น พอรองรับผู้ดูแลหลายคนเมื่อไหร่ มันจะเริ่ม push ให้คนอื่นเองโดยไม่ต้องแก้โค้ด

## Error

| รหัส | เมื่อไหร่ |
|---|---|
| `404` | `patient_id` หรือ `request_id` ไม่มีจริง |
| `409` | ตัดสินคำขอที่ตัดสินไปแล้ว — ไม่ทับของเดิม เพราะครอบครัวอาจลงมือตามคำตอบแรกไปแล้ว |
| `422` | `decision` ไม่ใช่ `approve`/`reject` หรือพิกัดนอกช่วง |

## ขั้นที่ 1 — หน้าจอเพิ่มผู้ป่วย: ส่งบ้านจุดเดียว

```json
PUT /api/patients/42/places/home
{ "place_name": "บ้าน", "latitude": 13.7563, "longitude": 100.5018 }
```

| ฟิลด์ | จำเป็น | หมายเหตุ |
|---|---|---|
| `place_name` | ✅ | 1–255 ตัวอักษร ผู้ดูแลตั้งเอง — **ชื่อต้องมาจากคน** ระบบตั้งชื่อสถานที่เองไม่ได้ |
| `latitude` / `longitude` | ✅ | −90..90 / −180..180 |
| `radius_m` | ⬜ | 20–5000 · ค่าเริ่มต้น **150** (ขนาดบ้านหลังหนึ่ง) ถ้าเป็นวัด/ตลาด/โรงพยาบาลต้องใส่ให้ใหญ่กว่านี้ ไม่งั้นแค่เดินข้ามลานก็นับว่าออกนอกที่คุ้นเคย |

**ไม่ต้องส่ง `visit_rank` / `stay_rank`** — บ้านคือ `daily_live` + `all_day` โดยนิยาม
backend ใส่ให้เอง (บ้านที่ถูกปักเป็น `rare` จะทำให้ระบบอ่านว่าผู้ป่วยเป็นคนแปลกหน้าในบ้านตัวเอง)

ตอบ `200` = ชุดหมุดทั้งหมดหลังแก้:

```json
{
  "patient_id": 42,
  "count": 3,
  "places": [
    { "cluster_id": 0, "place_name": "บ้าน", "latitude": 13.7563, "longitude": 100.5018,
      "visit_rank": "daily_live", "stay_rank": "all_day", "radius_m": 150,
      "source": "manual", "is_home": true },
    { "cluster_id": 1, "place_name": "ตลาด", "...": "..." , "is_home": false },
    { "cluster_id": 2, "place_name": "unnamed", "latitude": 13.8, "longitude": 100.6,
      "visit_rank": null, "stay_rank": null, "radius_m": null,
      "source": "learned", "is_home": false }
  ]
}
```

**`PUT` นี้ลบหมุดอื่นไม่ได้เลย** — เรียกซ้ำกี่ครั้งก็ทับเฉพาะบ้าน เรียกได้ทุกครั้งที่ผู้ดูแลแก้ที่อยู่

* `source: "learned"` = สถานที่ที่ Module 1 เดาเอง **ไม่มีชื่อ** (`"unnamed"`) และ `visit_rank`/`stay_rank`/`radius_m` เป็น `null`
  → แสดงแบบอ่านอย่างเดียว หรือไม่แสดงเลยก็ได้
* `is_home` มีได้ `true` แค่หมุดเดียวต่อผู้ป่วยหนึ่งคนเสมอ

## ขั้นที่ 2 — หน้าจอ "จัดการสถานที่": ส่งทั้งชุด

```json
POST /api/patients/42/places
{
  "places": [
    { "place_name": "บ้าน",  "latitude": 13.7563, "longitude": 100.5018,
      "visit_rank": "daily_live", "stay_rank": "all_day", "is_home": true },
    { "place_name": "วัด",   "latitude": 13.7601, "longitude": 100.5062,
      "visit_rank": "most_days", "stay_rank": "about_hour", "radius_m": 400 },
    { "place_name": "ตลาด",  "latitude": 13.7588, "longitude": 100.5099,
      "visit_rank": "most_days", "stay_rank": "brief",      "radius_m": 250 }
  ]
}
```

### 🛑 ส่ง `is_home: true` มาให้หมุดบ้านเสมอ

**เพิ่ม 26 ส.ค.** เดิม backend เดาเอาว่า `places[0]` คือบ้าน ซึ่งพังทันทีถ้า UI เรียงหมุด
ใหม่ (เรียงชื่อ เรียงระยะ หรือให้ผู้ดูแลลากสลับ) เพราะบ้านจะย้ายไปอยู่หมุดอื่นเงียบ ๆ แล้ว
`PUT .../places/home` ครั้งถัดไปจะไป**ลบสถานที่จริงทิ้ง** วัดจากของจริงแล้ว: ส่ง
`[วัด, บ้าน]` ครั้งเดียว แล้วอัปเดตบ้าน → วัดหายไปเลย

* ส่งได้ **มากสุดหมุดเดียว** ที่ `is_home: true` เกินกว่านั้น **422**
* ไม่ส่งเลยก็ได้ — backend จะถอยไปใช้ `places[0]` เหมือนเดิม (ของเก่ายังใช้ได้)
  แต่**อย่าพึ่งพฤติกรรมนี้** ถ้าหน้าจอมีการเรียงลำดับ

ตอบ `201` รูปแบบเดียวกับข้างบน

### 🛑 endpoint นี้ **ทับหมุดเดิมทั้งชุด**

ส่ง 1 หมุด = เหลือ 1 หมุด อีก 3 หายเงียบ ๆ พร้อม `201` ไม่มี error
**ต้อง `GET` มาก่อน แก้ในมือ แล้วส่งกลับทั้งชุดเสมอ** ถ้าจะแก้แค่บ้าน ให้ใช้ `PUT .../places/home` ข้างบนแทน

* **หมุดที่ส่ง `is_home: true` คือบ้าน** — ถ้าไม่ส่งเลย backend ถอยไปใช้ `places[0]` ดูกล่องข้างบน
* **ส่ง `places: []` ไม่ได้ (422)** ตั้งใจ: 0 หมุด = ระบบตกกลับ partial mode ซึ่งวัดแล้วว่า
  ผู้ป่วยนั่งอยู่บ้านกับหลงห่างบ้าน 2.5 กม. ได้ 18.8 low เท่ากันทั้งคู่ แยกไม่ออก
  ถ้าจะแก้หมุดผิด ให้ส่งชุดที่ถูกทับไปเลย
* สูงสุด **50 หมุด**
* **การเขียนหมุด (ทั้ง `POST` และ `PUT`) จะล้างกิจวัตรที่ระบบเรียนไว้ทิ้ง** —
  `routine_patterns` อ้างสถานที่ด้วย `cluster_id` ซึ่งถูกแจกใหม่ตามตำแหน่งทุกครั้งที่เขียน
  ถ้าไม่ล้าง กิจวัตรที่เรียนว่า "9 โมงมักอยู่วัด" จะกลายเป็น "9 โมงมักอยู่บ้าน" โดยที่เนื้อหา
  ไม่ได้เปลี่ยน ฝั่งแอปไม่ต้องทำอะไร แค่รู้ว่า `time_match` ของหน้าแนะนำจะเงียบไป
  จนกว่าฝั่ง backend จะรัน `build_routine_patterns` ใหม่

### `visit_rank` — เลือกจาก dropdown เท่านั้น ห้ามให้ผู้ดูแลพิมพ์ตัวเลข

| ค่า | ข้อความที่ควรขึ้นบน UI |
|---|---|
| `daily_live` | อยู่/นอนที่นี่ |
| `most_days` | ไปเกือบทุกวัน |
| `weekly` | ไปสัปดาห์ละครั้ง |
| `rare` | นาน ๆ ไปที |

### `stay_rank`

| ค่า | ข้อความที่ควรขึ้นบน UI |
|---|---|
| `all_day` | อยู่ทั้งวัน |
| `few_hours` | หลายชั่วโมง |
| `about_hour` | ราวหนึ่งชั่วโมง |

ที่ API ไม่รับตัวเลขตรง ๆ เพราะ `familiarity` เป็นค่า**เปรียบเทียบ** (หารด้วยค่ามากสุดในชุด)

## 11.1 `GET /api/recommendation/{patient_id}` — สถานที่บนหน้าโฮมของผู้ป่วย

ตัวที่ฝั่งแอป mock อยู่ตอนนี้ (`recommendedPlaces`) ต่อของจริงได้แล้ว

```
GET /api/recommendation/42
GET /api/recommendation/42?lat=13.7563&lng=100.5018
```

ตอบ `200`:

```json
{
  "patient_id": 42,
  "status": "ok",
  "message": "Top 3 place(s) by likelihood. Scorer: rule-based fallback (no trained model).",
  "flags": { "time_match_available": true, "location_used": true },
  "recommendations": [
    {
      "rank": 1,
      "cluster_id": 0,
      "place_name": "บ้าน",
      "latitude": 13.7563,
      "longitude": 100.5018,
      "confidence": 0.9123,
      "confidence_pct": 91,
      "factors": { "frequency": 1.0, "proximity": 0.98, "familiarity": 1.0, "time_match": 0.8 }
    }
  ]
}
```

| ฟิลด์ | ใช้ยังไง |
|---|---|
| `place_name` | **ชื่อที่ผู้ดูแลตั้งไว้ตอนปักหมุด — เอาขึ้นปุ่มตัวนี้** เป็น `null` ได้ ดูกล่องข้างล่าง |
| `rank` | 1 = น่าจะไปที่สุด เรียงมาให้แล้ว ไม่ต้องเรียงเอง |
| `cluster_id` | id ของหมุด **เปลี่ยนได้ทุกครั้งที่ผู้ดูแลแก้ชุดหมุด** อย่าเก็บถาวร |
| `confidence_pct` | 0–100 ปัดมาให้แล้ว ถ้าจะแสดงให้ผู้ดูแลเห็นใช้ตัวนี้ |
| `factors` | รายละเอียดว่าคะแนนมาจากไหน สำหรับ debug ไม่ต้องขึ้นหน้าจอผู้ป่วย |

> **`place_name` เพิ่งมีเมื่อ 2026-08-27** ก่อนหน้านี้ endpoint นี้คืนแค่พิกัด ซึ่งแปลว่า
> หน้าโฮมของผู้ป่วยไม่มีอะไรจะแสดงเลย เจอตอนเขียนสัญญาหัวข้อนี้
>
> **`place_name` เป็น `null` ได้** เมื่อสถานที่นั้นมาจากการเรียนรู้ของ Module 1 ไม่ใช่หมุดที่คน
> ปัก — อัลกอริทึมตั้งชื่อสถานที่ไม่ได้ ในทางปฏิบัติทุกสถานที่มาจากหมุด แต่ **อย่า default เป็น
> "ไม่ทราบ"** ให้ซ่อนปุ่มนั้นไปเลยดีกว่า ผู้ป่วยแยกไม่ออกว่าปุ่มที่เขียนว่า "ไม่ทราบ" คืออะไร

**ได้ 3 ที่เสมอ ทุกระดับ ไม่ต้องส่งพารามิเตอร์** — Level 1, Level 2 และผู้ป่วยที่ไม่ได้ระบุ
ระดับ ได้ 3 เท่ากันหมด

> **แก้ 2026-08-28: เดิม Level 2 ได้ 5** ตามที่รายงานเขียนไว้ ฝั่งแอปออกแบบหน้าโฮม Level 2
> เสร็จแล้วและขอเป็น 3 — หน้าจอแสดง 3 ปุ่มพร้อมกันโดยไม่ต้องเลื่อน และเหตุผลคือผู้ป่วยระยะ
> กลางยิ่งต้องการตัวเลือก*น้อยลง* ไม่ใช่มากขึ้น backend ทำตามแล้ว **ถ้าหน้าจอเปลี่ยนกลับไป
> แสดงได้มากกว่า 3 บอกมา** ฝั่ง backend แก้ที่เดียวคือ `_TOP_N_BY_LEVEL`

**`?lat=&lng=` ไม่ส่งก็ได้** ไม่ส่ง = ใช้พิกัด GPS ล่าสุดที่บันทึกไว้ · ไม่มีทั้งคู่ =
ตัด `proximity` ออกจากการคิดคะแนน แล้วตั้ง `flags.location_used = false`

| `status` | แปลว่า | แอปต้องทำ |
|---|---|---|
| `ok` | ปกติ | แสดงลิสต์ |
| `no_profile` | ผู้ป่วยยังไม่มีหมุดสักที่ `recommendations` เป็น `[]` | **ต้องรองรับ** ผู้ป่วยที่เพิ่งสร้างเป็นแบบนี้ทุกคน — ขึ้นข้อความชวนผู้ดูแลไปปักหมุด อย่าขึ้นหน้าจอว่าง |

`flags.time_match_available` = ระบบรู้กิจวัตรรายชั่วโมงของผู้ป่วยคนนี้แล้วหรือยัง
เป็น `false` จนกว่าฝั่ง backend จะรัน `build_routine_patterns` และ**กลับเป็น `false` อีกครั้ง
ทุกครั้งที่ผู้ดูแลแก้หมุด** (เหตุผลอยู่ท้ายหัวข้อ 10) แอปไม่ต้องทำอะไรกับ flag นี้
มีไว้ให้เข้าใจว่าทำไมอันดับขยับ

## 11.2 `POST /api/gps/batch` — คิวตอนเน็ตหลุด

```json
POST /api/gps/batch
{
  "points": [
    { "patient_id": 42, "latitude": 13.7563, "longitude": 100.5018,
      "recorded_at": "2026-08-27T09:00:00Z", "accuracy": 12.0, "speed": 1.2 },
    { "patient_id": 42, "latitude": 13.7570, "longitude": 100.5025,
      "recorded_at": "2026-08-27T09:00:30Z" }
  ]
}
```

จุดแต่ละจุดหน้าตาเหมือน body ของ `POST /api/gps` ทุกประการ:

| ฟิลด์ | จำเป็น | หมายเหตุ |
|---|---|---|
| `patient_id` | ✅ | เลข `users.id` **ไม่ใช่ Firebase uid** |
| `latitude` / `longitude` | ✅ | −90..90 / −180..180 |
| `recorded_at` | ✅ | **เวลาที่เครื่องอ่านค่าได้ ไม่ใช่เวลาที่ส่ง** UTC ISO ลงท้าย `Z` |
| `accuracy` | ⬜ | เมตร |
| `speed` | ⬜ | m/s — ไม่มีให้ส่ง `null` **อย่าส่ง `0.0`** มันแปลว่า "ยืนนิ่ง" ซึ่งคนละเรื่องกับ "ไม่รู้" |
| `altitude` · `direction` · `device_motion` | ⬜ | `direction` 0–359 |

ตอบ `200`:

```json
{ "status": "success", "patient_id": 42, "accepted": 2 }
```

**กฎที่ต้องรู้**

* **สูงสุด 500 จุดต่อครั้ง** เกินได้ `422` — คิวยาวกว่านั้นให้แบ่งส่ง
* **ทุกจุดในคำขอเดียวต้องเป็นผู้ป่วยคนเดียวกัน** ปนกันได้ `422`
* **ไม่ต้องเรียงก่อนส่ง** เซิร์ฟเวอร์เรียงตาม `recorded_at` ให้เอง (ตัวกรอง Kalman เป็น
  state ต่อเนื่อง คิวที่สลับลำดับจะทำให้เส้นทางบิด)
* **คะแนนความเสี่ยงคิดครั้งเดียวต่อคำขอ ไม่ใช่ต่อจุด** — คะแนนบอกว่า*ตอนนี้*อยู่ตรงไหน
  จุดระหว่างทางอยู่ในประวัติที่ตัวคิดคะแนนอ่านอยู่แล้ว และยัง**ถูก throttle 1 ครั้ง/60 วินาที/
  คนไข้** ร่วมกับ `POST /api/gps` ด้วย
* ส่งซ้ำจุดเดิมได้ ไม่มีการตรวจซ้ำ — แถวจะซ้ำในประวัติ **ให้แอปลบออกจากคิวเมื่อได้ `200`
  เท่านั้น** ถ้าไม่แน่ใจว่าถึงหรือยัง ยอมส่งซ้ำดีกว่าทิ้ง

| รหัส | เมื่อไหร่ |
|---|---|
| `200` | รับแล้วทั้งชุด |
| `403` | ส่งในนามคนไข้ที่ไม่ใช่ของคุณ (เปิด auth แล้วเท่านั้น) |
| `404` | `patient_id` ไม่มีในตาราง `users` |
| `422` | `points` ว่าง · เกิน 500 · ปนหลายคนไข้ · พิกัดนอกช่วง |

## 11.3 `GET /api/risk/{patient_id}` — คะแนนความเสี่ยงตอนนี้

```
GET /api/risk/42
GET /api/risk/42?lat=13.7563&lng=100.5018
```

> 🛑 **เรียกแล้วมีผลข้างเคียง** ทุกครั้งที่เรียก เซิร์ฟเวอร์จะ **คิดคะแนนใหม่ · บันทึกแถวลง
> `risk_scores` · และถ้าเข้าเกณฑ์ก็เขียน `alerts` แล้วยิง push เข้ามือถือผู้ดูแล**
> **ห้ามเรียกเป็นรอบ ๆ** ปกติแอปไม่ต้องเรียกเลย — `POST /api/gps` คิดให้อยู่แล้วทุก 60 วินาที
> เรียกเมื่อผู้ใช้กดดูจริง ๆ เท่านั้น

ตอบ `200`:

```json
{
  "patient_id": 42,
  "status": "ok",
  "message": "Risk 63.5% (medium).",
  "factors_used": ["route_deviation", "wandering", "confusion", "danger_zone", "unfamiliarity"],
  "risk_score": 63.5,
  "risk_level": "medium",
  "contributions": { "route_deviation": 24.0, "wandering": 18.5 },
  "wandering_detected": true,
  "gps_available": true,
  "emergency": false,
  "reason": null,
  "base_risk_score": 58.5,
  "temporal_adjustment": 5.0,
  "temporal_rules_triggered": ["night_hours"]
}
```

| `status` | แปลว่า |
|---|---|
| `ok` | คะแนนเต็มรูปแบบ ครบ 5 ปัจจัย |
| `partial` | **ผู้ป่วยยังไม่มีหมุดสักที่** เหลือแค่ 2 ปัจจัย แล้วเกลี่ยน้ำหนักใหม่ — **ห้ามแสดงเหมือนคะแนนเต็ม** วัดแล้วว่าโหมดนี้แยก "นั่งอยู่บ้าน" กับ "หลง 2.5 กม." ไม่ออก ทั้งคู่ได้ 18.8 |
| `no_data` | ไม่มีพิกัด GPS เลย ทุกฟิลด์คะแนนเป็น `null` |

* `risk_score` คือค่า **สุดท้าย** แล้ว = `base_risk_score` + `temporal_adjustment`
  ส่วน `contributions` รวมกันได้เท่ากับ `base_risk_score` ไม่ใช่ `risk_score`
* `risk_level` — `low` / `medium` / `high` เกณฑ์อยู่ในหัวข้อ 5
* `emergency: true` แปลว่ารอบนี้เขียน alert และพยายามส่ง push แล้ว `reason` บอกว่าเพราะอะไร
  (`danger_zone` · `sustained_risk` · อื่น ๆ)
* `factors_used` ตรงกับ key ใน `contributions` เสมอ — ถ้าจะทำหน้าอธิบายคะแนน ใช้ลิสต์นี้
  อย่าฮาร์ดโค้ดชื่อปัจจัย น้ำหนักและรายการปัจจัยแก้ได้จากฐานข้อมูลกฎ

## 11.4 `GET /api/search-area/{patient_id}` — พื้นที่ที่น่าจะอยู่ ตอนหาไม่เจอ

หน้าจอของ**ผู้ดูแล** ตอนผู้ป่วยหายไป ไม่ใช่หน้าจอผู้ป่วย

```
GET /api/search-area/42
GET /api/search-area/42?time_missing_minutes=40
GET /api/search-area/42?last_lat=13.75&last_lng=100.50&time_missing_minutes=40
```

> 🛑 **หนักและมีผลข้างเคียง** จำลองเส้นทาง 10,000 เส้นแล้วคำนวณ KDE ต่อ และ**ถ้า GPS ขาด
> จริงจะเขียน alert `gps_loss` แล้วยิง push** ตอบกลับมี **cell ความน่าจะเป็นราว 2,500 จุด**
> — payload ใหญ่ ใช้เวลาหลายวินาที **เรียกตอนผู้ดูแลกดค้นหาเท่านั้น ห้าม poll**

| query param | ค่าเริ่มต้น | ใส่เมื่อไหร่ |
|---|---|---|
| `time_missing_minutes` | **25** | เวลาที่หายไปจริง — ตัวนี้กำหนดรัศมีโดยตรง ควรให้ผู้ดูแลกรอก |
| `last_lat` / `last_lng` | พิกัดล่าสุดที่บันทึกไว้ | ผู้ดูแลรู้ว่าเห็นครั้งสุดท้ายที่ไหน แต่ระบบไม่มีข้อมูล |
| `last_speed_ms` / `last_direction_deg` | ค่าล่าสุดที่บันทึกไว้ | ปกติไม่ต้องส่ง |

| `status` | แปลว่า | แอปต้องทำ |
|---|---|---|
| `ok` | คำนวณให้แล้ว | วาดโซนบนแผนที่ |
| `gps_active` | **GPS ยังส่งอยู่ ไม่ต้องค้นหา** ได้แค่ `last_known_location` | พาไปหน้าแผนที่ปกติ (หัวข้อ 6) แทน |
| `no_data` | ไม่มีพิกัดเลยและผู้ดูแลก็ไม่ได้ส่งมา | ให้ผู้ดูแลกรอกจุดที่เห็นครั้งสุดท้าย แล้วเรียกใหม่พร้อม `last_lat`/`last_lng` |

ฟิลด์ที่ตอบกลับตอน `ok`:

| ฟิลด์ | คืออะไร |
|---|---|
| `high_probability_zone` · `medium_` · `low_` | ลิสต์ `{latitude, longitude, probability}` — **วาดเป็น heatmap ไม่ใช่หมุด** จำนวนหลักร้อยถึงหลักพันต่อโซน |
| `target_locations` | สถานที่คุ้นเคยที่ควรไปดูก่อน **มี `name` ให้ใช้** เรียงมาแล้ว — ตัวนี้แหละที่ทีมค้นหาอ่านจริง |
| `familiar_paths` | เส้นทางจากจุดสุดท้ายไปยังสถานที่คุ้นเคย `waypoints` เป็น `[[lat, lng], ...]` วาดเป็นเส้นได้เลย |
| `search_radius_meters` / `adjusted_radius_meters` | ก่อนและหลังปรับตามพฤติกรรมและระยะของโรค `adjustment_reason` อธิบายว่าปรับเพราะอะไร — **แสดงเหตุผลด้วย** ผู้ดูแลควรรู้ว่าทำไมวงถึงเท่านี้ |
| `grid_bounds` | กรอบสี่เหลี่ยมของตาราง ใช้ตั้ง viewport ของแผนที่ |

**ถ้าผู้ป่วยไม่มีหมุดเลย** `target_locations` กับ `familiar_paths` จะว่าง แต่โซนความน่าจะเป็น
ยังคำนวณได้ตามปกติ — วัดแล้วว่าโซนแทบไม่ขึ้นกับหมุด สิ่งที่ขึ้นกับหมุดคือ*รายการที่ให้ไปดู*

# 12. ผู้ดูแลหลายคนต่อผู้ป่วยหนึ่งคน (ใหม่ 2026-08-28)

ตอบคำถามข้อ 3 ที่ตกลงกันไว้ — *"แจ้งผู้ดูแลหลายคน + จัดอันดับระยะทาง + ฉันจะไปรับ"*
ฝั่งแอปบอกลำดับเองว่า backend แก้ฐานข้อมูลก่อนแล้วค่อยต่อ UI **เสร็จแล้ว: ฐานข้อมูล · สิทธิ์ · push หาทุกคน · ที่เก็บพิกัด ·
รหัสเชิญผู้ดูแลคนที่ 2 — ยังไม่เสร็จ: การจัดอันดับ และปุ่ม "ฉันจะไปรับ"**

เดิมผู้ป่วย 1 คนมีผู้ดูแลได้ **1 คน** (`users.caregiver_id` เป็น FK เดี่ยว) ตอนนี้เป็นตาราง
`patient_caregivers` ผูกได้หลายคน

## เสร็จแล้ว — ใช้ได้เลย

| | |
|---|---|
| **สิทธิ์เข้าถึง** | ผู้ดูแล**ทุกคน**ที่ผูกกับผู้ป่วยอ่านข้อมูลผู้ป่วยคนนั้นได้เท่ากันหมด ไม่มีใครสิทธิ์มากกว่าใคร |
| **Push** | alert 1 ครั้ง → ส่งเข้า**ทุกเครื่องของผู้ดูแลทุกคน** ไม่ต้องแก้อะไรฝั่งแอป ของเดิมทำงานต่อได้เลย |

## 12.1 `PUT /api/caregivers/{caregiver_id}/location` — แอปผู้ดูแลรายงานตำแหน่งตัวเอง

จำเป็นสำหรับการจัดอันดับระยะทาง — ไม่รู้ว่าผู้ดูแลอยู่ไหน ก็เรียงไม่ได้

```
PUT /api/caregivers/12/location
{ "latitude": 13.7563, "longitude": 100.5018 }
```

ตอบ `200`:

```json
{ "caregiver_id": 12, "location_updated_at": "2026-08-28T09:14:02Z" }
```

| เรื่อง | รายละเอียด |
|---|---|
| **ทับของเดิมเสมอ ไม่เก็บประวัติ** | เก็บแค่ตำแหน่งล่าสุดตำแหน่งเดียว ระบบไม่มีที่ไหนเก็บเส้นทางการเดินของผู้ดูแล — **จงใจ** การจัดอันดับถามแค่ "ตอนนี้ใครใกล้สุด" ไม่มีอะไรถามมากกว่านั้น |
| **⚠️ ต้องขอ consent ก่อนเริ่มส่ง** | นี่คือตำแหน่งของ*คนในครอบครัว* ไม่ใช่ของผู้ป่วย เขาไม่ได้อยู่ในความดูแลของใคร แอปต้องถามก่อน และควรมีสวิตช์ให้ปิด |
| **`location_updated_at` ตั้งจากฝั่ง server** | ไม่ได้รับจาก body — มือถือที่นาฬิกาเพี้ยนจะทำให้ตำแหน่งเก่าดูสดและชนะการจัดอันดับที่ควรแพ้ |
| **ส่งบ่อยแค่ไหน** | ยังไม่กำหนด **บอกมาว่าแอปส่งไหวแค่ไหน** (background/foreground, กินแบตแค่ไหน) แล้วค่อยตกลงเกณฑ์ว่าตำแหน่งเก่ากี่นาทีถือว่าใช้ไม่ได้ ตอนนี้เก็บเวลาไว้เฉยๆ ยังไม่มีใครตัดสิน |
| `403` | ส่งตำแหน่งแทนคนอื่นไม่ได้ — จะทำให้เขาขึ้นเป็นอันดับ 1 ของผู้ป่วยที่เขาอยู่ห่างเป็นสิบกิโล |
| `422` | ส่ง `caregiver_id` ที่เป็น**ผู้ป่วย** → ปฏิเสธ ตำแหน่งผู้ป่วยไปที่ `POST /api/gps` ซึ่งกรอง Kalman คิดคะแนน และยิง alert ได้ ส่งมาที่นี่มันจะเงียบและดูเหมือนสำเร็จ |

## 12.2 ผู้ดูแลคนที่ 2 เข้ามายังไง — รหัสเชิญ

ต้องมี **2 หน้าจอใหม่ฝั่งแอป** และมันเล็กทั้งคู่ หน้าตาเหมือนรหัสจับคู่เครื่องผู้ป่วย
ที่ทำไปแล้ว (หัวข้อ 2) — รูปแบบรหัสเดียวกัน อายุ 24 ชม. เท่ากัน ใช้ได้ครั้งเดียวเหมือนกัน

**หน้าที่ 1 — ผู้ดูแลที่มีอยู่กดออกรหัสเชิญ**

```
POST /api/patients/42/caregiver-invites
(body ว่าง)
```
```json
{ "patient_id": 42, "invite_code": "K7M2-QX94",
  "expires_at": "2026-08-29T09:14:02Z" }
```

**หน้าที่ 2 — ผู้ดูแลคนใหม่กรอกรหัส**

```
POST /api/caregivers/redeem-invite
{ "code": "K7M2-QX94" }
```
```json
{ "patient_id": 42, "patient_name": "ยาย",
  "caregiver_id": 57, "already_linked": false }
```

| เรื่อง | รายละเอียด |
|---|---|
| **คนใหม่ต้องสมัครก่อน** | ต้อง sign in Firebase + `POST /api/register` ด้วย `role: "caregiver"` **ก่อน**กรอกรหัส — endpoint นี้ไม่สร้างบัญชีและไม่คืน token ต่างจาก `POST /api/pair` ของเครื่องผู้ป่วย มันเพิ่มแค่สิทธิ์เข้าถึง |
| `caregiver_id` ใน body | ส่งเฉพาะตอน `AUTH_ENABLED=false` เปิด auth แล้วยึดจาก token — กันไม่ให้ใครแลกรหัสเข้าบัญชีคนอื่น |
| **ใครออกรหัสได้** | ผู้ดูแล**คนไหนก็ได้**ที่ผูกกับผู้ป่วยคนนั้น ไม่จำกัดเฉพาะคนแรก · **ตัวผู้ป่วยเองออกไม่ได้ (403)** แม้เครื่องผู้ป่วยจะอ่านข้อมูลตัวเองได้ — คนเป็นสมองเสื่อมแจกสิทธิ์ดูตำแหน่งตัวเองคือเรื่องที่ผู้ดูแลมีไว้เพื่อป้องกัน |
| **รหัสจับคู่เครื่องผู้ป่วย ≠ รหัสเชิญ** | คนละตาราง คนละชุด **จงใจ** — รหัสของหัวข้อ 2 ใช้*สวมเป็น*ผู้ป่วย รหัสนี้ใช้*ดู*ผู้ป่วย ถ้าใช้ชุดเดียวกัน รหัสที่ตั้งใจไว้ตั้งค่ามือถือจะกลายเป็นรหัสที่แจกสิทธิ์ดูตำแหน่งผู้ป่วยได้ |
| `404` | รหัสผิด/หมดอายุ/ใช้ไปแล้ว — **ข้อความเดียวทั้งสามกรณี** อย่าพยายามแยก แอปแสดง "รหัสไม่ถูกต้องหรือหมดอายุแล้ว" พอ |
| พิมพ์ตัวเล็ก/ใส่ขีด/มีเว้นวรรค | รับหมด normalise ให้เอง เหมือนรหัสจับคู่ |
| `already_linked: true` | คนนั้นเป็นผู้ดูแลอยู่แล้ว ไม่ใช่ error — แต่**รหัสถูกใช้ไปแล้ว** แสดง "คุณดูแล [ชื่อ] อยู่แล้ว" |

## 12.3 `GET /api/patients/{patient_id}/caregivers` — ใครอยู่ใกล้ผู้ป่วยที่สุด

**พร้อมใช้แล้ว 28 ส.ค.** อ่านอย่างเดียว ไม่เขียนอะไร ไม่ push · polling ได้

```json
{ "patient_id": 42,
```

| `distance_m: null` | ไม่รู้ตำแหน่งฝั่งใดฝั่งหนึ่ง (ผู้ดูแลยังไม่เคยส่ง หรือผู้ป่วยยังไม่เคยมี GPS) ไม่ใช่ error |

| `max_age_s` | ส่งมาด้วยทุกครั้ง เพื่อให้แอปเขียนข้อความได้ตรงกับที่ backend ใช้จริง ตอนนี้ **1800 วิ (30 นาที) เป็นค่าตั้งต้นชั่วคราว** — บอกมาว่าแอปส่งตำแหน่งถี่แค่ไหน แล้วเราแก้ค่าในฐานข้อมูล **ไม่ต้องแก้โค้ดและไม่ต้อง deploy** |
| สิทธิ์ | หลังประตูเดียวกับข้อมูลผู้ป่วยอื่น ๆ — คนนอก `403` |

## 12.4 ปุ่ม "ฉันจะไปรับ" — `POST` / `DELETE /api/alerts/{alert_id}/claim`

**พร้อมใช้แล้ว 28 ส.ค.** ตอบคำถามข้อ 2 ที่เราถามไปด้วยค่าตั้งต้นที่แก้ได้ — ถ้าอยากได้ต่างจากนี้บอกมา

```
POST /api/alerts/91/claim          ← "ฉันไปเอง"
```
```json
{ "alert": { "id": 91, "patient_id": 42, "alert_type": "wandering",
             "severity": "high", "message": "ออกนอกพื้นที่",
             "resolved": false,
             "claimed_by": 57, "claimed_by_name": "ลูกชาย",
             "claimed_at": "2026-08-28T14:02:11Z",
             "claimed_by_latitude": 13.7591, "claimed_by_longitude": 100.5018,
             "claimed_by_location_age_s": 42.0 },
  "push": "sent" }
```

> ### ⭐ เพิ่ม 29 ส.ค. — ตำแหน่งของคนที่กดรับ (ตามที่ขอมา)
>
> `claimed_by_latitude` · `claimed_by_longitude` · `claimed_by_location_age_s`
> มาพร้อมกันทุกที่ที่ `AlertOut` โผล่ — ทั้ง `POST /claim` `DELETE /claim`
> `PATCH /api/alerts/{id}` และ **ทุกแถวของ `GET /api/patients/{id}/alerts`**
>
> * **เป็นตำแหน่งของ *คนที่กดรับ* เท่านั้น และเฉพาะตอนที่ยังรับอยู่** ไม่ใช่แผนที่ผู้ดูแล
>   alert ที่ยังไม่มีใครรับคืน `null` ทั้งสามฟิลด์ — **ไม่ถอยไปใช้ตำแหน่งผู้ดูแลคนหลัก**
>   เพราะจุดบนแผนที่แปลว่า "มีคนกำลังไป" ซึ่งยังไม่มีใครพูด
> * **ต้องอ่าน `claimed_by_location_age_s` ทุกครั้งก่อนวาดจุด** ตำแหน่งอายุ 2 นาที
>   ที่แสดงเหมือนสด คือวิธีทำให้ครอบครัวเลิกรอ ตอนกดปุ่มแอปเขาเปิดอยู่แน่นอน
>   ค่าจึงมักจะน้อย แต่ห้ามสมมติเอา
> * **คนที่ไม่เคยส่งตำแหน่งเลย ยังได้ชื่อครบ** พิกัดเป็น `null` เฉย ๆ —
>   กฎเดียวกับ §12.3 คือตำแหน่งที่หายไปทำให้ข้อมูลน้อยลง ไม่ได้ทำให้คนหายไป

| เรื่อง | รายละเอียด |
|---|---|
| **ผู้ดูแลคนอื่นเห็นอะไร** | ได้ push ทันที (ไม่มี cooldown) หัวข้อ "มีคนไปรับแล้ว" เนื้อความ "[ชื่อ] กำลังไปรับผู้ป่วย" · data มี `event: "claimed"`, `alert_id`, `claimed_by` · และ `GET /api/patients/{id}/alerts` คืน `claimed_by` / `claimed_by_name` / `claimed_at` / พิกัด มาให้ทุกแถว **จอที่เปิดค้างอยู่ก็เห็นเมื่อรีเฟรช**<br>🛑 **แก้ 29 ส.ค. — บรรทัดนี้เคยพูดไม่จริง** ก่อนหน้านี้รายการคืน `claimed_by_name: null` ทุกแถว (มีชื่อเฉพาะตอนกดปุ่ม) เพราะตัวสร้าง response ในหน้ารายการไม่เคยโหลดคนที่กดรับมาเลย **ตอนนี้แก้แล้วและมีเทสต์กันไว้** ถ้าเคยเขียนโค้ดเผื่อ `null` ไว้ ไม่ต้องรื้อ แต่ไม่ต้องใช้แล้ว |
| **คนกดเองไม่ได้ push** | จงใจ — แจ้งเตือนคนเรื่องปุ่มที่เขาเพิ่งกดเอง คือวิธีสอนให้เขาเลิกอ่านแจ้งเตือน และแจ้งเตือนช่องนี้คือช่องที่ต้องอ่าน |
| **มีคนรับไปแล้ว** | `409` พร้อม `claimed_by` + `claimed_by_name` + `claimed_at` **ในตัว error** — แอปแสดง "ลูกชายรับเรื่องนี้แล้วเมื่อ 14:02" ได้เลย ไม่ต้องยิงซ้ำเพื่อไปหาว่าใคร |
| **กดซ้ำโดยคนเดิม** | `200` และ `push: "duplicate"` ไม่ push ซ้ำ |
| **เปลี่ยนใจได้** | `DELETE /api/alerts/{id}/claim` — **เฉพาะคนที่รับไว้เท่านั้น** (คนอื่น `403`) แล้วคนอื่นรับต่อได้ · การยกเลิก**ไม่ push** เพราะข่าวที่คนอื่นต้องรู้คือ "มีคนไปแล้ว" ซึ่งจะถูกส่งตอนคนต่อไปกด |
| 🛑 **"รับเรื่อง" ≠ "จบเรื่อง"** | `claimed_*` กับ `resolved` แยกกันคนละฟิลด์ ตั้งใจ — `resolved` แปลว่าผู้ป่วยปลอดภัยแล้ว ปิดด้วย `PATCH /api/alerts/{id}` เหมือนเดิม ถ้ากด "ฉันไปรับ" แล้วปิด alert ไปด้วย ครอบครัวจะเสียแถวเดียวที่บอกว่าเรื่องยังไม่จบ |
| **ต้องล็อกอิน** | `401` ถ้า `AUTH_ENABLED=false` — ไม่มี "ใคร" ให้บันทึก การบันทึกว่ามีคนไปรับทั้งที่ไม่รู้ว่าใคร คือการบอกครอบครัวว่ามีคนไปแล้วทั้งที่ยังไม่มีใครตัดสินใจ |
| `push` ที่เป็นไปได้ | `sent` · `duplicate` · `no_other_caregiver` (มีผู้ดูแลคนเดียว ไม่ใช่ error) · `failed` · `error` |

## ยังไม่มี — ต้องคุยกันก่อน

| | ทำไมยังไม่ทำ |
|---|---|
| **ตำแหน่งของคนที่กด "ฉันไปรับ"** | ตอนนี้คนอื่นเห็น*ชื่อ*กับ*เวลา* ยังไม่เห็นว่าเขาอยู่ตรงไหนบนแผนที่ ถ้าอยากได้บอกมา — ข้อมูลมีอยู่แล้วใน 12.3 แค่ยังไม่ได้ผูกเข้ากับ alert |

# 13. เขตอันตราย — `GET /api/danger-zones`

**มีอยู่แล้วตั้งแต่ 20 ส.ค. ใช้ได้เลยวันนี้ แต่เพิ่งเขียนลงสัญญานี้ 29 ส.ค.**
ขออภัย — endpoint นี้ถูกสร้างไว้นานแล้วและไม่มีใครบอกฝั่งแอปว่ามันมี

```
GET /api/danger-zones
Authorization: Bearer <Firebase ID token>
```
```json
[ { "id": 3, "name": "ทางแยกต่างระดับ", "zone_type": "highway",
    "center_latitude": 13.7601, "center_longitude": 100.5102,
    "radius_meters": 150, "active": true,
    "rationale": "ทางหลวง 6 เลนไม่มีทางข้าม" } ]
```

## ทำไมแอปต้องใช้อันนี้ — เรื่องนำทางไปที่ปลอดภัย

**Lane B (นำทางไปสถานีตำรวจ/โรงพยาบาลใกล้สุด) เป็นงานฝั่งแอปทั้งหมด** — ตกลงกัน
29 ส.ค. เพราะแอปมี Google API key อยู่แล้ว และการป้อนข้อมูลสถานที่เองฝั่ง backend จะ
ครอบคลุมแค่พื้นที่ที่เรากรอกไว้ ซึ่งพังพอดีตอนที่ผู้ป่วยเดินหลงออกไป**นอก**พื้นที่นั้น
คือตอนที่ต้องการฟีเจอร์นี้ที่สุด

**แต่ Google ไม่รู้ว่าอะไรอันตรายสำหรับผู้ป่วยสมองเสื่อม เรารู้ และอยู่ในตารางนี้**

Places API จะคืนโรงพักที่อยู่**คนละฝั่งทางหลวง**มาให้หน้าตาเฉย เพราะระยะทางเส้นตรงมันใกล้
ถ้าแอปนำทางผู้ป่วยข้ามไป เรากำลังพาคนสับสนข้ามถนน 6 เลนเพื่อไปหาที่ปลอดภัย

**สิ่งที่ขอให้ทำ** — ก่อนเลือกปลายทางที่จะนำทางไป:

1. ยิง `GET /api/danger-zones` (ผลไม่ค่อยเปลี่ยน แคชไว้ในเครื่องได้เลย รีเฟรชวันละครั้งพอ)
2. ผู้สมัครที่ **จุดหมายอยู่ในวงกลมของเขตอันตราย** → ตัดทิ้ง
3. ผู้สมัครที่ **เส้นทางจาก Directions ผ่านเข้าไปในวงกลม** → ถ้าเลือกที่อื่นได้ ให้เลือกที่อื่น
   ถ้าไม่มีทางอื่นจริง ๆ ให้แสดงคำเตือนแทนการนำทางเงียบ ๆ

| เรื่อง | รายละเอียด |
|---|---|
| ใครเรียกได้ | ใครก็ได้ที่ล็อกอิน — ไม่ผูกกับผู้ป่วยคนใดคนหนึ่ง **เขตอันตรายเป็นของกลางทั้งระบบ** ไม่มี `patient_id` |
| `zone_type` | `highway` · `waterway` · `construction` · `other` |
| `radius_meters` | วงกลม ไม่ใช่รูปหลายเหลี่ยม — จุดอยู่ในเขตเมื่อระยะจากจุดกลาง ≤ ค่านี้ |
| `rationale` | ข้อความภาษาคนอ่านรู้เรื่อง **เอาไปแสดงบนคำเตือนได้เลย** ไม่ต้องแต่งเอง |
| คืนเฉพาะที่ `active` | ที่ถูกปิดไปแล้วไม่ออกมา ไม่ต้องกรองเอง |

## 🛑 อีกสองข้อของ Lane B ที่ต้องคิดฝั่งแอป

**1. Places API ต้องเปิดแยกจาก Directions** คนละ API คนละการคิดเงินใน Google Cloud
ต่อให้ key เดียวกันก็ต้องไปเปิด Places API ในโปรเจกต์นั้นก่อน — เช็คก่อนเริ่มเขียน

**2. บางครั้งคำตอบที่ถูกคือ "อย่าเดิน ยืนรออยู่ตรงนั้น"** ผู้ป่วยระยะกลาง (`severity_level: 2`
ซึ่งแอปได้มาแล้วจาก `POST /api/pair` และ `GET /api/patients/{id}`) ที่ถูกสั่งให้เดิน 800 เมตร
ทำให้พื้นที่ที่ต้องค้นหาขยายออกทุกนาที และคนสับสนที่เดินตามคำสั่งเลี้ยวข้ามถนน
อันตรายกว่าการยืนอยู่กับที่ **แนะนำให้มีเพดานระยะทาง** เกินกว่านั้นแสดงว่า
"อยู่ตรงนี้นะ ผู้ดูแลกำลังไปหา" แทนการนำทาง — ตัวเลขเท่าไหร่คุณตัดสินได้เลย เป็นเรื่องหน้าจอ

# 14. `GET /api/me` — "ผู้ถือ token นี้คือใคร" (ใหม่ 2026-09-01)

**เพิ่มมาเพราะ `caregiver_login_screen.dart:110` ต้องอ่าน `CAREGIVER_TEST_ID` จาก `.env`**
ซึ่งไม่ใช่ความผิดฝั่งแอป — ก่อนหน้านี้ backend **ไม่มี route ไหนเลย** ที่ตอบคำถามนี้ได้

`POST /api/register` เป็น route เดียวที่เคยคืน `users.id` และมันยิงครั้งเดียวตอนสมัคร
ผู้ดูแลที่ login ซ้ำ หรือลงแอปเครื่องใหม่ จึงหาทางกลับไปหา id ของตัวเองไม่เจอ

## Request

```http
GET /api/me
Authorization: Bearer <Firebase ID token>
```

ไม่มี body ไม่มี query param

## Response 200

```json
{
  "id": 21,
  "firebase_uid": "AbCdEfGhIjKlMnOpQrStUvWxYz01",
  "name": "ผู้ดูแลทดสอบ",
  "role": "caregiver",
  "phone": "0812345678",
  "created_at": "2026-08-30T14:22:01.482913Z"
}
```

| field | ใช้ทำอะไร |
|---|---|
| `id` | **ตัวที่มาแทน `CAREGIVER_TEST_ID`** — เก็บลง `CaregiverSession` แล้วส่งเป็น `caregiver_id` ใน `POST /api/patients` |
| `role` | `"caregiver"` หรือ `"patient"` — **ใช้กันคนไข้ล็อกอินเข้าหน้าผู้ดูแล** ตอนนี้ไม่มีอะไรกันเลย และมันจะดูเหมือนสำเร็จด้วย |
| `phone` | เบอร์ที่หน้าจอ SOS ของคนไข้กดโทร (null ได้) |
| `name` | ชื่อที่แสดงบนหน้าโฮม |

## Error

| status | เมื่อไหร่ | ทำยังไงต่อ |
|---|---|---|
| **401** `missing bearer token` | ไม่ได้ส่ง header หรือส่ง `Bearer ` ว่างๆ | ให้ผู้ใช้ login ใหม่ |
| **401** `invalid or expired ID token` | token หมดอายุ / ปลอม | `getIdToken(true)` แล้วลองใหม่ ถ้ายังไม่ผ่านให้ login ใหม่ |
| **403** `signed in but not registered — call /api/register first` | Firebase มี account แล้ว แต่ยังไม่มีแถวใน `users` | **สถานะนี้เกิดขึ้นจริงได้** — สมัคร Firebase สำเร็จแต่ `POST /api/register` พลาด ให้พาไปหน้ากรอกชื่อ/เบอร์แล้ว register ใหม่ |

## ⚠️ สองข้อที่ต่างจาก route อื่นทั้งหมด

**1. ต้องมี token เสมอ แม้ `AUTH_ENABLED` จะปิดอยู่**
route อื่นตอนนี้เรียกได้โดยไม่ต้องมี header เลย แต่ตัวนี้ไม่ได้ — เพราะคำถามของมันคือ
"คุณคือใคร" และถ้าไม่มี token ก็ไม่มีคำตอบ ไม่ใช่ตอบว่า "ไม่มีใคร"
→ **แปลว่าต้องเรียกหลัง `signInWithEmailAndPassword` / `signInWithCustomToken` สำเร็จแล้วเท่านั้น**

**2. ไม่ใช่ `/api/caregivers/me`** — เครื่องคนไข้ก็ถือ token เหมือนกันและก็เรียกได้

# 15. `GET /api/predict-destination/{patient_id}` — ทำนายว่าจะไปที่ไหนต่อ (ใหม่ 2026-09-01)

> 🟢 **มีให้แล้ว แต่ยังไม่ต้องต่อตอนนี้** ไม่มีหน้าจอไหนต้องใช้ ไม่มี W1–W4 ข้อไหนแตะมัน
> ค่อยว่ากันหลัง pilot ตอนที่มีข้อมูล GPS จริงแล้วตัวเลขจะมีความหมายขึ้นเยอะ
> เอกสารนี้เขียนไว้เพื่อให้รู้ว่ามี ไม่ใช่เพื่อสั่งให้ทำ — ไปทำ §5 ใน
> `APP_SYNC_2026-09-01.md` ก่อนคุ้มกว่ามาก

**เดิม path นี้ตอบ 404** เพราะตัวที่รายงานอ้างถึงคือ LSTM ซึ่งถูกตัดตั้งแต่แผน 4 สัปดาห์
ตอนนี้มีของจริงมาแทน แต่ **เป็นคนละวิธี และมันบอกตัวเองว่าเป็นวิธีไหน**

## Request

```http
GET /api/predict-destination/5?lat=13.7563&lng=100.5018
Authorization: Bearer <Firebase ID token>
```

| param | จำเป็น | ความหมาย |
|---|---|---|
| `patient_id` (path) | ✅ | `users.id` |
| `lat` / `lng` | ❌ | ทับตำแหน่งปัจจุบัน — ไม่ส่งมาจะใช้จุด GPS ล่าสุดที่บันทึกไว้ |

## Response 200 — `status: "ok"`

```json
{
  "patient_id": 5,
  "status": "ok",
  "scorer": "markov",
  "history_status": "sparse",
  "transitions_observed": 8,
  "current_cluster_id": 0,
  "current_place_name": "บ้าน",
  "message": "Markov transition จาก 'บ้าน' — นับการย้ายได้ 8 ครั้งใน 30 วัน (ต่ำกว่า 20) ตัวเลขยังไม่น่าเชื่อถือ",
  "predictions": [
    {"rank": 1, "cluster_id": 1, "place_name": "วัด",
     "latitude": 13.7601, "longitude": 100.5062,
     "probability": 0.8, "probability_pct": 80},
    {"rank": 2, "cluster_id": 2, "place_name": "ตลาด",
     "latitude": 13.753, "longitude": 100.499,
     "probability": 0.2, "probability_pct": 20}
  ]
}
```

## 🛑 สามฟิลด์ที่ห้ามมองข้าม — มันคือเหตุผลที่ endpoint นี้ทำได้

| field | ค่า | แอปต้องทำอะไร |
|---|---|---|
| `scorer` | `"markov"` เสมอ | **ห้ามเขียนบนหน้าจอว่า "AI ทำนาย"** มันคือการนับว่าคนไข้เคยย้ายจากที่นี่ไปที่ไหนบ้าง ไม่ใช่ LSTM |
| `history_status` | `ok` \| `sparse` \| `none` | ดูตารางล่าง |
| `transitions_observed` | จำนวนเต็ม | จำนวนการย้ายที่นับได้ใน 30 วัน — เอาไว้ตรวจว่าทำไมตัวเลขถึงหน้าตาแบบนั้น |

| `history_status` | หมายความว่า | ควรแสดงยังไง |
|---|---|---|
| `"none"` | **ยังไม่เคยเห็นคนไข้ย้ายออกจากที่ที่ยืนอยู่เลย** ตัวเลขที่ได้คือการหารเท่ากัน (1 ÷ จำนวนหมุด) | **ห้ามแสดงเปอร์เซ็นต์** แสดงได้แค่รายชื่อสถานที่ หรือซ่อนไปเลย |
| `"sparse"` | นับได้น้อยกว่า 20 ครั้ง | แสดงได้ แต่ใส่คำว่า "ยังเก็บข้อมูลอยู่" กำกับ |
| `"ok"` | ≥ 20 ครั้ง | แสดงเปอร์เซ็นต์ได้ตามปกติ |

**ทำไมต้องเข้มขนาดนี้:** ถ้าคนไข้มีหมุด 3 จุดและยังไม่เคยเก็บ GPS จริงเลย ระบบจะตอบว่า
"วัด 50%" ซึ่งอ่านดูเหมือนคำทำนายของโมเดล แต่จริงๆ คือ 1 หารด้วย 2 โปรเจกต์นี้เคยพลาด
แบบนี้มาแล้วครั้งหนึ่ง (C-3 Confidence Score ที่ตันอยู่ที่ 35% ตลอดกาลเพราะมันวัดแค่ระยะทาง)
และต้องเขียน `trip_confidence.py` ขึ้นมาใหม่ทั้งตัว **ตัวเลขที่ดูเหมือนคำทำนายแต่ไม่ได้
วัดอะไร แย่กว่าไม่มีตัวเลข** เพราะผู้ดูแลจะเลิกเชื่อทั้งระบบภายในสัปดาห์เดียว

## สถานะอื่นที่ไม่ใช่ `ok` — คืน `predictions: []` ทุกอัน ไม่ใช่ error

| `status` | เมื่อไหร่ | ทำยังไงต่อ |
|---|---|---|
| `"no_profile"` | ยังไม่มีหมุดสักจุด | ให้ผู้ดูแลปักหมุดก่อน (`POST /api/patients/{id}/places`) |
| `"no_location"` | ไม่ได้ส่ง `lat`/`lng` และไม่มี GPS เก็บไว้เลย / ไม่มีประวัติ 30 วัน | ส่ง `lat`/`lng` มาด้วย หรือรอให้ `POST /api/gps` ทำงานสักพัก |
| `"unknown_current_place"` | **คนไข้ไม่ได้อยู่ในรัศมีของหมุดไหนเลย** | **นี่ไม่ใช่ข้อผิดพลาด** — Markov ต้องมีจุดตั้งต้น ถ้ากำลังกังวลว่าหลงทาง ให้ใช้ `GET /api/risk/{id}` แทน ซึ่งไม่ต้องการจุดตั้งต้น |

## ข้อควรระวัง

* **อ่านอย่างเดียว ไม่เขียนอะไรลง DB และไม่ push** ต่างจาก `GET /api/risk` และ
  `GET /api/search-area` ที่เป็น `GET` แต่มี side effect
* **ถึงอย่างนั้นก็ยัง ห้าม poll** — มัน `fit` transition matrix ใหม่จาก GPS 30 วันทุกครั้ง
  ที่เรียก และคำตอบจะเปลี่ยนก็ต่อเมื่อคนไข้ย้ายที่เท่านั้น เรียกตอนเปิดหน้าจอก็พอ
* **คืนได้สูงสุด 3 อันดับ** เท่ากับ `/api/recommendation` — อันดับ 4-5 ที่ข้อมูลระดับนี้
  คือ noise
* `place_name` เป็น `null` ได้ ถ้าเป็นสถานที่ที่ Module 1 หาเจอเองแทนที่ผู้ดูแลจะปัก
  (ตัว clustering ตั้งชื่อไม่ได้) — ซ่อน tile นั้นไป อย่าพิมพ์ว่า "ไม่ทราบ" กฎเดียวกับ §11.1
