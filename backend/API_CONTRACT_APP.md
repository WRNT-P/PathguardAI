# API contract — แอปมือถือ: รับแจ้งเตือน (FCM)

> เขียน 2026-08-22 · **แก้ 2026-08-26 เพิ่มหัวข้อ 8 (ปุ่ม SOS), 9 (ขออนุมัติเดินทาง), 10 (หมุดสถานที่)** · สำหรับคนที่ 1 (Flutter)
> **สถานะ: backend เขียนเสร็จและมีเทสต์แล้ว** ยิงจริงได้เลย
> ถ้าจะเปลี่ยนอะไรในนี้ ต้องบอกกันก่อน อย่าแก้ฝ่ายเดียว

ก่อนหน้านี้เวลาผู้ป่วยเดินหลง ระบบเขียนแถวลงตาราง `alerts` แล้วจบ ไม่มีอะไรออกจากเซิร์ฟเวอร์
วิธีเดียวที่จะรู้คือต้องนั่งเฝ้า dashboard เอาไว้ ตอนนี้ต่อสายสุดท้ายแล้ว

# 1. ลงทะเบียนเครื่องผู้ดูแล

## `POST /api/devices/token`

**ถ้าไม่เรียกอันนี้ = ไม่มี push ตลอดกาล** alert จะถูกเขียนลง DB แล้วไม่ไปไหน

### Request

```json
{
  "user_id": 12,
  "token": "fcm-registration-token-จาก-firebase-messaging",
  "platform": "android"
}
```

| ฟิลด์ | ชนิด | หมายเหตุ |
|---|---|---|
| `user_id` | int | `users.id` ของ **ผู้ดูแล** ไม่ใช่ของผู้ป่วย — ได้จาก `POST /api/register` |
| `token` | string 10–255 | จาก `FirebaseMessaging.instance.getToken()` |
| `platform` | `android` \| `ios` \| `web` | default `android` |

### Response `200`

```json
{ "id": 1, "user_id": 12, "platform": "android" }
```

`404` = ยังไม่ได้ `POST /api/register` ก่อน

### เรียกเมื่อไหร่

- หลัง sign-in ครั้งแรก
- **ทุกครั้งที่เปิดแอป** — Firebase ออก token ใหม่ตอนลงแอปใหม่ และหมดอายุเองได้
- ตอน `onTokenRefresh` ยิง

เรียกซ้ำได้ ไม่เกิดแถวซ้ำ (upsert ยึด token เป็นตัวตน) และถ้าเครื่องเดียวกันมีคนล็อกอินใหม่
token จะย้ายไปเป็นของคนหลังสุดโดยอัตโนมัติ

# 2. ผูกผู้ป่วยกับผู้ดูแล — ด้วยรหัสจับคู่

> **เปลี่ยนเมื่อ 2026-08-26** เดิมหัวข้อนี้เขียนว่า *"ไม่มีรหัสเชิญ ไม่มีตารางจับคู่"* และให้
> ผู้ป่วยเรียก `POST /api/register` เอง **ยกเลิกแล้ว** — ผู้ป่วยอัลไซเมอร์ถือ email + password
> ไม่ได้ ตอนนี้ผู้ดูแลเป็นคนสร้างผู้ป่วย แล้วได้รหัสมากรอกบนเครื่องผู้ป่วย

## ขั้นที่ 1 — ผู้ดูแลสร้างผู้ป่วย

```json
POST /api/patients
{ "name": "ยาย", "severity_level": 2, "caregiver_id": 12 }
```

| ฟิลด์ | จำเป็น | หมายเหตุ |
|---|---|---|
| `name` | ✅ | 1–255 ตัวอักษร |
| `severity_level` | ⬜ | `1` = ระยะต้น · `2` = ระยะกลาง · ไม่ส่งก็ได้ |
| `caregiver_id` | ⚠️ | **ส่งเฉพาะตอน `AUTH_ENABLED=false`** พอเปิด auth แล้ว backend ยึดจาก token เสมอ และ**เมินค่าที่ส่งมา** เพื่อไม่ให้ใครผูกผู้ป่วยเข้าบัญชีคนอื่น |

ตอบ `201`:

```json
{
  "patient_id": 42,
  "name": "ยาย",
  "severity_level": 2,
  "caregiver_id": 12,
  "pairing_code": "7K2M-P9QX",
  "expires_at": "2026-08-27T09:15:00Z"
}
```

**แสดง `pairing_code` ให้ผู้ดูแลเห็นตามที่ส่งมา** (มีขีดคั่นเพื่อให้อ่านออกเสียงง่าย) รหัสอายุ
**24 ชั่วโมง** และ**ใช้ได้ครั้งเดียว**

> **"สถานที่ปลอดภัย" ที่หน้าจอนี้เก็บ ส่งด้วย `PUT /api/patients/{id}/places/home` — ดูหัวข้อ 10**
> `POST /api/patients` ไม่รับพิกัด และ**ปักแค่บ้านจุดเดียวไม่พอ** หัวข้อ 10 มีตัวเลขที่วัดมาแล้ว

## ขั้นที่ 2 — เครื่องผู้ป่วยกรอกรหัส

```json
POST /api/pair
{ "code": "7K2M-P9QX" }
```

**เป็น endpoint เดียวในระบบที่ไม่ต้องมี token** เพราะมันคือทางที่เครื่องผู้ป่วยจะ*ได้*
token มา ตอบ `200`:

```json
{
  "patient_id": 42,
  "firebase_custom_token": "eyJhbGciOi..."
}
```

## ขั้นที่ 3 — แอปเอา custom token ไป sign in

```dart
await FirebaseAuth.instance.signInWithCustomToken(res.firebaseCustomToken);
// จากนั้นใช้ ID token ปกติในทุก request — ดูหัวข้อ 7
```

Firebase จะสร้างบัญชีให้ตาม uid ที่ backend กำหนดไว้ล่วงหน้า เครื่องผู้ป่วย
**ไม่ต้องสมัคร ไม่ต้องจำอีเมล ไม่ต้องตั้งรหัสผ่าน** และกรอกรหัสแค่ครั้งเดียวตลอดไป

## ข้อควรรู้

- รหัสรับได้ทั้งพิมพ์เล็ก มีขีด มีเว้นวรรค หรือมีช่องว่างท้าย — backend normalise ให้เอง
- ตัวอักษรในรหัสเลี่ยง `0 O 1 I L U` เพราะคนอ่านผิดบ่อย
- **รหัสผิด / หมดอายุ / ใช้ไปแล้ว ตอบ `404` เหมือนกันหมด** เจตนา — ถ้าตอบต่างกันเท่ากับ
  ยืนยันให้คนที่กำลังเดาว่ารหัสนี้มีอยู่จริง
- ถ้า sign in ไม่สำเร็จ **ให้ผู้ดูแลกดสร้างรหัสใหม่** อย่าให้ผู้ป่วยลองซ้ำ
- `POST /api/register` ยังอยู่ **สำหรับผู้ดูแล** ที่ sign in Firebase เองตามปกติ

ผู้ป่วยที่ไม่มี `caregiver_id` จะไม่มีวันได้รับ push — แต่เส้นทางนี้ตั้ง `caregiver_id` ให้เสมอ

# 3. หน้าตาของ push ที่จะได้รับ

### `notification`

| ฟิลด์ | ค่า |
|---|---|
| `title` | `PathGuard — เข้าเขตอันตราย` / `— ต้องการความช่วยเหลือ` / `— สัญญาณ GPS หาย` / `— พบการเดินหลง` |
| `body` | ข้อความจาก backend เช่น `Patient entered a danger zone — risk 91%.` |

### `data` — **ทุกค่าเป็น string** (ข้อบังคับของ FCM ต้อง parse เอง)

```json
{
  "alert_id": "42",
  "patient_id": "7",
  "alert_type": "geofence",
  "severity": "critical",
  "latitude": "13.77",
  "longitude": "100.555"
}
```

| ฟิลด์ | ใช้ทำอะไร |
|---|---|
| `patient_id` | เอาไปเปิดหน้าแผนที่ของผู้ป่วยคนนั้น |
| `latitude` / `longitude` | จุดที่เกิดเหตุ — **อาจเป็นสตริงว่าง `""`** ถ้า alert นั้นไม่มีพิกัด ต้องเช็คก่อน parse |
| `alert_type` | `geofence` (เข้าเขตอันตราย) · `emergency` (คะแนนสูง/เสี่ยงต่อเนื่อง) · `gps_loss` (สัญญาณหาย) · `sos` (ผู้ป่วยกดปุ่มเอง) · `trip_denied` (คำขอเดินทางถูกปฏิเสธ) · `wandering` |
| `severity` | `low` · `medium` · `high` · `critical` |

`android.priority = "high"` ตั้งไว้แล้วฝั่ง backend เพื่อให้ทะลุ Doze ของ Android

# 4. จะได้ push ถี่แค่ไหน

**อย่างมาก 1 ครั้งต่อ 10 นาที ต่อ `alert_type` ต่อผู้ป่วย 1 คน**

ตาราง `alerts` ยังเขียนทุกรอบที่เข้าเงื่อนไข (รอบละ 60 วิ ตอน GPS เข้า) เพราะมันคือประวัติ
ที่หน้า timeline ต้องใช้ แต่การ *ส่ง* ถูกจำกัดแยกต่างหาก — ยายที่นั่งอยู่ในเขตอันตราย 1 ชั่วโมง
ได้ alert 60 แถว แต่ได้ push 6 ครั้ง ไม่ใช่ 60

`alert_type` ต่างชนิดไม่กด cooldown ของกันและกัน — GPS หายตอนที่เพิ่งส่ง geofence ไป
30 วินาทีก่อน ยังส่งได้ตามปกติ

ค่า 10 นาทีนี้อยู่ในตาราง `risk_thresholds` ชื่อ `push_cooldown_seconds` แก้ได้ตอนรันโดยไม่ต้อง deploy
(อ้างอิง MOPH ED Triage 2561 Level 1-2 = แทรกแซงใน 0–10 นาที)

**ยกเว้น `sos` ซึ่งใช้ค่าของตัวเอง = 60 วินาที** (`sos_cooldown_seconds`) เพราะการกดปุ่มซ้ำ
คือคนกดอีกครั้ง ไม่ใช่เงื่อนไขเดิมที่ยังค้างอยู่ — ดูหัวข้อ 8

# 5. เกณฑ์ที่ทำให้เกิด alert (ไม่ได้เปลี่ยน)

ทั้งหมดมาจาก MOPH ED Triage 2561 ที่เก็บใน rule KB — backend ไม่ได้ตั้งเกณฑ์ใหม่เพื่อ push

| เกิด alert เมื่อ | ผลลัพธ์ |
|---|---|
| อยู่ในเขตอันตราย | `geofence` · `critical` · ทันที |
| คะแนน > 80 | `emergency` · `high` · ทันที |
| คะแนน ≥ 50 ติดกัน 5 รอบ | `emergency` · `high` · reason `sustained_risk` |
| ไม่มี GPS เกิน 10 นาที | `gps_loss` · `high` |
| **ผู้ป่วยกดปุ่ม SOS** | `sos` · `critical` · ทันที **ไม่ผ่านการให้คะแนนเลย** (หัวข้อ 8) |

> ⚠️ **สิ่งที่ต้องรู้:** เดินหลงห่างบ้าน 2 กม. วัดได้ **63.5 = medium ไม่ถึง 80** เคสเดินหลงจริง
> จึงมาทางกฎ "5 รอบติด" เสมอ = ~5 นาทีหลังเริ่มหลง ไม่ใช่ทันที

# 6. หลังกด push แล้วดึงอะไรต่อ

push พาไปหน้าแผนที่ได้ แต่ payload มีแค่จุดที่เกิดเหตุจุดเดียว หน้าจอต้องการเส้นทาง
และประวัติ — สองอันนี้คือที่มา

> ทั้งคู่ย้ายมาจาก `/demo/track` และ `/demo/alerts` ใน `demo_server.py` ที่ dashboard
> ใช้อยู่แล้ว **ไม่ใช่ของปลอมและไม่ได้เขียนใหม่** — dashboard ตอนนี้เรียก endpoint
> เดียวกับที่มือถือเรียก

## `GET /api/patients/{patient_id}/track?hours=6`

| พารามิเตอร์ | ค่า |
|---|---|
| `hours` | 1–720 · default 6 |

```json
{
  "patient_id": 7,
  "count": 240,
  "points": [
    {
      "latitude": 13.7563,
      "longitude": 100.5018,
      "recorded_at": "2026-08-22T09:14:03.120000+00:00",
      "speed": 1.1,
      "synthetic_injected": false
    }
  ]
}
```

- **เรียงเก่า → ใหม่** วาด polyline ได้เลยไม่ต้อง sort
- ชื่อฟิลด์ตรงกับ `POST /api/gps` ที่แอปส่งอยู่แล้ว ใช้ model ตัวเดียวกันได้
- `speed` เป็น `null` ได้ (มือถือไม่ได้ส่งมา)
- `synthetic_injected: true` = จุดที่สคริปต์เดโมใส่เข้าไป ข้อมูลผู้ป่วยจริงเป็น `false` เสมอ
- **ถ้าในช่วง `hours` มีไม่ถึง 2 จุด จะคืน 300 จุดล่าสุดแทน** ตั้งใจให้เป็นแบบนี้ —
  มือถือที่ปิดมาตั้งแต่เช้าไม่ควรทำให้แผนที่ว่างเปล่า เพราะจอว่างอ่านว่า "ยายไม่ได้ไปไหน"
  ทั้งที่ความจริงคือ "ไม่มีข้อมูลช่วงนี้" — ให้ดูที่ `recorded_at` ของจุดสุดท้ายเสมอ

## `GET /api/patients/{patient_id}/alerts?limit=20`

| พารามิเตอร์ | ค่า |
|---|---|
| `limit` | 1–200 · default 20 |

```json
{
  "patient_id": 7,
  "count": 2,
  "alerts": [
    {
      "id": 101,
      "patient_id": 7,
      "alert_type": "geofence",
      "severity": "critical",
      "message": "Patient entered a danger zone — risk 86.8%.",
      "latitude": 13.77,
      "longitude": 100.555,
      "resolved": false,
      "created_at": "2026-08-22T04:01:30.247575+00:00"
    }
  ]
}
```

**ใหม่สุดขึ้นก่อน** และ **จำนวนแถวจะเยอะกว่าจำนวน push มาก** — ตารางนี้เขียนทุกรอบที่
เข้าเงื่อนไข (ดูหัวข้อ 4) ยายอยู่ในเขตอันตราย 1 ชั่วโมงจะได้ 60 แถว แต่ push 6 ครั้ง
ถ้าจะทำ timeline ให้อ่านง่าย แนะนำให้ยุบแถวที่ `alert_type` เดียวกันติดกันเป็นก้อนเดียว
ฝั่งแอป

## `PATCH /api/alerts/{alert_id}`

```json
{ "resolved": true }
```

คืน alert ที่อัปเดตแล้ว (หน้าตาเหมือนใน list) · `404` ถ้าไม่มี alert นั้น

**ย้อนกลับได้** ส่ง `{"resolved": false}` เพื่อยกเลิก — ตั้งใจให้กดผิดแล้วแก้ได้
`resolved_at` ถูกเซ็ต/ล้างให้อัตโนมัติ ไม่ต้องส่งมา

> ก่อนหน้านี้คอลัมน์ `resolved` มีมาตั้งแต่สร้างตารางแต่ไม่มีใครเขียนเลย — แปลว่า
> "เจอยายแล้ว" ไม่มีที่อยู่ในระบบ นี่คือที่ของมัน

## `404` ทั้งสอง endpoint ถ้า `patient_id` ไม่มีในตาราง `users`

ตั้งใจให้ 404 ไม่ใช่คืน list ว่าง เพราะ list ว่างอ่านว่า "ยังไม่มีอะไรเกิดขึ้น"
ทั้งที่ความจริงคือ "ส่ง id ผิด"

# 7. Auth — เตรียมโค้ดไว้ แต่ยังไม่เปิด

**ตอนนี้ทุก endpoint ยังเปิดโล่ง ไม่ต้องส่ง token ก็เรียกได้** แต่โค้ดฝั่ง backend
เขียนและเทสต์ครบแล้ว เปิดได้ด้วย env ตัวเดียว (`AUTH_ENABLED=true`)

**เขียนแอปให้ส่ง token มาตั้งแต่ตอนนี้เลย** ตอนนี้ backend จะไม่สนใจมัน แต่วันที่เปิดสวิตช์
แอปจะไม่ต้องแก้อะไรเลย ถ้าไม่ทำ วันนั้นทุก request จะ 401 พร้อมกันหมด

> **เครื่องผู้ป่วยเอา ID token มาจากไหน** — จาก `signInWithCustomToken()` ในหัวข้อ 2
> ไม่ใช่จากการ sign in ด้วยอีเมล หลังจากนั้นมันคือ ID token ธรรมดาเหมือนของผู้ดูแลทุกประการ

## ต้องส่งอะไร

```
Authorization: Bearer <Firebase ID token>
```

เอามาจาก `FirebaseAuth.instance.currentUser?.getIdToken()` — **คนละตัวกับ FCM token**
ในหัวข้อ 1 · token หมดอายุทุก 1 ชั่วโมง Firebase SDK ต่ออายุให้เอง แต่ต้องเรียก
`getIdToken()` ใหม่ทุกครั้งที่ยิง อย่า cache ไว้เอง

ส่งทุก endpoint ยกเว้นไม่มี — รวมถึง `/api/register` ด้วย

## กฎที่ backend จะบังคับ

| กรณี | รหัส |
|---|---|
| ไม่ส่ง token / token ปลอม / หมดอายุ | `401` + header `WWW-Authenticate: Bearer` |
| token ใช้ได้ แต่ยังไม่เคย `POST /api/register` | `403` `signed in but not registered` |
| ขอข้อมูลคนไข้ที่ไม่ใช่ของตัวเอง | `403` `not your patient` |
| `POST /api/gps` ในนามคนไข้อื่น | `403` |
| `POST /api/devices/token` ด้วย `user_id` ของคนอื่น | `403` |
| `POST /api/register` ด้วย `firebase_uid` ไม่ตรงกับ token | `403` |

**ใครดูข้อมูลคนไข้ได้บ้าง:** ตัวคนไข้เอง กับผู้ดูแลที่อยู่ใน `users.caregiver_id`
ของคนไข้คนนั้นเท่านั้น ผู้ดูแลคนอื่นได้ `403` (ไม่ใช่ `404` — ตั้งใจ ไม่โกหกว่าไม่มีคนไข้คนนี้)

## ที่แอปควรทำ

- เจอ `401` → ขอ token ใหม่แล้วลองอีกครั้ง 1 รอบ ถ้ายัง 401 → พาไปหน้า sign-in
- เจอ `403 signed in but not registered` → เรียก `/api/register` แล้วลองใหม่
- เจอ `403 not your patient` → นี่คือบั๊กฝั่งแอป (ส่ง `patient_id` ผิด) อย่า retry

# 8. ปุ่ม SOS — `POST /api/sos`

**เพิ่ม 2026-08-26** หลังคนที่ 1 ถามว่าปุ่มใน `navigation_screen.dart` ควรยิงไปไหน
คำตอบคือ endpoint ของตัวเอง **ไม่ใช่ `POST /api/gps` + flag**

## ทำไมไม่ใช้ GPS + flag

| ปัญหา | รายละเอียด |
|---|---|
| จะโดน throttle กลืน | `POST /api/gps` คำนวณ risk แค่ **1 ครั้ง/60 วินาที/คนไข้** กดตอนวินาทีที่ 20 หลังรอบล่าสุด = ไม่มีการคำนวณ = ไม่มี alert = ปุ่มเงียบ |
| เครื่องกฎจะตัดสินแทนคน | alert เกิดเมื่อ `decide_emergency` บอกว่าเข้าเกณฑ์ กดปุ่มขณะยืนอยู่ในบ้าน คะแนน ≈ 16.5 = `low` = **ไม่ยิงอะไรเลย** ปุ่มจะตายเงียบตรงที่ที่คนไข้อยู่บ่อยที่สุด |
| `batch` เรียงตาม `recorded_at` | SOS ที่ค้างในคิว offline จะถูกเล่นย้อนหลังเหมือนเพิ่งเกิด |

endpoint นี้จึง **ข้ามการให้คะแนนทั้งหมด** — เขียน alert แล้ว push แล้วตอบ
คนไข้คือผู้มีอำนาจตัดสินว่าคนไข้ต้องการความช่วยเหลือหรือไม่ ไม่ต้องให้ AI เห็นชอบ

## Request

```json
POST /api/sos
Content-Type: application/json
Authorization: Bearer <Firebase ID token>

{
  "patient_id": 1,
  "latitude": 13.7563,
  "longitude": 100.5018
}
```

| ฟิลด์ | ชนิด | บังคับ | หมายเหตุ |
|---|---|---|---|
| `patient_id` | int | ✅ | `users.id` ของ **ผู้ป่วย** (จาก `/api/register`) ไม่ใช่ Firebase UID |
| `latitude` | float \| null | — | ตำแหน่งตอนกด ถ้าส่งมาจะใช้ค่านี้ก่อน |
| `longitude` | float \| null | — | เหมือนกัน |

**ส่งพิกัดมาด้วยถ้ามี** ถ้าไม่ส่ง (หรือส่ง `null`) backend จะใช้จุด GPS ล่าสุดที่มีในฐานข้อมูล
ถ้าไม่มีเลยก็ยังยิง alert อยู่ดี แค่ไม่มีพิกัด — **ห้ามรอ GPS fix ก่อนยิง SOS**
เพราะที่ที่ GPS จับไม่ได้ (ในอาคาร ใต้ดิน ชิปเย็น) คือที่ที่คนไข้หลงง่ายที่สุดพอดี

## Response `201`

```json
{
  "alert_id": 42,
  "patient_id": 1,
  "severity": "critical",
  "latitude": 13.7563,
  "longitude": 100.5018,
  "push": "sent"
}
```

`push` บอกว่าเกิดอะไรขึ้นกับการส่งจริง ใช้ตัดสินใจว่าจะแสดงอะไรบนหน้าจอได้

| `push` | แปลว่า | แอปควรทำ |
|---|---|---|
| `sent` | ผู้ดูแลได้รับแล้ว | ✅ ขึ้น "แจ้งผู้ดูแลแล้ว" |
| `cooldown` | กดซ้ำภายใน 60 วิ ไม่ได้ส่งซ้ำ | ✅ ยังถือว่าสำเร็จ — ผู้ดูแลได้รับไปแล้วเมื่อครู่ |
| `no_caregiver` | ผู้ดูแลยังไม่ได้ลงทะเบียนเครื่อง | ⚠️ **ต้องบอกผู้ใช้ตรงๆ** ว่าส่งไม่ถึง |
| `failed` / `error` | FCM ล่ม | ⚠️ เหมือนกัน |

> **สำคัญ: `201` ไม่ได้แปลว่าผู้ดูแลได้รับ** มันแปลว่า alert ถูกบันทึกแล้ว
> ต้องดู `push` ถึงจะรู้ว่าถึงมือหรือยัง อย่าขึ้นข้อความว่า "ส่งแล้ว" จากรหัส 201 อย่างเดียว
> เพราะถ้าผู้ดูแลยังไม่ลงทะเบียนเครื่อง คนไข้จะเชื่อว่ามีคนกำลังมาช่วย ทั้งที่ไม่มี

## ความถี่

**อย่างมาก 1 push ต่อ 60 วินาที ต่อผู้ป่วย** (`sos_cooldown_seconds` ใน `risk_thresholds`)
ไม่ใช่ 10 นาทีเหมือน alert อัตโนมัติ เพราะการกดซ้ำคือคนกดอีกครั้ง = ข้อมูลใหม่
แต่ก็ไม่ใช่ 0 เพราะพฤติกรรมกดซ้ำเป็นอาการ BPSD อย่างหนึ่ง — คนที่จะกด 30 ครั้งคือคนที่
ระบบนี้ทำมาเพื่อเขาพอดี และ 30 push = ผู้ดูแลปิดแจ้งเตือน

**ทุกครั้งที่กดเขียนแถวใน `alerts` เสมอ** ไม่ว่าจะ push หรือไม่ ดังนั้น
`GET /api/patients/{id}/alerts` (หัวข้อ 6) จะเห็นการกดครบทุกครั้ง

## Push ที่ผู้ดูแลจะเห็น

| | |
|---|---|
| `title` | `PathGuard — ผู้ป่วยกดขอความช่วยเหลือ` |
| `body` | `Patient pressed the SOS button.` |
| `data.alert_type` | `sos` |
| `data.severity` | `critical` |

`alert_type` เป็น `sos` ไม่ใช่ `emergency` **โดยตั้งใจ** — cooldown คีย์ด้วย
(`patient_id`, `alert_type`) ถ้าใช้ชื่อเดียวกัน alert อัตโนมัติที่เพิ่งส่งไปเมื่อ 3 นาทีก่อน
จะกลืนการกดปุ่มของคนไข้เงียบๆ ฝั่งแอปควรแยกหน้าตาของ `sos` ออกจาก alert อัตโนมัติด้วย
เพราะผู้ดูแลตัดสินใจต่างกันระหว่าง "แอปคิดว่ามีอะไรผิดปกติ" กับ "เขาขอความช่วยเหลือเอง"

## Error

| รหัส | เมื่อไหร่ |
|---|---|
| `404` | `patient_id` ไม่มีในตาราง `users` → ต้อง `POST /api/register` ก่อน |
| `403` | (ตอนเปิด auth) ยิง SOS ในนามคนไข้ที่ไม่ใช่ของตัวเอง |
| `422` | `latitude`/`longitude` นอกช่วง |

# 9. ขออนุมัติเดินทาง (Trip Approval — C-3)

> **สร้าง 2026-08-26** ตามรายงานหัวข้อ C-3 ใช้เฉพาะ **ผู้ป่วย Level 2** เท่านั้น
> Level 1 เดินทางเองได้ ไม่ต้องขอ

## ขั้นที่ 1 — เครื่องผู้ป่วยส่งคำขอ

```json
POST /api/trip-requests
{
  "patient_id": 42,
  "destination_name": "ตลาดใหม่",
  "latitude": 13.7585,
  "longitude": 100.5018
}
```

ตอบ `201`:

```json
{
  "id": 7,
  "patient_id": 42,
  "destination_name": "ตลาดใหม่",
  "latitude": 13.7585,
  "longitude": 100.5018,
  "status": "pending",
  "confidence": 0.8,
  "factors": { "familiarity": 0.8, "danger_zone": false },
  "nearest_place_name": "บ้าน",
  "nearest_place_distance_m": 100.0,
  "blocking_zone_name": null,
  "confidence_status": "ok",
  "created_at": "2026-08-26T09:15:00Z",
  "decided_at": null
}
```

**ถ้าผู้ป่วยเป็น Level 1** จะได้ `201` เหมือนกัน แต่ `status: "not_required"` และ
`id: null` — **ไม่มีการบันทึกแถว ให้แอปพาไปได้เลย** ไม่ต้องรอใคร ตั้งใจให้ไม่ใช่ error
เพราะแอปไม่ควรต้องรู้กฎนี้เอง

## ขั้นที่ 2 — ผู้ดูแลดูคำขอ

```
GET /api/patients/{patient_id}/trip-requests?status=pending&limit=20
```

เรียงใหม่สุดก่อน `status` กรองได้ด้วย `pending` / `approved` / `rejected`

## ขั้นที่ 3 — ผู้ดูแลตัดสิน

```json
PATCH /api/trip-requests/7
{ "decision": "approve" }      // หรือ "reject"
```

ตอบ `200`:

```json
{ "id": 7, "patient_id": 42, "status": "rejected",
  "decided_at": "2026-08-26T09:20:00Z",
  "alert_id": 91, "push": "skipped_self" }
```

## Confidence Score หมายความว่าอะไร

**ไม่ใช่ "โอกาสที่จะหลง"** แต่คือ **"ปลายทางนี้ใกล้ที่ที่ผู้ป่วยรู้จักแค่ไหน"** (0–1)

| ค่า | แปลว่า |
|---|---|
| `1.0` | ปลายทางอยู่ในรัศมีของหมุดที่ไปบ่อยที่สุด |
| `0.5–0.9` | อยู่ใกล้ที่ที่รู้จัก |
| `0.0` | ไกลเกิน `route_deviation_ceiling_m` (500 ม.) จากที่ที่รู้จักทุกแห่ง **หรือ** อยู่ในเขตอันตราย |

**`danger_zone: true` คือการวีโต้ ไม่ใช่การหักคะแนน** — ปลายทางในเขตอันตรายได้ `0.0`
เสมอ ต่อให้เป็นบ้านตัวเอง ให้แอปแสดง `blocking_zone_name` ให้ผู้ดูแลเห็นชัดๆ

**`confidence_status: "no_profile"`** = ผู้ป่วยยังไม่มีหมุดสักที่ จึงเทียบกับอะไรไม่ได้
**อย่าแสดงเป็น 0%** เพราะมันคนละความหมายกับ "มั่นใจว่าไม่ควรไป"

## เรื่องที่ต่างจากรายงาน — ตั้งใจ

รายงานเขียนว่าเมื่อปฏิเสธ *"ระบบจะส่ง SOS ให้ผู้ดูแลทุกคนอัตโนมัติ"* ทำจริงต่างสองจุด:

1. **`alert_type` เป็น `trip_denied` ไม่ใช่ `sos`** — cooldown ของ push คีย์ด้วย
   (`patient_id`, `alert_type`) ถ้าใช้ชื่อเดียวกัน คำขอที่ถูกปฏิเสธจะกลืนการกดปุ่ม SOS จริง
   ของผู้ป่วยไป 10 นาที และผู้ดูแลก็ตัดสินใจต่างกันระหว่างสองเรื่องนี้
2. **"ผู้ดูแลทุกคน" ตอนนี้คือคนเดียว** และเป็นคนที่เพิ่งกดปฏิเสธเอง จึง**ข้าม push**
   (`push: "skipped_self"`) แต่**ยังเขียนแถว alert เสมอ** เพื่อให้ timeline และ dashboard
   เห็น พอรองรับผู้ดูแลหลายคนเมื่อไหร่ มันจะเริ่ม push ให้คนอื่นเองโดยไม่ต้องแก้โค้ด

## Error

| รหัส | เมื่อไหร่ |
|---|---|
| `404` | `patient_id` หรือ `request_id` ไม่มีจริง |
| `409` | ตัดสินคำขอที่ตัดสินไปแล้ว — ไม่ทับของเดิม เพราะครอบครัวอาจลงมือตามคำตอบแรกไปแล้ว |
| `422` | `decision` ไม่ใช่ `approve`/`reject` หรือพิกัดนอกช่วง |

# 10. หมุดสถานที่ (`places`) — "สถานที่ปลอดภัย" ที่หน้าจอเพิ่มผู้ป่วยเก็บ

> **เพิ่ม 2026-08-26** endpoint นี้มีมาตั้งแต่ 2026-08-20 แล้ว แต่ไปอยู่ใน
> `API_CONTRACT_ADMIN.md` ซึ่งไม่เคยส่งให้คนที่ 1 — หน้าจอเลยเก็บ "สถานที่ปลอดภัย"
> ไว้โดยไม่มีที่ส่ง หัวข้อนี้ปิดช่องนั้น

## ⚠️ อ่านก่อน — ปักแค่บ้านจุดเดียว **ไม่พอ** (วัดมาแล้ว)

รันผ่าน Module 3 ของจริงด้วยน้ำหนักที่ seed ไว้ ทุกอย่างคงที่ เปลี่ยนแค่ชุดหมุด:

| ผู้ป่วยอยู่ตรงไหน | ปักแค่บ้าน | ปักครบ 4 ที่ประจำ |
|---|---|---|
| อยู่บ้าน | 9.0 low | 9.0 low |
| **วัดที่ไปทุกวัน** | **56.0 medium** | 15.0 low |
| **ตลาดที่ไปทุกวัน** | **56.0 medium** | 15.0 low |
| **บ้านลูกสาว** | **56.0 medium** | 18.0 low |
| ห่างบ้าน 2.5 กม. หลงจริง | 56.0 medium | 56.0 medium |

ถ้าปักแค่บ้าน ค่า `familiarity` จะเป็น 0.000 ทุกที่ยกเว้นบ้าน แปลว่า
**ระบบแยก "อยู่ที่วัดที่ไปทุกวัน" กับ "หลงห่างบ้าน 2.5 กม." ไม่ออก — ได้ 56.0 medium เท่ากัน**

แย่กว่านั้น: กฎ sustained (คะแนน ≥50 ติดกัน 5 รอบ ที่ throttle 60 วิ) แปลว่า
**ครอบครัวจะโดน push หลังผู้ป่วยอยู่ที่วัดราว 5 นาที ทุกครั้งที่ไป** นี่คือ alert fatigue
แบบเดียวกับที่แผนตั้งใจเลี่ยงตอนปฏิเสธ "push ตั้งแต่ medium แรก"

**หมุดที่ขาดไปไม่ใช่ความแม่นที่หายไปนิดหน่อย แต่คือ false alarm ทุกครั้งที่ผู้ป่วยไปที่นั่น**

👉 **UI ควรบังคับ/ชวนให้ผู้ดูแลปักที่ประจำให้ครบก่อนเริ่มติดตาม** ไม่ใช่แค่บ้าน
อย่างน้อยควรมี: บ้าน · วัด/มัสยิด · ตลาด · บ้านญาติที่ไปบ่อย

## ขั้นที่ 1 — หน้าจอเพิ่มผู้ป่วย: ส่งบ้านจุดเดียว

```json
PUT /api/patients/42/places/home
{ "place_name": "บ้าน", "latitude": 13.7563, "longitude": 100.5018 }
```

| ฟิลด์ | จำเป็น | หมายเหตุ |
|---|---|---|
| `place_name` | ✅ | 1–255 ตัวอักษร ผู้ดูแลตั้งเอง — **ชื่อต้องมาจากคน** ระบบตั้งชื่อสถานที่เองไม่ได้ |
| `latitude` / `longitude` | ✅ | −90..90 / −180..180 |
| `radius_m` | ⬜ | 20–5000 · ค่าเริ่มต้น **150** (ขนาดบ้านหลังหนึ่ง) ถ้าเป็นวัด/ตลาด/โรงพยาบาลต้องใส่ให้ใหญ่กว่านี้ ไม่งั้นแค่เดินข้ามลานก็นับว่าออกนอกที่คุ้นเคย |

**ไม่ต้องส่ง `visit_rank` / `stay_rank`** — บ้านคือ `daily_live` + `all_day` โดยนิยาม
backend ใส่ให้เอง (บ้านที่ถูกปักเป็น `rare` จะทำให้ระบบอ่านว่าผู้ป่วยเป็นคนแปลกหน้าในบ้านตัวเอง)

ตอบ `200` = ชุดหมุดทั้งหมดหลังแก้:

```json
{
  "patient_id": 42,
  "count": 3,
  "places": [
    { "cluster_id": 0, "place_name": "บ้าน", "latitude": 13.7563, "longitude": 100.5018,
      "visit_rank": "daily_live", "stay_rank": "all_day", "radius_m": 150,
      "source": "manual", "is_home": true },
    { "cluster_id": 1, "place_name": "ตลาด", "...": "..." , "is_home": false },
    { "cluster_id": 2, "place_name": "unnamed", "latitude": 13.8, "longitude": 100.6,
      "visit_rank": null, "stay_rank": null, "radius_m": null,
      "source": "learned", "is_home": false }
  ]
}
```

**`PUT` นี้ลบหมุดอื่นไม่ได้เลย** — เรียกซ้ำกี่ครั้งก็ทับเฉพาะบ้าน เรียกได้ทุกครั้งที่ผู้ดูแลแก้ที่อยู่

* `source: "learned"` = สถานที่ที่ Module 1 เดาเอง **ไม่มีชื่อ** (`"unnamed"`) และ `visit_rank`/`stay_rank`/`radius_m` เป็น `null`
  → แสดงแบบอ่านอย่างเดียว หรือไม่แสดงเลยก็ได้
* `is_home` มีได้ `true` แค่หมุดเดียวต่อผู้ป่วยหนึ่งคนเสมอ

### 🛑 endpoint นี้ **ทับหมุดเดิมทั้งชุด**

ส่ง 1 หมุด = เหลือ 1 หมุด อีก 3 หายเงียบ ๆ พร้อม `201` ไม่มี error
**ต้อง `GET` มาก่อน แก้ในมือ แล้วส่งกลับทั้งชุดเสมอ** ถ้าจะแก้แค่บ้าน ให้ใช้ `PUT .../places/home` ข้างบนแทน

* **`places[0]` คือบ้านเสมอ** — backend ตั้ง `is_home` ให้ตัวแรกของชุด
* **ส่ง `places: []` ไม่ได้ (422)** ตั้งใจ: 0 หมุด = ระบบตกกลับ partial mode ซึ่งวัดแล้วว่า
  ผู้ป่วยนั่งอยู่บ้านกับหลงห่างบ้าน 2.5 กม. ได้ 18.8 low เท่ากันทั้งคู่ แยกไม่ออก
  ถ้าจะแก้หมุดผิด ให้ส่งชุดที่ถูกทับไปเลย
* สูงสุด **50 หมุด**

### `visit_rank` — เลือกจาก dropdown เท่านั้น ห้ามให้ผู้ดูแลพิมพ์ตัวเลข

| ค่า | ข้อความที่ควรขึ้นบน UI |
|---|---|
| `daily_live` | อยู่/นอนที่นี่ |
| `most_days` | ไปเกือบทุกวัน |
| `weekly` | ไปสัปดาห์ละครั้ง |
| `rare` | นาน ๆ ไปที |

### `stay_rank`

| ค่า | ข้อความที่ควรขึ้นบน UI |
|---|---|
| `all_day` | อยู่ทั้งวัน |
| `few_hours` | หลายชั่วโมง |
| `about_hour` | ราวหนึ่งชั่วโมง |
| `brief` | แป๊บเดียว |

ที่ API ไม่รับตัวเลขตรง ๆ เพราะ `familiarity` เป็นค่า**เปรียบเทียบ** (หารด้วยค่ามากสุดในชุด)
ถ้าผู้ดูแลใส่เลขใกล้ ๆ กันทุกที่ ทุกที่จะคุ้นเคยเท่ากันหมด แล้วระบบจะเลิกเตือนไปเฉย ๆ

## ขั้นที่ 3 — อ่านกลับมาแสดง

```
GET /api/patients/42/places
```

ตอบ `200` รูปแบบเดียวกับข้างบน (`patient_id` / `places` / `count`)

## Error

| รหัส | เมื่อไหร่ |
|---|---|
| `404` | `patient_id` ไม่มีในตาราง `users` — ต้องสร้างผู้ป่วยก่อน (หัวข้อ 2) |
| `422` | พิกัดนอกช่วง · `visit_rank`/`stay_rank` ไม่อยู่ในลิสต์ · `places: []` · เกิน 50 หมุด |

ทั้ง 3 endpoint อยู่ใต้ auth เดียวกับที่เหลือ — ส่ง `Authorization: Bearer` ตามหัวข้อ 7

> เขตอันตราย (`danger_zones`) เป็นคนละเรื่องและยังไม่มีในหน้าจอฝั่งแอป
> ถ้าจะทำ ค่อยคุยกัน — สเปกอยู่ใน `API_CONTRACT_ADMIN.md`
