# ส่วนที่ 1 — ของใหม่ที่ขึ้น `main` แล้ว ใช้ได้เลย

## 1.1 `GET /api/patients/{patient_id}` — เครื่องผู้ป่วยอ่านระดับของตัวเองได้แล้ว

```
GET /api/patients/42
```
```json
{ "patient_id": 42, "name": "ยาย", "severity_level": 2 }
```

| รหัส | แปลว่า |
|---|---|
| `200` | ปกติ |
| `403` | ไม่ใช่ผู้ป่วยของคุณ (เฉพาะตอนเปิดระบบยืนยันตัวตนแล้ว) |
| `404` | ไม่มี `patient_id` นี้ |

`severity_level`: `1` = ระยะต้น · `2` = ระยะกลาง · `null` = ผู้ดูแลไม่ได้ระบุ
**อย่า default เป็น 1 เมื่อเจอ `null`** ให้ถามผู้ดูแลแทน

**ทำไมเพิ่งมี:** ก่อนหน้านี้ `severity_level` ออกจาก backend ทางเดียวคือ response ของ
`POST /api/patients` ซึ่งเป็นการเรียกของ**ผู้ดูแล** บนเครื่องผู้ดูแล ส่วนเครื่องผู้ป่วยได้แค่
`patient_id` กับ token จาก `/api/pair` ซึ่งเรียกครั้งเดียวตลอดชีวิตเครื่อง
**เครื่องผู้ป่วยจึงไม่มีทางรู้ระดับของตัวเองเลย** — น่าจะเป็นเหตุผลที่บอกว่าหน้า Level 2
"ทำไว้แล้วแต่ยังไม่มีทางเข้าถึง" หน้าจอมี แต่ไม่มีข้อมูลมาตัดสินว่าจะพาใครไปหน้าไหน

**ผู้ดูแลแก้ระดับทีหลัง** (รหัสจับคู่ใช้ได้ครั้งเดียว)

## 1.3 `GET /api/recommendation/{id}` — เพิ่ม `place_name` แล้ว เลิก mock ได้

```
GET /api/recommendation/42
GET /api/recommendation/42?lat=13.7563&lng=100.5018   ← ไม่ส่งก็ได้
```
```json
{
  "patient_id": 42,
  "status": "ok",
  "flags": { "time_match_available": true, "location_used": true },
  "recommendations": [
    {
      "rank": 1,
      "cluster_id": 0,
      "place_name": "บ้าน",
      "latitude": 13.7563, "longitude": 100.5018,
      "confidence": 0.9123,
      "confidence_pct": 91,
      "factors": { "frequency": 1.0, "proximity": 0.98, "familiarity": 1.0, "time_match": 0.8 }
    }
  ]
}
```

* **`place_name` คือชื่อที่ผู้ดูแลตั้งตอนปักหมุด — เอาขึ้นปุ่มตัวนี้**
  เป็น `null` ได้เมื่อสถานที่นั้นมาจากการเรียนรู้ของระบบ (อัลกอริทึมตั้งชื่อไม่ได้)
  **อย่าแสดงว่า "ไม่ทราบ" ให้ซ่อนปุ่มนั้นไปเลย** ผู้ป่วยแยกไม่ออกว่าปุ่มชื่อ "ไม่ทราบ" คืออะไร
* **จำนวนไม่ต้องส่งพารามิเตอร์** — เซิร์ฟเวอร์อ่าน `severity_level` เอง: Level 1 ได้ 3 · Level 2 ได้ 5 · ไม่ระบุได้ 3
* `cluster_id` **เปลี่ยนได้ทุกครั้งที่ผู้ดูแลแก้ชุดหมุด** อย่าเก็บถาวร
* `status: "no_profile"` + `recommendations: []` = ผู้ป่วยยังไม่มีหมุดสักที่
  **ต้องรองรับ** เพราะผู้ป่วยที่เพิ่งสร้างเป็นแบบนี้ทุกคน — ขึ้นข้อความชวนผู้ดูแลไปปักหมุด อย่าขึ้นหน้าจอว่าง

> **ขอโทษด้วยเรื่องนี้:** endpoint นี้ใช้ได้มาหลายสัปดาห์แล้วแต่ไม่เคยอยู่ในสัญญาฉบับไหนเลย
> และตอนไปนั่งเขียนสัญญาให้มันเมื่อวาน **เพิ่งพบว่ามันไม่คืน `place_name`** คืนแค่พิกัด
> ซึ่งแปลว่าเอาขึ้นหน้าจอผู้ป่วยไม่ได้เลย แก้แล้ว

## 1.4 หัวข้อ 11 ใหม่ในสัญญา — 4 endpoint ที่เราลืมเขียน

`GET /api/recommendation/{id}` · `POST /api/gps/batch` · `GET /api/risk/{id}` · `GET /api/search-area/{id}`

### 🛑 อ่านกล่องนี้ก่อนต่อโค้ด: สองตัวเป็น `GET` ที่เขียนข้อมูลและยิง push

**`GET /api/risk/{id}`** — ทุกครั้งที่เรียก เซิร์ฟเวอร์จะคิดคะแนนใหม่ · บันทึกแถวลงฐานข้อมูล ·
และถ้าเข้าเกณฑ์ก็**เขียน alert แล้วยิง push เข้ามือถือผู้ดูแล**

**`GET /api/search-area/{id}`** — จำลองเส้นทาง 10,000 เส้น + คำนวณ KDE ตอบกลับมี cell
ราว 2,500 จุด และ**ถ้า GPS ขาดจริงจะเขียน alert แล้วยิง push**

**ห้าม poll ทั้งสองตัว** ปกติแอปไม่ต้องเรียก `/api/risk` เลย — `POST /api/gps` สั่งให้คิดเองอยู่แล้ว
ทุก 60 วินาที เรียกเมื่อผู้ใช้กดดูจริง ๆ เท่านั้น
ผิดปกติที่เป็น `GET` แต่เปลี่ยน verb ตอนนี้จะพังของที่ต่อไปแล้ว จึงเขียนเตือนไว้แทน

### `POST /api/gps/batch` — คิวตอนเน็ตหลุด

```json
{ "points": [
    { "patient_id": 42, "latitude": 13.7563, "longitude": 100.5018,
      "recorded_at": "2026-08-27T09:00:00Z", "accuracy": 12.0, "speed": 1.2 }
] }
```
* สูงสุด **500 จุดต่อครั้ง** · **ทุกจุดต้องเป็นผู้ป่วยคนเดียวกัน** · เกินหรือปนกัน = `422`
* **ไม่ต้องเรียงก่อนส่ง** เซิร์ฟเวอร์เรียงตาม `recorded_at` ให้เอง
* `speed` ไม่มีให้ส่ง `null` **อย่าส่ง `0.0`** — `0.0` แปลว่า "ยืนนิ่ง" คนละเรื่องกับ "ไม่รู้"
* `recorded_at` คือ**เวลาที่เครื่องอ่านค่าได้ ไม่ใช่เวลาที่ส่ง** UTC ISO ลงท้าย `Z`
* **ลบออกจากคิวเมื่อได้ `200` เท่านั้น** ไม่แน่ใจว่าถึงไหม ส่งซ้ำดีกว่าทิ้ง

รายละเอียดเต็มทั้ง 4 ตัวอยู่ในสัญญาหัวข้อ 11

# ส่วนที่ 2 — คำถาม 4 ข้อ ตอบสั้น ๆ ได้เลย ไม่ต้องรอทำเสร็จ

## ❓ ข้อ 1 — ตอนนี้แอปส่ง `Authorization: Bearer <ID token>` ทุก request แล้วหรือยัง

**ข้อนี้บล็อกงานฝั่งเราอยู่จริง ๆ**

เราจะเปิดระบบยืนยันตัวตน (`AUTH_ENABLED`) แล้วเปิดทางให้มือถือยิงเข้ามาจากภายนอก
แต่**ถ้าเปิดตอนที่แอปยังไม่ส่ง header แอปจะ 401 ทั้งตัวพร้อมกัน**

เหตุที่ต้องเปิดก่อนเปิดทางเข้า: `patient_id` เป็นเลขจำนวนเต็มเรียงกัน 1, 2, 3 —
ถ้าเปิด URL สาธารณะโดยไม่มี auth **ใครก็ตามที่นับเลขเป็นก็อ่านตำแหน่งสดของผู้ป่วยสมองเสื่อมได้**

**ตอบว่า "ยัง" ก็ได้ครับ เราจะได้รอ ขอแค่รู้** — ถ้ายัง ให้เริ่มส่งได้เลยตั้งแต่ตอนนี้
เซิร์ฟเวอร์ยังไม่ตรวจ ส่งไปก็ไม่มีผลอะไร แต่วันที่เราเปิดจะไม่พังพร้อมกันทั้งแอป

## ❓ ข้อ 2 — หน้า Level 2 homepage คิดไว้ว่าหน้าตายังไง

ตอนนี้ backend ให้ **Level 2 เห็น 5 สถานที่ · Level 1 เห็น 3**
เหตุผลที่เขียนไว้ตอนสร้างคือ *"Level 2 ล็อกช่องค้นหา ตารางสถานที่จึงเป็นทางเดียวที่เขาจะไปไหนได้
ต้องมีให้ครบ"*

**นั่นเป็นการเดาหน้าจอที่ยังไม่มีใครสร้าง** ถ้าหน้าจริงไม่ใช่ตารางแบบนั้น เลข 5 ก็ไม่มีความหมาย
บอกมาได้เลยว่าคิดไว้ยังไง เราปรับให้ตรงก่อนที่ทั้งสองฝั่งจะเขียนไปคนละทาง

## ❓ ข้อ 3 — 🛑 ในรายงานมี 4 ฟีเจอร์ที่ backend ไม่ได้ทำ และเราไม่เคยบอกคุณ 2 ข้อ

เราไล่รายงานเทียบโค้ดทีละบรรทัด (ผลอยู่ที่ `backend/REPORT_VS_CODE.md` มีเลขบรรทัดอ้างอิงทุกข้อ)

| ฟีเจอร์ในรายงาน | สถานะจริงของ backend | เคยบอกกันหรือยัง |
|---|---|---|
| **Real-time Navigation** "เลี้ยวซ้าย อีก 80 ม." | ไม่มี — ไม่มี routing provider ใน backend เลย `route_prediction` ทำนายลำดับ *กลุ่มสถานที่* ไม่ใช่คำสั่งเลี้ยว | ✅ คุยแล้ว ยังไม่มีคำตอบ |
| **คำนวณเส้นทางกลับตอนออกนอกเส้นทาง** | ไม่มี — ใช้ routing ตัวเดียวกับข้อบน · การ**ตรวจจับ**ว่าออกนอกเส้นทางมีแล้วในรูปคะแนน (`route_deviation` น้ำหนัก 30%) ที่ไม่มีคือการ**นำทางกลับ** | ✅ คุยแล้ว ยังไม่มีคำตอบ |
| **นำทางไปสถานีตำรวจ/โรงเรียนใกล้สุด** | **ไม่มีเลย** ไม่มีตาราง POI ไม่มีรายการสถานที่ปลอดภัย (`danger_zones` เป็นแนวคิดตรงข้าม คือที่ที่ห้ามเข้า) | ❌ **ไม่เคยบอก** |
| **แจ้งผู้ดูแลทุกคน + จัดอันดับตามระยะทาง + กด "ฉันจะไปรับ"** | **ไม่มีเลย และโครงสร้างปัจจุบันทำไม่ได้** — ผู้ป่วย 1 คนมีผู้ดูแลได้ 1 คน (`users.caregiver_id` เป็น FK เดี่ยว) · ไม่มีที่เก็บ GPS ของ*ผู้ดูแล* จึงคำนวณระยะทางไม่ได้ · ไม่มี action "ฉันจะไปรับ" | ❌ **ไม่เคยบอก** |

**สองข้อบน — ข่าวดี** ตอนที่เราเขียนว่า "ทำไม่ได้เพราะไม่มีผู้ให้บริการเส้นทาง" ยังไม่รู้ว่า
**คุณต่อ Google Directions API ไปแล้วและได้เส้นทางเดินจริง** ตอนนี้มีแล้ว สองฟีเจอร์นั้น
**อาจทำได้ทั้งหมดฝั่งแอปโดยไม่ต้องแตะ backend เลย** — เราอัปเดต `REPORT_VS_CODE.md` แล้ว

**สองข้อล่าง — ต้องรู้กันก่อน** ถ้าจะเอาจริง**ต้องแก้ฐานข้อมูล ซึ่งเป็นงานฝั่งเรา และต้องเริ่มก่อน
ไม่ใช่ค่อยมาทำสัปดาห์สุดท้าย** ข้อสุดท้ายไม่ใช่แค่เพิ่ม endpoint — ต้องเปลี่ยนความสัมพันธ์

**ที่ถามเพราะเรื่องนี้เพิ่งเกิดไปรอบหนึ่งแล้ว** — **ปุ่ม SOS ถูกตัดออกจากแผนฝั่งเรา
แต่คุณสร้างปุ่มไว้ และไม่มีใครบอกกันเลย** จนคุณถามมาเองว่าให้ยิง endpoint ไหน
ตอนนั้นเราเลือกสร้าง SOS ให้แทนที่จะให้คุณลบปุ่มทิ้ง เพราะปุ่ม SOS ที่กดแล้วไม่เกิดอะไร
ในแอปสำหรับผู้ป่วยสมองเสื่อม แย่กว่าไม่มีปุ่มเลย — ไม่อยากให้เกิดซ้ำอีก


## ❓ ข้อ 4 — ขอบเขตงานฝั่งคุณ: ทำถึงไหนแล้ว และเส้นแบ่งอยู่ตรงไหน

ฝั่งเรารู้แค่สิ่งที่คุณบอกมาเป็นครั้ง ๆ ซึ่งที่ผ่านมามันไม่พอ — เราเพิ่งเจอว่าคุณสร้างปุ่ม SOS
ที่แผนเราตัดไปแล้ว และสร้างหน้า navigation ที่ backend ไม่มีข้อมูลจะป้อนให้
ทั้งสองอย่างเรารู้ทีหลังทั้งคู่ **ไม่ใช่ความผิดใคร แต่เป็นช่องว่างที่ต้องปิด**

ขอภาพรวมสักครั้ง ไม่ต้องละเอียด รูปแบบนี้ก็พอ:

| หน้าจอ / ฟีเจอร์ | สถานะ | หมายเหตุ |
|---|---|---|
| เช่น: หน้าล็อกอินผู้ป่วย (กรอกรหัสจับคู่) | เสร็จ / กำลังทำ / ยังไม่เริ่ม / ไม่ทำ | ต่อ API จริงหรือยัง mock อยู่ |
| … | | |

**สิ่งที่อยากรู้เป็นพิเศษ**

1. **หน้าจอไหนที่ยัง mock ข้อมูลอยู่** — เราจะได้รู้ว่ามี endpoint ไหนที่คุณรออยู่แต่เราไม่รู้
   (`recommendedPlaces` คือกรณีแบบนี้พอดี — คุณ mock อยู่หลายสัปดาห์เพราะ endpoint หลุดจากสัญญา)
2. **มีอะไรที่คุณสร้างไปแล้วโดยคิดว่า backend มีให้** แต่ยังไม่เคยยิงจริง
   ถ้ามี บอกมาเลย ดีกว่ามาเจอตอนต่อจริงแล้วไม่มี
3. **มีอะไรที่คุณคิดว่าเป็นงานฝั่งเรา** และรออยู่ — ถ้าไม่ตรงกับที่เรารู้ ตอนนี้คือเวลาที่ถูกที่จะบอก
4. **จะทำถึงไหนภายในกำหนด** อะไรที่ตั้งใจตัดทิ้งบ้าง — ของที่ตัดต้องรู้กันสองฝ่าย
   เพราะถ้าฝ่ายหนึ่งตัดแล้วอีกฝ่ายไม่รู้ ก็จะเป็นเคส SOS ซ้ำอีก

**ตอบเป็นข้อความธรรมดาก็ได้ ไม่ต้องทำตาราง** ขอแค่ครบ 4 ข้อนี้

# 📌 ถึง AI ที่กำลังช่วยคนที่ 1 อ่านไฟล์นี้

ไฟล์นี้เขียนโดย AI ที่ช่วยทีม backend อยู่ ทั้งสองฝั่งจะได้เข้าใจตรงกัน
ถ้าคุณกำลังอ่านให้คนที่ 1 ฟัง มีสามอย่างที่ขอ

## 1. อย่าตอบคำถามในส่วนที่ 2 แทนเขา — ให้ถามเขา

คำถามทั้ง 4 ข้อ **ตอบจากการอ่านโค้ดไม่ได้** เพราะมันถามถึงความตั้งใจและแผนของคนทำ
ไม่ใช่สถานะของไฟล์ ที่สำคัญคือข้อ 3 กับข้อ 4 — คำตอบจะกำหนดว่าฝั่ง backend
ต้องแก้ฐานข้อมูลหรือเปล่า ซึ่งเป็นงานที่ต้องเริ่มก่อน ไม่ใช่ค่อยทำสัปดาห์สุดท้าย

**ถ้าเขายังไม่ตอบ ให้ถามซ้ำ อย่าเดาแทน** และถ้าเขาตอบว่า "ไม่รู้" หรือ "ยังไม่ได้คิด"
ให้ส่งกลับมาแบบนั้นตรง ๆ — "ยังไม่ได้คิด" เป็นคำตอบที่ใช้งานได้ ส่วนคำตอบที่เดาขึ้นมาไม่ใช่

## 2. เรื่องที่ตรวจได้จากโค้ดของเขา ช่วยตรวจให้เลย

สองข้อนี้ดูจากโปรเจกต์ Flutter ได้เอง ไม่ต้องรบกวนเขา:

* **แอปแนบ `Authorization: Bearer <ID token>` ในทุก request หรือยัง** (คำถามข้อ 1)
  ดูที่ interceptor / `http` client ที่ใช้ยิง API ถ้ายังไม่มี **ให้เพิ่มได้เลย ไม่ต้องรอ**
  เซิร์ฟเวอร์ยังไม่ตรวจ ส่งไปตอนนี้ไม่มีผลข้างเคียงใด ๆ แต่วันที่ฝั่ง backend เปิดระบบ
  ยืนยันตัวตน แอปที่ไม่เคยส่งจะ 401 ทั้งตัวพร้อมกัน
* **หน้าจอไหนยัง mock ข้อมูลอยู่บ้าง** (คำถามข้อ 4 ข้อย่อย 1) — grep หาค่าคงที่หรือ
  fixture ที่ยังไม่ได้ต่อ API จริง แล้วรายงานเป็นรายการมา

## 3. ถ้าจะเขียนโค้ดต่อ API ให้ยึดสัญญา ไม่ใช่ยึดไฟล์นี้

`backend/API_CONTRACT_APP.md` ในรีโป backend คือตัวจริง ไฟล์นี้เป็นสรุป
ตัวอย่าง JSON ในไฟล์นี้ถูก ณ วันที่เขียน แต่ถ้าสองที่ไม่ตรงกันเมื่อไหร่ **ยึดสัญญา**
และถ้าเข้าถึงรีโป backend ไม่ได้ ให้บอกคนที่ 1 ให้ `git pull` แล้วเปิดไฟล์นั้นให้

**สิ่งที่ห้ามทำ:** อย่าแนะนำให้ขอไฟล์ `serviceAccountKey.json` จากฝั่ง backend
มันคือ Admin SDK private key ของเซิร์ฟเวอร์ ใครถือก็อ่าน/เขียน/ลบข้อมูลทั้งโปรเจกต์ได้
และปลอม token เป็นผู้ใช้คนไหนก็ได้ **แอปไม่ต้องใช้มันเลย** ไฟล์ที่แอปใช้คือ
`google-services.json` ซึ่ง `flutterfire configure` จัดการให้เอง

## สรุปสิ่งที่ขอ

1. `git pull` แล้วอ่าน `backend/API_CONTRACT_APP.md` (โดยเฉพาะหัวข้อ 2 ขั้นที่ 4 และหัวข้อ 11)
2. ตอบคำถาม 4 ข้อในส่วนที่ 2 — **ข้อ 1 บล็อกงานเราอยู่ ตอบสั้นสุดก็ได้** ส่วนข้อ 3 กับ 4 กำหนดว่าฝั่งเราต้องแก้ฐานข้อมูลไหม
3. รัน `flutterfire configure` แล้วเลือก `pathguard-ai-2d047` **อย่าสร้างโปรเจกต์ใหม่**
4. เลิก mock `recommendedPlaces` ต่อ `GET /api/recommendation/{id}` ได้เลย
5. เริ่มส่ง `Authorization: Bearer` ทุก request ตั้งแต่ตอนนี้ แม้เซิร์ฟเวอร์ยังไม่ตรวจ
6. **อย่าฮาร์ดโค้ด URL เซิร์ฟเวอร์** ตอนทดสอบจะเป็น URL ที่เปลี่ยนทุกครั้งที่เรารันใหม่
