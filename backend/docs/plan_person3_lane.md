## 1. การตัดสินใจที่ล็อกแล้ว

### D1 — หมุดที่ผู้ดูแลปักคือดีไซน์ ไม่ใช่ทางเลี่ยง (L3-0)

ตัดสินจากการวัด ไม่ใช่ความชอบ สามอย่าง:

**ก. `known_places` ขยับ Module 4 น้อยกว่าที่คิดมาก** รันลำดับเรียกจริงของ
`/api/search-area` (ขั้น 5-8) บน track GeoLife จริง 30 วัน ด้วยชุด `known_places` 3 แบบ
**โซนความน่าจะเป็นจาก KDE ออกมาเหมือนกันทุกไบต์ (750/750/1000 เซลล์) ทั้งสามแบบ**
เพราะ `_astar_familiar` ใส่จุดปลายทางเข้าไปแค่ 5 จุด ในกองจุดจาก Monte-Carlo 10,000 จุด
`known_places` ขยับแค่ *รายชื่อเป้าหมายที่ให้ไปค้น* กับรัศมี ±50% เท่านั้น

**ข. ในส่วนที่ขึ้นกับสถานที่จริง ๆ ผลของ Module 1 เป็นโทษ** เป้าหมายค้นหาอันดับ 1
ที่มันให้คือก้อนถนน freq-3285 จาก gotcha 12 — ทีมค้นหาคนหายจะถูกชี้ไปที่จุดศูนย์กลางถนน
ส่วนหมุดให้เป้าหมายอันดับ 1 ที่ระยะ 0 เมตร คือบ้านผู้ป่วยจริง ๆ

**ค. `place_clustering.py:63-69` ไม่ส่ง `place_name` ออกมาเลย** — มีแค่
`cluster_id/latitude/longitude/visit_frequency/avg_stay_time` สถานที่ที่ระบบเรียนเองจึง
**บอกครอบครัวเป็นคำพูดไม่ได้ตลอดกาล** รายการค้นหาอ่านออกมาว่า "unknown" ห้าครั้งติด
**มีแต่คนเท่านั้นที่ตั้งชื่อสถานที่ได้** นี่เป็นข้อจำกัดเชิงโครงสร้าง ไม่ใช่บั๊กที่รอแก้

### D2 — รายงานเก็บ Module 1 ไว้ และรายงานผลลบเป็นผลการทดลอง

ตัดสินโดยผู้ใช้ 26 ส.ค. — สร้างแล้ว วัดแล้ว พบว่า DBSCAN บนจุดดิบให้ "สถานที่" 142-156 แห่ง

โค้ดอยู่ในรีโปต่อไป `docs/PathGuard_Module_Walkthrough.md:8-13` มีแบนเนอร์เตือนแล้ว

### D3 — ปักแค่บ้านไม่พอ และนี่คือความเสี่ยงอันดับหนึ่งของ pilot

รัน pipeline Module 3 จริงด้วยน้ำหนักที่ seed ไว้ (0.30/0.25/0.20/0.15/0.10) และเพดาน
(50/80/500) คงทุกอย่างไว้ เปลี่ยนแค่ `known_places`:

| ผู้ป่วยอยู่ไหน | ปักแค่บ้าน | ปักครบ 4 ที่ |

| อยู่บ้าน | 9.0 low | 9.0 low |
| วัดที่ไปทุกวัน | **56.0 medium** | 15.0 low |
| ตลาดที่ไปทุกวัน | **56.0 medium** | 15.0 low |
| บ้านลูกสาว | **56.0 medium** | 18.0 low |
| ห่างบ้าน 2.5 กม. หลงจริง | 56.0 medium | 56.0 medium |

ปักแค่บ้าน → `familiarity` = 0.000 ทุกที่ยกเว้นบ้าน → **แยก "อยู่วัดที่ไปทุกวัน" กับ
"หลง 2.5 กม." ไม่ออก** และกฎ sustained (มากกว่าหรือเท่ากับ 50 ติดกัน 5 รอบ ที่ throttle
60 วิ) จะ push หลังอยู่วัดราว 5 นาที **ทุกครั้งที่ไป**

สคริปต์วัดเป็นของใช้แล้วทิ้ง ไม่ได้ commit — วิธีทำบันทึกไว้ตรงนี้เพื่อสร้างใหม่ได้:
คงทุกอย่างไว้ เปลี่ยนแค่ `known_places` แล้วเรียก `collect_risk_factors` → normalize →
`calculate_risk` ด้วยน้ำหนักจาก `seed_risk_rules`

### D4 — คุณทำ backend คนที่ 1 ทำ frontend

### Phase B — L3-1 สัญญา `places` ✅ เสร็จ 26 ส.ค.

ทำ:

* `API_CONTRACT_APP.md` §10 — เดิม `places` อยู่แต่ใน `API_CONTRACT_ADMIN.md`

* `PUT /api/patients/{id}/places/home` — endpoint แคบที่ทับเฉพาะบ้าน **ลบหมุดอื่นไม่ได้**
  เพราะ `POST .../places` ทับทั้งชุด ถ้าหน้าจอส่ง "บ้านอย่างเดียว" ซ้ำหลังปักครบแล้ว
  หมุดที่เหลือจะหายเงียบ ๆ พร้อม `201`
* identity ใช้ flag `is_home` และฝั่ง whole-set ตั้งให้ `places[0]` เสมอ →
  มีหมุดบ้านหนึ่งจุดพอดีเสมอ upsert จึงมีแถวให้ทับ ไม่ใช่สร้างซ้ำ
* `PlacesIn.min_length=1` **เก็บไว้ตั้งใจ** (ตัดสิน 26 ส.ค.) — สิ่งเดียวที่มันห้ามคือ
  "0 หมุด" ซึ่งทำให้ตกกลับ partial mode ที่วัดแล้วว่าอยู่บ้านกับหลง 2.5 กม. ได้ 18.8 low
  เท่ากัน และมันคือสิ่งที่การันตีว่า `places[0]` มีอยู่จริง
* `scripts/demo_server.py` mount router แค่ 8 จาก 13 ทั้งที่คอมเมนต์อ้างว่า mount เหมือน
  `app.main` → หมุดที่ยิงเข้าพอร์ต dashboard ได้ 404 แก้ให้ตรงกันแล้ว

**เกณฑ์ตรวจ:**

1. `PUT .../places/home` หลังปักครบชุด → `count` ไม่ลด → มีเทสต์
2. ยิง `PUT` ซ้ำ → ทับ ไม่เพิ่ม → มีเทสต์
3. `is_home == true` หมุดเดียวเสมอ ไม่ว่ามาจากทางไหน → มีเทสต์
4. รูปแบบ response ในสัญญาตรงกับที่ยิงจริง → ตรวจแล้ว (`unnamed` ไม่ใช่ `unknown`)
5. §10 ต้องมีตาราง 56-medium ไม่งั้น pilot ออกไปพร้อม false alarm ทุกครั้งที่ออกจากบ้าน

### Phase D — L3-4 `routine_patterns` ✅ เสร็จ 26 ส.ค.

`behavioral_profiles.routine_patterns` มีมาตั้งแต่ตอนออกแบบ schema และ**ไม่เคยมีใครเขียน**
`recommendation_generation.py` จึงตั้ง `time_match` ไว้ที่น้ำหนัก 0.0 และ hardcode ค่าเป็นศูนย์
— ตัวจัดอันดับวิ่งบน 3 ปัจจัยจาก 4 มาตลอด

ทำ: `app/ai/module1_behavior/routine_patterns.py` + `scripts/build_routine_patterns.py`

**ทำไมมันไม่ใช่การเปิด L3-3 ใหม่:** สถานที่มาจากหมุดที่คนปักอยู่แล้ว มันเรียนแค่ *ชั่วโมง*
ที่ผู้ป่วยอยู่แต่ละหมุด **สร้าง ย้าย หรือตั้งชื่อสถานที่ไม่ได้เลย** ไม่มีหมุด = ไม่เรียนอะไร

การตัดสินใจสองข้อ:

1. **ตัวหารคือทุก fix ในชั่วโมงนั้น ไม่ใช่เฉพาะที่ match** ผู้ป่วยที่เดินอยู่ข้างนอกเกือบทั้ง
   บ่ายสามควรได้ค่าต่ำทุกที่ ไม่ใช่ค่ามั่นใจสูงให้ที่ที่บังเอิญเดินผ่าน
2. **ชั่วโมงเป็นเวลาท้องถิ่น คำนวณที่เดียว** `recorded_at` เป็น UTC แต่ "ไปวัดตอนเช้า"
   ของครอบครัวไทยไม่ใช่ ถ้าฝั่งสร้างกับฝั่งอ่านเหลื่อมกัน lookup จะพลาดทุกชั่วโมง
   `time_match` จะอ่านได้ 0.0 ตลอด **โดยไม่มี error และหน้าตาเหมือนคนไข้ที่ไม่มีกิจวัตรเป๊ะ ๆ**

น้ำหนัก `time_match` = 0.25 ต่ำกว่า `frequency` ตั้งใจ — กิจวัตรที่อนุมานเอาเองมีค่าน้อยกว่า
ความถี่ที่ผู้ดูแลบอกมาเอง

**เกณฑ์ตรวจ:**

1. probability ใช้ตัวหารเป็นทุก fix → มีเทสต์ (4 ใน 10 = 0.4 ไม่ใช่ 1.0)
2. ชั่วโมงที่มีหลักฐานน้อยกว่า `MIN_SAMPLES_PER_HOUR` ไม่พูดอะไร → มีเทสต์
3. **ฝั่งสร้างกับฝั่งอ่านตกลงกันเรื่องชั่วโมง** → มีเทสต์ที่แดงถ้าเปลี่ยน `score_place`
   ไปใช้ `ctx.now.hour` (ซึ่งเป็นสิ่งที่โค้ดที่เหลือในโปรเจกต์ทำอยู่) — พิสูจน์แล้วว่าแดงจริง
4. ไม่มีหมุด = ไม่เรียน → มีเทสต์ที่วิ่งผ่าน DB จริง
5. คนไข้ที่ไม่มีกิจวัตรได้คะแนนเท่าเดิมเป๊ะ → `has_routine` กัน `time_match` ออกจากสูตร
6. caller ที่ไม่มีนาฬิกา (`now=None` ใน `trip_confidence`) ต้องไม่พัง → มีเทสต์
   **ข้อนี้เจอตอนรัน suite เต็ม ไม่ใช่ตอนเขียน** — `score_place` ไม่เคยอ่าน `now` มาก่อน
   จึงไม่มีอะไรบังคับให้ถาม
