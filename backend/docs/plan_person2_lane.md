## 3. ทำไมต้อง throttle 60 วินาที

`GET /api/risk/{id}` **ครั้งเดียว** ทำสิ่งเหล่านี้:

- ดึง GPS **30 วันเต็ม** จาก Postgres — `risk.py:81`
- `fit()` **IsolationForest** — `wandering_detection.py:252`
- `fit()` **RoutePredictor** — `risk_data_collection.py:141,146`
- โหลด rule KB ใหม่ ไม่มี cache — `risk.py:75-78` (ตั้งใจ เพื่อให้แก้กฎแล้วมีผลทันที)

มือถือส่งทุก 30 วิ = **2,880 ครั้ง/วัน/คนไข้** และเมื่อสะสมครบ 30 วันคือ fit โมเดล
บนข้อมูล ~86,000 แถว **ทุก 30 วินาที** — เรียกทุกจุดไม่ได้เด็ดขาด

**ตัวจับเวลาใช้ `risk_scores.calculated_at` ที่มีอยู่แล้ว** ไม่ต้องเพิ่ม state ใหม่
ข้อดีคือรอดตอนรีสตาร์ตเซิร์ฟเวอร์ และไม่พังถ้าวันหลังรันหลาย worker
(ต่างจาก `kalman_filter._filters` ที่เป็น dict ในหน่วยความจำ)

60 วิ ยังอยู่ในเกณฑ์ "แจ้งเตือนภายใน 2 นาที" ของแผนสบายๆ

**ทำแล้ว 25 ส.ค.:** ถอด `confusion` ออกจาก `_PARTIAL_FACTORS` เหลือ
`wandering` + `danger_zone` (เกลี่ยเป็น 0.625/0.375 จากค่า KB ตอนรัน ไม่ฮาร์ดโค้ด)
ได้ 18.8 ทั้งสองแบบ คือ**หายกลับหัว แต่ยังแยกไม่ออก** ที่ 30 จุด
(ตัว `wandering` ต้องมี ~600 จุดถึงจะแยกออก) ปลด `xfail(strict)` ใน `test_alert_chain.py`
แล้ว และเพิ่มเทสต์ที่ปักหมุด invariant ตรงๆ ว่า**คนนั่งนิ่งต้องไม่ได้คะแนนสูงกว่าคนเดิน** —
เทสต์ floor เดิม (31 คะแนน) จับบั๊กนี้ได้โดยบังเอิญเท่านั้น ปัจจัยที่บวก 15 คะแนนตอนพัก
จะลอดใต้ floor แล้วทำให้กลับหัวอีกโดยไม่มีใครรู้

**เปลี่ยนจาก "หน้าจอโกหก" เป็น "หน้าจอไม่รู้"** — ไม่ได้ตรวจจับเก่งขึ้น ทั้งก่อนและหลัง
ยังเป็น level `low` และไม่มี alert ยิง แต่ 39% ตอนยายนั่งดูทีวีคือตัวเลขที่ผู้ดูแลเอาไป
ตัดสินใจได้และมันผิด ส่วน 18.8 เท่ากันทั้งคู่ตรงกับความจริงว่ามี 30 จุดและไม่มีหมุด

**ไม่กระทบเล่มรายงาน:** ตาราง `risk_factor_weights` ใน `docs/module3_rule_based_system.md` §5
(route 0.30 · wandering 0.25 · confusion 0.20 · danger_zone 0.15 · unfamiliarity 0.10)
พร้อมแหล่งอ้างอิงทางการแพทย์ ไม่ถูกแตะสักตัว — full mode ยังคิด 5 ปัจจัยครบ และคำว่า

ถูก gitignore ทั้งโฟลเดอร์) มันคือของที่เพิ่มเข้ามา 19–20 ส.ค. หลังเล่มเขียนเสร็จ

## 4f. รหัสจับคู่เครื่องผู้ป่วย (26 ส.ค.) — L2-4 งานใหม่ที่ต้องทำก่อนเปิด auth

โผล่มาจากการกรี้ล lane 3 แต่มันเป็นงาน lane นี้ เพราะมันปิดทาง `AUTH_ENABLED`

**สิ่งที่เพิ่งรู้:** หน้าผู้ดูแลของคนที่ 1 เพิ่มผู้ป่วยด้วย **ชื่อ + เลเวลอัลไซเมอร์

schema แล้ว backend รองรับได้ประมาณหนึ่งอย่างครึ่งจากสี่:

| หน้า admin เก็บ | backend มีที่เก็บไหม |
|---|---|
| ชื่อ | ได้ — `users.name` |
| **เลเวลอัลไซเมอร์ 1/2** | **ไม่มีคอลัมน์ไหนเลย** `users` มีแค่ `id, firebase_uid, name, role, caregiver_id, created_at` และไม่มีโค้ดที่ไหนใน `app/` อ่านค่าความรุนแรง |
| สถานที่ปลอดภัย | ตรงกับหมุด `known_places` ได้ แต่ `API_CONTRACT_APP.md` ไม่เคยมีคำว่า `places` — เขาไม่เคยถูกบอกว่ามี endpoint นี้ |
| **รหัส login** | **ไม่มีแนวคิดนี้เลย** ไม่มีตาราง ไม่มีคอลัมน์ ไม่มี endpoint |

**ทำไมมันร้ายแรง:** `auth.py:103-118` บังคับว่าทุก request ต้องมี
`Authorization: Bearer <Firebase ID token>` ที่ uid แปลงกลับเป็นแถวใน `users` ได้
ไม่งั้น 403 — เครื่องที่ถือแค่รหัสไม่มี token **เปิด `AUTH_ENABLED` เมื่อไหร่
`/api/gps` ตายทันที** ซึ่งคือเส้นเลือดใหญ่ทั้งเส้น แปลว่า L2-3 ไม่ใช่การพลิก env
var อีกต่อไป และคำตอบของ L2-1 อาจกลับมาเป็น *"ส่งไม่ได้"* ไม่ใช่ *"ยังไม่ส่ง"*

**ตัดสินใจแล้ว 26 ส.ค. — แลกรหัสเป็น Firebase custom token**

```
1. ผู้ดูแลกดสร้างผู้ป่วย  → สร้าง users row + สุ่มรหัส เก็บลงตาราง pairing_codes

4. แอป signInWithCustomToken() → ได้ Firebase ID token ของจริง
5. ทุก request หลังจากนั้นส่ง Authorization: Bearer <id_token> ตามปกติ
```

`firebase-admin` อยู่ใน `requirements.txt` แล้วและ init ที่ `app/db/database.py:89`

**เหตุผลที่ไม่เลือกทางที่ตอบ `patient_id` เปล่าๆ:** ไม่ใช่เรื่องความปลอดภัยล้วน แต่เป็น
ต้นทุนโครงการ — สองทางต่างกัน **บรรทัดเดียวต่อฝั่ง** (ตาราง endpoint และ logic ตรวจ
รหัสเหมือนกันหมด) แต่ทางที่ไม่มี token ทำให้ `AUTH_ENABLED` เปิดไม่ได้ตลอดกาล →

## 6. ต้องเคลียร์กับทีม

1. **`notification.py` แผนขัดกันเอง** — การ์ดแบ่งบทบาทบอกว่าเป็นงานคนที่ 2 แต่ตารางสัปดาห์ที่ 2
   บอกว่าเป็นงานคนที่ 3 ไฟล์เดียวกัน เสี่ยงทั้งทำซ้อนกันและไม่มีใครทำ — เอกสารนี้ถือว่าเป็นของเรา
2. **คนที่ 3 จะมาแตะ `gps.py` และ `risk.py`** ที่เราแก้ใน Phase 0 และ 3 — บอกเขาก่อน
3. **สัญญา API เปลี่ยนแล้ว** (ดู Phase 0) — คนที่ 1 ต้องรู้ก่อนเขียนโค้ดยิง GPS
4. **แอปผู้ดูแลต้องเสร็จทันวันทดลอง** ไม่งั้น FCM ไม่มีปลายทาง และเกณฑ์
   "ผู้ดูแลได้รับแจ้งเตือน" สอบตก — ตาข่ายรองคือให้ผู้ดูแลเปิด dashboard ค้างบนมือถือ
   (`dashboard.html:395` poll ทุก 60 วิ ทำงานอยู่แล้ว ไม่ต้องเขียนอะไรเพิ่ม)

## 7. ก่อนให้ผู้ป่วยจริงลอง

ไม่ใช่เช็คลิสต์เต็มของ pilot 4 สัปดาห์ แต่เป็นขั้นต่ำสำหรับการทดลองแบบมีคนเฝ้า:

- [ ] **ผู้ดูแลปักหมุดบ้าน/รพ./ตลาด ก่อนเริ่ม** — ไม่งั้นได้แค่ 60% และ `unfamiliarity` บอด
- [ ] **ตั้งเขตอันตรายในตาราง `danger_zones`** — 15% ที่ใช้ได้ตั้งแต่วันแรก แต่ต้องมีข้อมูล
- [ ] ไม่มีข้อมูล GeoLife หรือคนไข้อื่นปนใน `patient_id` ของผู้ป่วยจริง
- [ ] ทดสอบเดินออกนอกเส้นทาง → แจ้งเตือนถึงผู้ดูแล จับเวลาได้จริง ซ้ำ 3 ครั้ง
- [ ] ครอบครัวรู้ว่านี่เป็นต้นแบบ ไม่ใช่อุปกรณ์ความปลอดภัยที่รับรองแล้ว
- [ ] มีคนเฝ้าดูแลตามปกติคู่ขนานตลอด
- [ ] ลบข้อมูลทั้งหมดได้เมื่อจบ (ดู D5)

> ระบบนี้จะยังไม่ใช่อุปกรณ์ความปลอดภัยที่พึ่งพาได้ ถ้ามือถือแบตหมด เน็ตหลุด
> หรือ Android ฆ่าแอป ระบบจะเงียบสนิทโดยไม่มีใครรู้ว่ามันเงียบ
> ห้ามให้ครอบครัวลดการเฝ้าระวังเพราะคิดว่ามีแอปคอยดูให้แล้ว
