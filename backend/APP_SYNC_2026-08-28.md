# ส่วนที่ 1 — คำตอบของคุณเปลี่ยนอะไรบ้าง

## 1.1 ✅ Level 2 เหลือ 3 ที่แล้ว ตามที่ขอ

`GET /api/recommendation/{id}` คืน **3 ที่ ทุกระดับ** แล้ว ทั้ง Level 1, Level 2
และผู้ป่วยที่ไม่ได้ระบุระดับ ไม่ต้องส่งพารามิเตอร์อะไรเพิ่ม

**เหตุผลของคุณดีกว่าที่รายงานเขียนไว้ และเราแก้ตามคุณ ไม่ใช่ตามรายงาน** รายงานให้
Level 2 ได้ 5 และโค้ดเคยทำตามนั้น สมมติฐานที่ใช้ตอนนั้นคือ "ช่องค้นหา Level 2 ถูกล็อก
แกริดจึงต้องครอบคลุมทุกที่ที่เขาอาจอยากไป" — การล็อกช่องค้นหาเป็นเรื่องจริงและคุณยืนยันแล้ว
แต่ตอนนั้นมันคือการเถียงเรื่องหน้าจอที่ยังไม่มีใครสร้าง ตอนนี้หน้าจอมีจริงแล้วและมันแสดง 3

เราใส่เทสต์ล็อกไว้ (`test_home_screen_shows_three_places_at_every_stage`) เพราะไม่มีอะไร
กันไม่ให้คนถัดไปอ่านรายงานแล้ว "แก้กลับ" เป็น 5 **ถ้าหน้าจอเปลี่ยนไปแสดงได้มากกว่า 3 บอกมา
ฝั่งเราแก้ที่เดียว**

## 1.2 ✅ หน้าผู้ป่วยที่ยังไม่มีหมุด — ของเดิมรองรับอยู่แล้ว

ที่คุณจะขึ้นว่า *"รอผู้ดูแลเพิ่มสถานที่ให้"* ไม่ต้องรออะไรจากเรา endpoint คืน **HTTP 200**
ไม่ใช่ error:

```json
{ "patient_id": 42, "status": "no_profile", "recommendations": [],
  "message": "No behavioral profile yet — Module 1 has not trained this patient." }
```

⚠️ **เช็ค `status` ไม่ใช่ `message`** — `message` เป็นภาษาอังกฤษสำหรับ dev และเปลี่ยนได้
`status` มี 2 ค่าคือ `ok` กับ `no_profile` เท่านั้น

## 1.3 นำทาง / ออกนอกเส้นทาง — backend ไม่ต้องทำอะไรทั้งคู่ ✅

บันทึกไว้ในเอกสารแล้วว่าเป็นงานฝั่งแอป 100% ใช้ Directions API
`REPORT_VS_CODE.md` เคยเขียนว่า "ทำไม่ได้ เพราะโปรเจกต์ไม่มีผู้ให้บริการเส้นทาง" — แก้แล้ว

⚠️ **อย่าสับสน 2 อย่างนี้:** "ออกนอกเส้นทาง" ของคุณ (ออกนอก route → คำนวณเส้นใหม่)
คนละตัวกับ `route_deviation` ของเรา (เป็นปัจจัย 30% ของคะแนนความเสี่ยง) สองอันนี้ไม่ต้องคุยกัน

# ส่วนที่ 2 — ของใหม่: ผู้ป่วย 1 คนมีผู้ดูแลได้หลายคนแล้ว

คุณตอบว่าเอาฟีเจอร์ *"แจ้งผู้ดูแลหลายคน + จัดอันดับระยะทาง + ฉันจะไปรับ"* และบอกลำดับเองว่า
**backend แก้ฐานข้อมูลก่อน แล้วแอปค่อยต่อ UI** — ฐานข้อมูลแก้เสร็จแล้ว พร้อมให้ต่อ UI

เดิมผู้ป่วย 1 คนมีผู้ดูแลได้ **1 คน** เท่านั้น (เป็น FK เดี่ยวในตาราง `users`) ตอนนี้เป็นตาราง
แยก ผูกได้ไม่จำกัด

## 2.1 ที่ทำงานเองแล้ว ไม่ต้องแก้โค้ดแอป

| | |
|---|---|
| **สิทธิ์เข้าถึง** | ผู้ดูแล**ทุกคน**ที่ผูกกับผู้ป่วยอ่านข้อมูลได้เท่ากันหมด ไม่มีใครสิทธิ์มากกว่าใคร |
| **Push** | alert 1 ครั้ง → เข้า**ทุกเครื่องของผู้ดูแลทุกคน** ของเดิมที่คุณต่อไว้ทำงานต่อได้เลย |

## 2.2 🆕 2 หน้าจอใหม่ที่ต้องสร้าง — รหัสเชิญผู้ดูแล

**นี่คือส่วนที่ต้องการงานฝั่งคุณ** และมันเล็ก หน้าตาเหมือนรหัสจับคู่เครื่องผู้ป่วยที่คุณ
ทำไปแล้ว (สัญญาหัวข้อ 2) — รูปแบบรหัสเดียวกัน อายุ 24 ชม. เท่ากัน ใช้ได้ครั้งเดียวเหมือนกัน

**หน้าที่ 1 — ผู้ดูแลที่มีอยู่ กดปุ่ม "เพิ่มผู้ดูแล" แล้วได้รหัสมาอ่านให้ฟัง**

```
POST /api/patients/42/caregiver-invites
(body ว่าง {})
```
```json
{ "patient_id": 42, "invite_code": "K7M2-QX94",
  "expires_at": "2026-08-29T09:14:02Z" }
```

**หน้าที่ 2 — ผู้ดูแลคนใหม่กรอกรหัส**

```
POST /api/caregivers/redeem-invite
{ "code": "K7M2-QX94" }
```
```json
{ "patient_id": 42, "patient_name": "ยาย",
  "caregiver_id": 57, "already_linked": false }
```

| เรื่อง | รายละเอียด |
|---|---|
| 🛑 **คนใหม่ต้องสมัครก่อน** | ต้อง sign in Firebase + `POST /api/register` ด้วย `role: "caregiver"` **ก่อน** กรอกรหัส · **ต่างจาก `POST /api/pair` ของเครื่องผู้ป่วย** — อันนี้ไม่สร้างบัญชี ไม่คืน token เพิ่มแค่สิทธิ์เข้าถึง |
| **ใครออกรหัสได้** | ผู้ดูแล**คนไหนก็ได้**ที่ผูกกับผู้ป่วยคนนั้น ไม่จำกัดเฉพาะคนแรก · **แต่ตัวผู้ป่วยเองออกไม่ได้ (403)** |
| **รหัสจับคู่เครื่อง ≠ รหัสเชิญ** | คนละชุดคนละตาราง **จงใจ** — รหัสหัวข้อ 2 ใช้*สวมเป็น*ผู้ป่วย รหัสนี้ใช้*ดู*ผู้ป่วย ถ้าใช้ชุดเดียวกัน รหัสที่ตั้งใจไว้ตั้งค่ามือถือจะกลายเป็นรหัสแจกสิทธิ์ดูตำแหน่งผู้ป่วยได้ **อย่าเอามารวมหน้าจอเดียวกัน** |
| `404` | รหัสผิด / หมดอายุ / ใช้ไปแล้ว — **ข้อความเดียวทั้งสามกรณี** แสดง "รหัสไม่ถูกต้องหรือหมดอายุแล้ว" พอ |
| พิมพ์ตัวเล็ก ใส่ขีด มีเว้นวรรค | รับหมด เราจัดรูปให้เอง เหมือนรหัสจับคู่ |
| `already_linked: true` | เขาเป็นผู้ดูแลอยู่แล้ว **ไม่ใช่ error** แต่รหัสถูกใช้ไปแล้ว — แสดง "คุณดูแล [ชื่อ] อยู่แล้ว" |

## 2.3 🆕 `PUT /api/caregivers/{caregiver_id}/location` — แอปผู้ดูแลรายงานตำแหน่งตัวเอง

จำเป็นสำหรับการจัดอันดับระยะทาง ไม่รู้ว่าผู้ดูแลอยู่ไหนก็เรียงไม่ได้

```
PUT /api/caregivers/12/location
{ "latitude": 13.7563, "longitude": 100.5018 }
```
```json
{ "caregiver_id": 12, "location_updated_at": "2026-08-28T09:14:02Z" }
```

| เรื่อง | รายละเอียด |
|---|---|
| **ทับของเดิมเสมอ ไม่เก็บประวัติ** | เก็บแค่ตำแหน่งล่าสุด ระบบไม่มีที่ไหนเก็บเส้นทางการเดินของผู้ดูแลเลย **จงใจ** — การจัดอันดับถามแค่ "ตอนนี้ใครใกล้สุด" |
| 🛑 **ต้องขอ consent ก่อนเริ่มส่ง** | นี่คือตำแหน่งของ*คนในครอบครัว* ไม่ใช่ของผู้ป่วย เขาไม่ได้อยู่ในความดูแลของใคร **แอปต้องถามก่อน และควรมีสวิตช์ให้ปิด** |
| `422` | ส่ง id ที่เป็น**ผู้ป่วย** มาที่นี่ → ปฏิเสธ ตำแหน่งผู้ป่วยไป `POST /api/gps` เท่านั้น ที่นั่นมันถูกกรอง Kalman คิดคะแนน และยิง alert ได้ ส่งมาที่นี่มันจะเงียบและ*ดูเหมือนสำเร็จ* |

# ส่วนที่ 3 — คำถาม 3 ข้อ ตอบสั้นๆ ได้เลย

## ❓ ข้อ 1 — แอปผู้ดูแลส่งตำแหน่งตัวเองได้ถี่แค่ไหน

ตอบมาว่าเป็น background หรือเฉพาะตอนเปิดแอป และกินแบตแค่ไหนถึงยอมรับได้

**ทำไมถึงถาม:** การจัดอันดับต้องมีเกณฑ์ว่า *"ตำแหน่งเก่ากี่นาทีถือว่าใช้ไม่ได้"* ตำแหน่ง
เมื่อวานต้องไม่ชนะการจัดอันดับ แต่ถ้าตั้งเกณฑ์ 5 นาทีแล้วแอปส่งทุก 30 นาที ทุกคนจะถูกตัดออก
หมดและไม่มีใครขึ้นอันดับเลย **เกณฑ์นี้ตั้งจากพฤติกรรมแอป ไม่ใช่จากที่เราเดา** — นี่คือ
สิ่งเดียวที่ค้างการจัดอันดับอยู่ตอนนี้

## ❓ ข้อ 2 — กด "ฉันจะไปรับ" แล้วผู้ดูแลคนอื่นควรเห็นอะไร

แค่ "มีคนไปรับแล้ว" หรือเห็นชื่อคนที่รับ หรือเห็นตำแหน่งของคนที่รับด้วย
และถ้ากดแล้วเปลี่ยนใจได้ไหม

## ❓ ข้อ 3 — 🛑 ขอ "เส้นเดียว" ที่ต่อ backend จริง ก่อนที่ UI จะครบ

**ข้อนี้สำคัญที่สุดในไฟล์ และมันเป็นเรื่องตารางเวลา ไม่ใช่เรื่องเทคนิค**

คำตอบข้อ 1 ของคุณคือ *"ยังไม่มี endpoint ไหนของ backend ถูกเรียกเลยสักตัว"* ซึ่งเราเข้าใจ
และมันสมเหตุสมผลกับแผนของคุณ (ทำ UI ให้ครบก่อน ค่อยต่อ backend เมื่อ Firebase พร้อม)

แต่ **W1 ของแผน 4 สัปดาห์คือ "GPS จากมือถือจริงไปถึงฐานข้อมูล" และมันยังไม่เริ่มเลยสักก้าว**
W2, W3, W4 ต่อคิวอยู่หลัง W1 ทั้งหมด แผนถึงบอกให้ freeze สัญญาตั้งแต่วันแรกและต่อไปเรื่อยๆ
พอดันการเชื่อมต่อทั้งหมดไปไว้ท้าย ความเสี่ยงทั้งหมดก็ไปกองอยู่ตรงนั้นด้วย

**ไม่ได้ขอให้หยุดทำ UI** ขอแค่ **1 หน้าจอ เรียก 1 endpoint จริงๆ** เพื่อพิสูจน์ว่าท่อทะลุ

ตัวที่เหมาะที่สุดคือ **`GET /api/recommendation/{id}`**:
* ของฝั่งเราพร้อมและเทสต์ผ่าน
* สัญญาหัวข้อ 11.1 เขียนไว้ครบ
* คุณ mock มันอยู่แล้ว (`recommendedPlaces`) เปลี่ยนเป็นของจริงคือแก้ที่เดียว
* มันเป็นตัวป้อนปลายทางให้ระบบนำทางที่คุณทำเสร็จแล้ว — ต่อเสร็จ นำทางจะพาไปหมุดจริง
  ของผู้ดูแลแทนที่จะเป็นข้อมูล mock

**บอกมาว่าพร้อมเมื่อไหร่** ฝั่งเราต้องเปิด `AUTH_ENABLED` + เปิด tunnel ให้ ซึ่งใช้เวลา
ไม่กี่นาที แต่ต้องนัดกัน เพราะ tunnel รันบนโน้ตบุ๊กและ URL เปลี่ยนทุกครั้งที่รีสตาร์ต

# ส่วนที่ 4 — สรุปสถานะฟีเจอร์ทั้ง 4 ที่คุณตอบว่า "เอา"

| ฟีเจอร์ | ฝั่ง backend | ฝั่งแอป |
|---|---|---|
| นำทาง real-time | ✅ ไม่ต้องทำอะไร | ✅ คุณบอกว่าเสร็จแล้ว |
| เส้นทางกลับตอนออกนอกเส้นทาง | ✅ ไม่ต้องทำอะไร | 🟠 คุณบอกว่ายังไม่เสร็จ |
| **แจ้งผู้ดูแลหลายคน + จัดอันดับ + ฉันจะไปรับ** | 🟠 **ฐานข้อมูล สิทธิ์ push รหัสเชิญ ที่เก็บพิกัด เสร็จแล้ว** · จัดอันดับรอคำตอบข้อ 1 · "ฉันจะไปรับ" รอคำตอบข้อ 2 | ⬜ ต่อ UI ได้แล้ว (ส่วนที่ 2) |
| **นำทางไปสถานที่ปลอดภัยใกล้สุด** | ⬜ **ยังไม่เริ่ม** ตาราง POI ยังไม่มี | ⬜ รอ backend |

**เรื่อง POI:** เราจะเริ่มต่อจากนี้ แต่ติดคำถามที่ฝั่งเราตอบเองไม่ได้เหมือนกัน —
**ข้อมูลโรงพัก/โรงพยาบาล/สถานที่ปลอดภัย จะเอามาจากไหน** ป้อนมือเฉพาะพื้นที่ที่ครอบครัว
ไพลอตอยู่ (แม่นแต่ไม่ scale) หรือดึงจาก Google Places / OpenStreetMap (ครอบคลุมแต่ต้องจัดการ
ข้อมูลขยะ) — ถ้าแอปมี Google Places API key อยู่แล้วจากการทำ Directions ตอบมาด้วย
มันเปลี่ยนคำตอบ

## 1. อย่าตอบคำถามในส่วนที่ 3 แทนเขา
ทั้งสามข้อเป็นเรื่องที่ต้องดูโค้ดฝั่งแอปจริงหรือเป็นการตัดสินใจของทีม อย่าเดา ให้ถามเขา
โดยเฉพาะข้อ 3 ที่เป็นเรื่องตารางเวลา ไม่ใช่เรื่องเทคนิค

## 2. เรื่องที่ตรวจได้จากโค้ดของเขา ช่วยตรวจให้เลย
* `recommendedPlaces` ที่ mock อยู่ — เตรียมรับ **3 ที่** ทั้ง Level 1 และ Level 2
  (เดิมแผนคือ Level 2 ได้ 5) และรับ `status: "no_profile"` + array ว่าง โดยไม่ถือเป็น error
* ถ้าจะต่อ `GET /api/recommendation` ให้ใช้ `place_name` ขึ้นปุ่ม **และเผื่อกรณี `null`**
  (ซ่อนปุ่มไปเลย อย่าเขียน "ไม่ทราบ")
* หน้าจอ "เพิ่มผู้ดูแล" ที่จะสร้าง **ห้ามใช้รหัสชุดเดียวกับหน้าจับคู่เครื่องผู้ป่วย**
  เป็นคนละ endpoint คนละความหมาย

## 3. ถ้าจะเขียนโค้ดต่อ API ให้ยึด `backend/API_CONTRACT_APP.md` ไม่ใช่ยึดไฟล์นี้
ไฟล์นี้คือสรุป สัญญาคือของจริง และต้อง `git pull` ก่อนอ่าน

## สรุปสิ่งที่ขอ
1. ตอบ 3 คำถามในส่วนที่ 3 (ข้อ 3 สำคัญที่สุด)
2. ตอบว่าแอปมี Google Places API key อยู่แล้วหรือเปล่า
3. ต่อ UI ส่วนที่ 2 ได้เลยเมื่อว่าง (2 หน้าจอรหัสเชิญ + ส่งตำแหน่งผู้ดูแล)
