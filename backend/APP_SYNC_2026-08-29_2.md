# 1. ข้อ 3 — คุณต่อได้เลยวันนี้ 🟢

คุณเขียนมาว่า:

> *"ปัญหาคือ: อันนี้ทำไม่ได้จนกว่าจะรัน `flutterfire configure` เสร็จก่อน เพราะ
> `GET /api/recommendation` ต้องมี Firebase ID token ถึงจะยิงได้ — ถูกไหมครับ?"*

**ไม่ถูกครับ ตอนนี้ยังไม่ต้องมี** เราไม่ตอบจากความจำ — ยิงจริงเข้าฐานข้อมูล Neon ตัวจริง
โดยไม่ใส่ header อะไรเลยสักตัว:

```
AUTH_ENABLED as the process sees it: False
GET /api/recommendation/1   ->  200   PASSED AUTH
```

**200 ครับ ไม่ใช่ 401**

เพราะ `app/services/auth.py:50` อ่านค่าแบบนี้:

```python
return os.getenv("AUTH_ENABLED", "false").strip().lower() in ("1", "true", "yes")
```

ค่าตั้งต้นคือ **false** และไฟล์ `.env` ของเราไม่มีบรรทัด `AUTH_ENABLED` เลย → `current_caller`
คืน `ANONYMOUS` → `verify_patient_access` ผ่านตั้งแต่บรรทัดแรก **ทุก endpoint เปิดโล่งอยู่ตอนนี้**

## สิ่งที่คุณเข้าใจถูก และมันสำคัญ

**"พอเปิด auth แล้วต้องมี Firebase ID token"** — ถูกต้องเป๊ะ และนั่นคือเหตุผลที่ §7 บอกให้
**ใส่ `Authorization: Bearer` ไว้ตั้งแต่วันนี้ทั้งที่เซิร์ฟเวอร์ยังไม่อ่าน**

แต่สวิตช์นั้น**อยู่ที่ฝั่งเรา ไม่ใช่ฝั่งคุณ** และตอนนี้มันปิดอยู่ แปลว่า
**ลำดับงานที่คุณคิดว่าเป็น Firebase → แล้วค่อยต่อ backend จริง ๆ แล้วทำขนานกันได้**

| | ทำอะไร | ต้องรออะไร |
|---|---|---|
| **วันนี้** | เปลี่ยน `recommendedPlaces` จาก mock เป็นยิง `GET /api/recommendation/{id}` จริง | **ไม่ต้องรออะไรเลย** |
| ขนานกันไป | `flutterfire configure` + จับคู่ด้วยรหัส (§2) | รอสิทธิ์เข้าโปรเจกต์ Firebase |
| หลังจากนั้น | เราเปิด `AUTH_ENABLED=true` | รอ Firebase ของคุณเสร็จ |

## เรื่อง Firebase — ✅ เพิ่มคุณเข้าโปรเจกต์แล้ว ไปรันต่อได้เลย

**คุณไม่ได้ต้องการ "ไฟล์" ครับ** `flutterfire configure` ไม่ได้กินไฟล์ที่เราส่งให้ —
**มันล็อกอินบัญชี Google ของคุณแล้วไปดึง config มาเอง**

> ✅ **เพิ่มบัญชีของคุณเข้าโปรเจกต์ Firebase เป็น Editor เรียบร้อยแล้ว (29 ส.ค.)**
> ไม่ต้องรออะไรจากเราอีก

เหลือขั้นเดียวและเป็นของคุณ: รัน `flutterfire configure` ในโปรเจกต์ Flutter ของคุณ
→ มันจะสร้าง `firebase_options.dart` และวาง `google-services.json` ให้เอง
(เรารันแทนไม่ได้ เพราะไฟล์ต้องไปอยู่ในโปรเจกต์ของคุณ)

🛑 **และย้ำ `APP_SYNC_2026-08-27.md` §5 อีกครั้ง: อย่าขอ `serviceAccountKey.json`**
นั่นคือกุญแจ Admin SDK ของเซิร์ฟเวอร์ ใครถือก็อ่าน/เขียน/ลบข้อมูลได้ทั้งโปรเจกต์และ**ปลอมเป็น
ผู้ใช้คนไหนก็ได้** ห้ามอยู่ในแอป ห้ามส่งผ่านแชท ไฟล์ที่แอปต้องใช้คือ `google-services.json`
ซึ่งเป็น client config ที่ออกแบบมาให้ฝังไปกับแอปอยู่แล้ว

## เราจะเปิด tunnel ให้ตอนไหน — และเปิด auth ด้วยเลยไหม

**เราอยากทดสอบด้วยท่าจริง คือ auth เปิด** เพราะสุดท้ายก็ต้องใช้ท่านั้นอยู่ดี
แต่ท่านั้นต้องการ Firebase ของคุณก่อน ไม่ใช่ต้องการ URL — **ถ้าเปิด `AUTH_ENABLED`
ตอนที่แอปยังไม่มี Firebase แอปจะ 401 ทุกเส้น** และการทดสอบเกิดไม่ได้เลย

เลยเป็นแบบนี้ เอาตามว่าอะไรพร้อมก่อน:

| | เงื่อนไข | ทำอย่างไร |
|---|---|---|
| **ทางหลัก ⭐** | Firebase ของคุณใช้ได้ทันวันทดสอบ | **เปิด auth + tunnel พร้อมกัน** ทดสอบด้วยท่าจริงตั้งแต่ครั้งแรก ไม่ต้องมารื้อทีหลัง |
| ทางสำรอง | Firebase ยังไม่เสร็จ แต่คุณพร้อมทดสอบท่อแล้ว | tunnel + **auth ปิด** เฉพาะรอบนั้น แล้วเปิด auth ทันทีที่ Firebase คุณเสร็จ |

**ทางสำรองยอมรับได้เพราะตอนนี้ Neon มีแต่ข้อมูล seed 4 แถวกับ track GeoLife ปี 2008 —
ยังไม่มีผู้ป่วยจริงสักคน** สิ่งที่กฎ "เปิด auth ก่อนเปิด tunnel" ปกป้องไว้จึงยังไม่มีอยู่จริง
แต่มันคือทางสำรอง ไม่ใช่แผน

**ตอนนี้ทางหลักเปิดอยู่แล้ว** — บัญชีคุณถูกเพิ่มเข้าโปรเจกต์ Firebase เรียบร้อย
เหลือแค่คุณรัน `flutterfire configure` ยิ่งรันเร็ว โอกาสได้ทดสอบด้วยท่าจริง
ตั้งแต่ครั้งแรกยิ่งสูง และทางสำรองก็ไม่ต้องถูกใช้เลย

🛑 **และมีเส้นที่ไม่ยืดหยุ่น: วินาทีที่ตำแหน่งของ "คนที่ไม่ได้อยู่ในทีมนี้" เข้า Neon
`AUTH_ENABLED` ต้องเปิด** ไม่ใช่กำหนดเป็นวันที่ และไม่ใช่แค่ "มีแถวใน `users`" —
ผูกกับว่า*ใคร*อยู่ในข้อมูล ถ้าเราเดินทดสอบกันเองในทีม นั่นคือตำแหน่งของเราเองซึ่งเรารับ
ความเสี่ยงเองได้ แต่คนนอกทีมแม้แต่คนเดียวคือคนละเรื่องกันสิ้นเชิง

ตอนที่เปิด แอปที่ไม่ส่ง `Authorization` จะ 401 ทั้งตัวพร้อมกัน ซึ่งเป็นเหตุผลเดียวกับที่
ขอให้ใส่ header ไว้ตั้งแต่วันนี้

# 2. ข้อ 2 — เราตอบคุณผิดเมื่อวาน ขอแก้ 🔴

คุณขอ: **"เห็นสถานะ + ชื่อ + ตำแหน่งของคนที่กดรับ"**

เมื่อวานเราเขียนว่า *"ข้อมูลมีอยู่แล้วใน §12.3 อยากได้บอกมา ต่อให้ไม่ยาก"* —
**ครึ่งหลังจริง ครึ่งแรกไม่จริง** อ่านฟิลด์ออกมาจากโค้ดตรง ๆ:

```
RankedCaregiver -> caregiver_id, name, is_primary, distance_m, location_age_s, usable
AlertOut        -> id, patient_id, alert_type, severity, message, latitude, longitude,
                   resolved, claimed_by, claimed_by_name, claimed_at, created_at
```

* §12.3 คืน **`distance_m` ซึ่งเป็น "ระยะทางกี่เมตร" ไม่ใช่พิกัด** — ปักหมุดบนแผนที่ไม่ได้
* `AlertOut` **ไม่มีตำแหน่งของคนกดรับเลย** มีแค่ `claimed_by` / `claimed_by_name` / `claimed_at`
* **ไม่มี endpoint ไหนในระบบคืนพิกัดของผู้ดูแลออกไปเลยสักเส้น**

**ที่คุณได้ตอนนี้: สถานะ ✅ ชื่อ ✅ ตำแหน่ง ❌**

## ที่จะเพิ่มให้ ถ้ายืนยันว่าอยากได้

เพิ่ม 3 ฟิลด์บน `AlertOut`: `claimed_by_latitude` · `claimed_by_longitude` ·
`claimed_by_location_age_s` **ยังไม่ได้ทำ** บอกมาแล้วทำให้ ไม่บล็อกงานที่คุณทำอยู่ตอนนี้

ข้อดีที่บังเอิญเข้าทาง: **คนที่เพิ่งกดปุ่ม แปลว่าแอปเขาเปิดอยู่แน่นอน ณ วินาทีนั้น**
ตำแหน่งของคนกดรับจึงสดเสมอ ต่างจากคนอื่นในรายการ (ดูข้อ 3 ข้างล่าง)

> เราเก็บตำแหน่งผู้ดูแลแบบ**ล่าสุดจุดเดียว ไม่มีประวัติ** ตั้งใจ — เส้นทางย้อนหลังของ
> ผู้ดูแลคือการสอดส่องสมาชิกครอบครัวที่ไม่ใช่ผู้ป่วย โดยไม่มีฟีเจอร์ไหนรองรับ
> การโชว์ตำแหน่ง**คนที่กดรับ ระหว่างที่ยังรับอยู่** เป็นการใช้ที่มีเหตุผลรองรับชัดเจนและมีขอบเขต

# 3. ข้อ 1 — ขอคง 30 นาที ไม่ใช่ 10 นาที 🟡

เหตุผล "2 เท่าของ interval กัน delay" ของคุณ**ถูกต้อง สำหรับคำถามหนึ่ง** แต่มันเป็นคนละคำถาม
กับที่ค่านี้ใช้ตอบ:

| คำถาม | คำตอบที่ถูก |
|---|---|
| "อัปเดตรอบนี้มาช้าผิดปกติไหม" | 2× interval = **10 นาที ถูกของคุณ** |
| **"ตำแหน่งนี้ยังใหม่พอจะตัดสินว่าใครอยู่ใกล้ที่สุดไหม"** ← ค่านี้ตอบข้อนี้ | ขึ้นกับคนเดินเร็วแค่ไหน ไม่ใช่แอปส่งถี่แค่ไหน |

## ประโยคแรกของคุณเองคือปัญหา

> *"ตอนแอปผู้ดูแลเปิดอยู่"*

ตอนตี 2 ที่ผู้ป่วยเดินออกจากบ้าน **แอปผู้ดูแลปิดอยู่ทุกเครื่อง** ไม่มีใครส่งตำแหน่งมาหลายชั่วโมงแล้ว

ไม่ได้แปลว่าใครถูกตัดออก (ไม่มีใครถูกตัด — นั่นคือทั้งหมดของ "ดันไปท้ายแถว ไม่ตัดออก")
แต่ปัญหาอยู่ที่**ลำดับการเรียง** ใน `app/api/users.py`:

```python
rows.sort(key=lambda c: (not c.usable, c.distance_m, not c.is_primary, c.caregiver_id))
#                        ^^^^^^^^^^^^ ความสด มาก่อน ระยะทาง เสมอ
```

**ความสดชนะระยะทางเด็ดขาด** ตั้ง 10 นาทีแล้วเจอเคสนี้:

| | ระยะจากผู้ป่วย | อัปเดตล่าสุด | เกณฑ์ 10 นาที | เกณฑ์ 30 นาที |
|---|---|---|---|---|
| ลูกชาย — เปิดแอปค้างอยู่ที่ห้าง | **20 กม.** | 2 นาที | ✅ **อันดับ 1** | อันดับ 2 |
| ลูกสาว — บ้านติดกัน ปิดแอปไป 12 นาที | **500 ม.** | 12 นาที | ❌ อันดับ 2 | ✅ **อันดับ 1** |

ที่ 10 นาที ระบบตอบว่า **"ใครบังเอิญเปิดแอปค้างไว้"** แทนที่จะตอบ **"ใครอยู่ใกล้ที่สุด"**
ซึ่งเป็นคำถามเดียวที่ endpoint นี้มีไว้ตอบ ครอบครัวจะโทรหาผิดคน

**ดังนั้นคง `caregiver_location_max_age_seconds = 1800` ไว้** ค่านี้อยู่ในฐานข้อมูล
เปลี่ยนทีหลังได้ตลอดด้วย SQL แถวเดียว ไม่แตะโค้ด ไม่ deploy ไม่กระทบแอป
ถ้าวันหน้ามีข้อมูลจริงว่าคนเปิดแอปบ่อยแค่ไหน เราปรับตามได้ทันที

## ที่ UI ต้องรู้

**`usable: false` ไม่ได้แปลว่า "คนนี้ใช้ไม่ได้"** แปลว่า **"ลำดับนี้เชื่อได้น้อยลง"**
ซึ่งคุณรับข้อนี้ไปแล้วและทำถูก: แสดงต่างออกไป (เทาลง / เขียนว่า "ตำแหน่งเมื่อ 2 ชม.ที่แล้ว")
**ไม่ใช่ซ่อน** `location_age_s` ส่งมาให้ดิบ ๆ ทุกแถว เอาไปเขียนข้อความเองได้

## ✅ ส่วนที่ไม่ต้องเถียงกัน: 3-5 นาทีตอนแอปเปิด ไม่ทำ background service เต็มรูปแบบ

**เห็นด้วยทั้งข้อ** และเหตุผล MVP ของคุณถูก — เราไม่ได้ขอ background service สำหรับ
ตำแหน่ง**ผู้ดูแล** เลย

> ⚠️ แต่คนละเรื่องกับ**ตำแหน่งผู้ป่วย** — อันนั้น W2 ของแผนคือ "ติดตามต่อเนื่องขณะปิดจอ
> หนึ่งชั่วโมงไม่ขาด" ซึ่งต้องเป็น background service จริง ๆ คนละ requirement กันคนละตัว
> อย่าเผลอเอาเหตุผล "ไม่ทำ background service" ข้ามฝั่งไปที่ผู้ป่วย
