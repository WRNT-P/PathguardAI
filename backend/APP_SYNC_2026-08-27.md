## 1. รหัสจับคู่ — ใช้ของ backend และ**ลบ `patient_directory.dart` ทิ้งได้เลย**

ที่เจอว่าไม่ตรงกัน ถูกแล้ว และคำตอบคือใช้ของ backend เพราะเหตุผลด้านความปลอดภัย
ไม่ใช่เพราะใครเขียนก่อน

`POST /api/pair` **ไม่มีตัวนับการเดาผิดและไม่มี rate limiting** — โดยการออกแบบมันคือ
route เดียวที่ต้องทำงานได้ก่อนผู้เรียกจะมี token ใด ๆ **ตัวรหัสคือ credential ทั้งหมด**
ความยาวรหัสจึงเป็นการป้องกันทั้งหมดที่มี

| | จำนวนความเป็นไปได้ |
|---|---|
| 6 หลักตัวเลข | **1,000,000** |
| 8 ตัวจากตัวอักษร 30 ตัว (ของ backend) | **656,100,000,000** |

หนึ่งล้าน + เดาได้ไม่จำกัด = สคริปต์ไล่หมดในไม่กี่นาที แล้วได้ token เข้าถึงตำแหน่งสด
ของผู้ป่วยสมองเสื่อม ต่างกัน 656,000 เท่า ถ้าจะใช้ 6 หลักจริง ๆ ต้องเพิ่ม rate limiting
ก่อน ซึ่งเป็นงานมากกว่าการเปลี่ยนรูปแบบรหัส

### ข่าวดี: `patient_directory.dart` ไม่ต้องแก้ ให้ลบ

เซิร์ฟเวอร์เป็นคนสุ่มรหัส เก็บลงตาราง และคุมอายุ/การใช้ซ้ำให้เอง ฝั่งแอปแค่เรียก:

```
POST /api/patients
{ "name": "ยาย", "severity_level": 2 }

→ 201
{ "patient_id": 42, "name": "ยาย", "severity_level": 2, "caregiver_id": 12,
  "pairing_code": "FV49-6D2Q", "expires_at": "2026-08-28T09:15:00Z" }
```

* **แสดง `pairing_code` ตามที่ส่งมา รวมขีดคั่น** มันถูกจัดกลุ่มละ 4 มาแล้ว เพราะผู้ดูแล
  ต้องอ่านออกเสียงให้อีกเครื่อง
* **ตัวอักษรที่ใช้: `23456789ABCDEFGHJKMNPQRSTVWXYZ`** — ไม่มี `0 O 1 I L U` ตั้งใจตัดออก
  เพราะเป็นคู่ที่คนคัดลอกผิดบ่อยที่สุด (`U` ตัดเพราะเขียนมือแล้วกลายเป็น `V`)
* **อายุ 24 ชั่วโมง ใช้ได้ครั้งเดียว**

### หน้า login ของผู้ป่วย

* `keyboardType: TextInputType.number` → เปลี่ยนเป็น `TextInputType.text`
* แนะนำ `textCapitalization: TextCapitalization.characters`
* **ไม่ต้อง validate รูปแบบเอง** เซิร์ฟเวอร์รับตัวพิมพ์เล็ก รับขีดคั่น รับช่องว่างท้าย
  แล้ว normalise ให้เอง — ผู้ดูแลพิมพ์ `fv49 6d2q` ก็ผ่าน
* ตอบกลับ:

```
POST /api/pair
{ "code": "FV49-6D2Q" }

→ 200
{ "patient_id": 42, "firebase_custom_token": "..." }
```

เอา `firebase_custom_token` เข้า `signInWithCustomToken()` แล้วเครื่องผู้ป่วยก็เป็น
ผู้ใช้ปกติที่ส่ง `Authorization: Bearer <ID token>` ได้ตลอดไป **ไม่ต้อง pair อีกเลย**

### ข้อความ error

`400/404` มี **ข้อความเดียวสำหรับทั้งสามกรณี** (รหัสผิด / หมดอายุ / ใช้ไปแล้ว)
ตั้งใจไม่แยก เพราะการบอกว่า "รหัสนี้หมดอายุ" คือการยืนยันกับคนนอกว่ารหัสนี้มีอยู่จริง
ฝั่งแอปแสดงข้อความเดียวไปเลย

## 2. SOS — endpoint มีอยู่แล้ว ตั้งแต่ 26 ส.ค.

ที่บอกว่าหาไม่เจอในเอกสาร **เป็นความผิดของเรา ไม่ใช่การเข้าใจผิด** —
หัวข้อ 8 ถูกเพิ่มเข้า `API_CONTRACT_APP.md` วันเดียวกับที่สร้าง แต่ไฟล์ที่ส่งให้เป็นฉบับก่อนหน้านั้น
**`git pull` แล้วเปิด `backend/API_CONTRACT_APP.md` หัวข้อ 8 จะเห็นฉบับเต็ม** —
ต่อไปอ่านจากรีโปแทนไฟล์ที่ส่งกันทางแชท จะได้ไม่ค้างอีก

```
POST /api/sos
{ "patient_id": 42, "latitude": 13.7563, "longitude": 100.5018 }
```

* **พิกัดไม่บังคับ** ถ้าเครื่องหา GPS ไม่ได้ก็ส่งมาแค่ `patient_id` — ปุ่มที่กดไม่ได้
  ตอนไม่มีสัญญาณคือปุ่มที่พังตอนที่ต้องใช้ที่สุด
* **ข้ามการคำนวณคะแนนทั้งหมด** ไม่มีเงื่อนไขว่าเสี่ยงพอหรือยัง คนกดเองแปลว่าต้องส่ง
* cooldown ของตัวเอง **60 วินาที** (ไม่ใช่ 10 นาทีเหมือน alert อัตโนมัติ) เพราะกดซ้ำ
  = คนกดใหม่ = ข้อมูลใหม่

### เรื่องที่บอกว่า "ข้อความ SOS โกหกได้" — ถูกต้อง และนี่คือกฎ

response มี field **`push`** ค่าที่เป็นไปได้:

| `push` | แปลว่า | ควรบอกผู้ป่วยว่า |
|---|---|---|
| `sent` | ส่งถึงเครื่องผู้ดูแลแล้ว | "แจ้งผู้ดูแลแล้ว" |
| `cooldown` | เพิ่งส่งไปไม่ถึงนาที ยังไม่ส่งซ้ำ | "แจ้งไปแล้วเมื่อครู่ กำลังรอ" |
| `no_caregiver` | **ผู้ดูแลยังไม่ได้ลงทะเบียนเครื่องรับแจ้งเตือน** | ⚠️ "ส่งไม่ถึง" ต้องบอกตรง ๆ |
| `failed` | FCM ปฏิเสธ | ⚠️ "ส่งไม่ถึง" |
| `error` | อย่างอื่นพัง | ⚠️ "ส่งไม่ถึง" |

**`201` แปลว่า "บันทึกแล้ว" ไม่ใช่ "ถึงมือแล้ว"** — ถ้าขึ้น "มีคนกำลังมาช่วย" ทั้งที่
ไม่มีใครรู้เรื่อง ผู้ป่วยจะยืนรออยู่ตรงนั้น นี่เป็นเหตุผลเดียวที่ field นี้มีอยู่

## 3. `severity_level` — ช่องโหว่ฝั่ง backend ที่เจอเพราะข้อความนี้

เมื่อเห็นว่าแอปแยกหน้า Level 1 / Level 2 เราไปไล่ดูว่าเครื่องผู้ป่วยรู้ได้ยังไงว่าตัวเอง
เป็นระดับไหน แล้วพบว่า **รู้ไม่ได้**

* `severity_level` ส่งกลับที่เดียวในระบบคือ `POST /api/patients` ซึ่งเป็นการเรียกของ**ผู้ดูแล**
* `POST /api/pair` ที่เครื่องผู้ป่วยเรียก คืนแค่ `patient_id` กับ token
* และแอปเรียก `/api/pair` **ครั้งเดียวตลอดชีวิตเครื่อง** — เปิดแอปรอบหน้าใช้ token ที่
  cache ไว้ ไม่ได้ pair ใหม่ ต่อให้ยัด `severity_level` ใส่ response ของ pair
  ก็ยังอ่านซ้ำไม่ได้อยู่ดี

**เดาว่านี่คือเหตุผลที่บอกว่า "หน้า Level 2 navigation ทำไว้แล้ว แต่ยังไม่มีทางเข้าถึง"**
— หน้ามี แต่ไม่มีข้อมูลมาตัดสินใจว่าจะพาใครไปหน้าไหน

### เราจะแก้ให้

เพิ่ม `GET /api/patients/{patient_id}` คืน `patient_id · name · severity_level`
คุ้มด้วยระบบสิทธิ์เดียวกับ route อื่น และเพิ่ม `severity_level` ใน response ของ
`POST /api/pair` ด้วย จะได้ไม่ต้องยิงสองครั้งตอนจับคู่

**ฝั่งผู้ดูแลก็ต้องใช้** ตอนนี้อ่านชื่อกับระดับของผู้ป่วยตัวเองกลับมาไม่ได้เลยเหมือนกัน

**ขึ้น `main` แล้ว 2026-08-27** — `GET /api/patients/{patient_id}` และ `severity_level`
ใน response ของ `POST /api/pair` ใช้ได้จริงแล้วทั้งคู่ รายละเอียดอยู่ที่
`API_CONTRACT_APP.md` หัวข้อ 2 ขั้นที่ 4 — `git pull` แล้วอ่านได้เลย

## 5. 🛑 Firebase — ไฟล์ที่ต้องขอ ไม่ใช่ `serviceAccountKey.json`

ที่เขียนว่า "ต้องขอไฟล์ config จากเพื่อน" — ระวังตรงนี้ เพราะชื่อมันคล้ายกันแต่คนละชั้นความลับ

| ไฟล์ | คืออะไร | ส่งให้กันได้ไหม |
|---|---|---|
| `google-services.json` (Android)<br>`GoogleService-Info.plist` (iOS) | **client config** — ตั้งใจให้ฝังไปกับแอปอยู่แล้ว โหลดจาก Firebase console แยกต่อแอป | ✅ **นี่คือไฟล์ที่ต้องใช้** |
| `serviceAccountKey.json` | **Admin SDK private key ของเซิร์ฟเวอร์** ใครถือ อ่าน/เขียน/ลบข้อมูลได้ทั้งโปรเจกต์ และสร้าง token ปลอมเป็นผู้ใช้คนไหนก็ได้ | 🛑 **ห้ามส่ง ห้ามใส่ในแอป ห้ามผ่านแชท** |

แอปไม่ต้องใช้ตัวหลังเลย มันอยู่ฝั่งเซิร์ฟเวอร์อย่างเดียวเพื่อออก custom token ให้ `/api/pair`

### วิธี sign-in ที่ตกลงกัน

1. เครื่องผู้ป่วยกรอกรหัส → `POST /api/pair` → ได้ `firebase_custom_token`
2. `FirebaseAuth.instance.signInWithCustomToken(token)`
3. จากนั้นส่ง `Authorization: Bearer <ID token>` ทุก request

**ส่ง header นี้ตั้งแต่ตอนนี้เลย แม้เซิร์ฟเวอร์จะยังไม่ตรวจ** วันที่เราเปิดระบบยืนยันตัวตน
แอปที่ไม่เคยส่งจะขึ้น 401 พร้อมกันทั้งตัว
